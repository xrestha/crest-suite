## B2. Till controls — enforced server-side (added S577, completed S579)

Not from a competitor audit; these came out of the phase-6 critique of our own code, and all three were
the same shape: a rule the browser applied and the database did not. **All three are applied to
the live DB and smoke-tested from a real POS PIN session (2026-08-19)** — method in
`.claude/rules/pos-billing.md`; note that admin and Owner are exempt from every one of these guards
by design, so an admin session proves nothing about them.

- [x] ~~Discount cap + void permission enforced only in React~~ — shipped S577. `pos_orders_client`
  is a plain same-client `FOR ALL` policy, so a Staff-rank till JWT held UPDATE on every one of its
  own client's orders; one PATCH walked past both checks. Now `guard_pos_order_close()`, a BEFORE
  UPDATE trigger (chosen over the RPC the critique proposed — an RPC protects only the callers that
  choose to call it). Smoke-tested live: a direct PATCH from a till session gets 403 on a void and
  on an over-cap discount, 200 on an at-cap one. `paid_amount` is deliberately NOT enforced — a
  second copy of the VAT/rounding maths would reject real bills mid-service if it ever drifted.
- [x] ~~An already-fired KOT item could be pulled with no permission, reason or record~~ — shipped
  S577. `pos_kot_removals`, written **inside** `save_pos_order_items` from its own before/after
  diff, so no caller can remove a fired line without producing the record. Deliberately a record,
  not a block: pulling a fired item is routine, and rank-gating it would stall a live service.
  Surfaced as KOT Log → **Pulled Items**.
- [x] ~~Item-level comp was browser-only~~ — shipped S579, closing the family. Three holes in one
  act: nothing guarded the comp columns (a till JWT could PATCH `comped = true` and the line left
  the bill with no NC number, reason, attribution or slip); `apply_pos_item_comps` checked client
  but not **rank**, while the UI gates the panel on Supervisor+; and `p_comped_by` was
  caller-supplied, so a comp could be recorded under a colleague's name — the column the Sales
  Exception Report ranks staff by. Now `guard_pos_item_comp()` fences the six columns while
  `apply_pos_item_comps` (SECURITY DEFINER, so `current_user` is the owner) remains the only write
  path, checks Supervisor rank, and derives `comped_by` from `auth.uid()`.

- [x] ~~Stock Ageing Report (FIFO/Expiry shows dates, not aging buckets)~~ — **shipped S591
  (2026-08-19)**, the last 🔴 on this list. `/stock-ageing` (Pro, IMS): how long the stock still
  on hand has been sitting, bucketed 0-30 / 31-60 / 61-90 / 90+ days across a BS fiscal year,
  valued at what was actually paid for each surviving batch. Headline figure is the working
  capital sitting in 90+ day stock. Distinct from FIFO / Expiry, which is single-period and covers
  only items carrying an expiry date — this covers every item and answers "what is my money doing
  on the shelf" rather than "what is about to go off". The arithmetic is a pure, tested module
  (`stockAgeingCalc.js` + 15 tests) rather than page code, same reasoning as
  `supplierAttribution.js`: it is a stock valuation, so a wrong figure reads as a plausible one.
  Two honesty rules baked in — consumption is **not** tracked per batch anywhere in the schema, so
  this is the standard FIFO assumption (stated on the page, same basis FIFO / Expiry uses), and
  stock carried in from before the window is aged from the window start, flagged `c/f`, and
  disclosed as "age ≥ FY start" rather than being given a precision it does not have. Sales run
  through `selectDepletingSales` (S588), so a POS + manual client cannot over-consume its own
  batches and make real stock vanish off the shelf.

## D. Known roadmap items

- [x] ~~S532 verification pass: POS PIN lockout was still bypassable after S531~~ — 2026-08-10, found by auditing what `anon` can actually EXECUTE rather than by re-reading the code (see `README.md` S532). S531 correctly moved `check_pos_pin_lock`/`record_pos_pin_attempt` *inside* `pos-staff-login` so the browser can't skip them, but never revoked the EXECUTE grant the browser had needed — all four lockout functions were created with no explicit GRANT/REVOKE, so they carried Postgres's default `GRANT EXECUTE TO PUBLIC`, and PUBLIC includes `anon`. `record_pos_pin_attempt` is `SECURITY DEFINER` with no auth check and its success branch is `UPDATE profiles SET pos_pin_failed_attempts = 0, pos_pin_locked_until = NULL WHERE id = p_staff_id`, so one anonymous POST with `p_success: true` cleared the counter for any staff member. POS is shielded in practice by the `pos_device_secret` gate that runs first (an attacker needs a valid device secret before the lockout is even reachable) — HR Self-Service, which takes only `{staff_id, pin}`, was the exploitable path. Fixed in `20260810190000` (`service_role`-only on the four lockout functions). Root cause is a grant trap distinct from the one already documented: an EXECUTE grant is per **signature**, not per name, so adding a parameter to a previously-hardened function creates a new signature carrying a fresh PUBLIC grant — `submit_guest_order` (both overloads) surfaced in the same audit for exactly this reason, alongside `submit_my_leave_request`/`submit_my_tada_claim`. **Verified live in a browser**: correct PIN signs in, four wrong PINs return `401`, the fifth returns `423` "Too many incorrect attempts" — the `423` being the proof, since it means the counter advanced across five separate requests under `service_role`.
- [x] ~~S440 offline-sync hardening pass~~ — 2026-07-22, found during a whole-app audit/debug pass (see `README.md` S440). Two fixes on the POS offline order-taking path, a sibling to S372's own `flushPosOrderQueue` idempotency fix: (1) `enqueuePosOrder` in `offlineQueue.js` did a read-modify-write across *two* IndexedDB transactions (readonly `get` → merge → readwrite `put`). `saveOrder` fires `logKotSend('KOT')` + `logKotSend('BOT')` un-awaited back-to-back, both routing through it while offline — so two concurrent calls read the same `kot_sends:[]` pre-image and the second `put` clobbered the first, silently dropping one station's queued KOT/BOT send so it never replayed into `pos_kot_log` on sync (KOT Reconciliation under-counts; the physical ticket still printed, so no *order* was lost). Fixed by collapsing get+merge+put into a single `readwrite` transaction — IndexedDB serialises overlapping readwrite transactions on a store, so the append is now atomic regardless of await ordering. (2) Offline orders minted their permanent `pos_orders.id` from `crypto.randomUUID()`, `undefined` on WebViews older than Chrome 92 / Safari 15.4 — would throw mid-save, lose the order, and hang the save button. Added `src/utils/uuid.js` (native, falling back to a `getRandomValues` v4) and wired it in. Re-confirmed billing stays hard-gated offline (`payDisabled` includes `!isOnline`) — the offline surface is order-taking only, no money path. Build clean, 91/91 tests pass.
- [x] ~~Discount netting bug + Stock Movements ledger report~~ — shipped S395, 2026-07-15, found via a cross-module (IMS↔POS↔HR) audit. Two related fixes: (1) `writeSalesEntries()` in `PosOrders.jsx` snapshotted `unit_price` on `'pos'`-source `sales_entries` rows at full pre-discount price regardless of the bill's `discountAmt`/`discRatio` — meaning every IMS revenue report reading that column (Monthly/Annual/Period Comparison Summary, Menu Repricing/Engineering, Recipe Margin, Overheads, Best Sellers, Sales.js, Owner Dashboard's Food Cost %/Net Margin %) silently overstated revenue by the discount total on every discounted bill, since S286's `pos_comp` source-exclusion fix only handled comps, never discounts. Fixed by applying the same `discRatio` already computed for the bill's own VAT recalc to `'pos'`-row `unit_price` (only on `closeType === 'paid'`); `'pos_comp'` rows stay full-price since they're already revenue-excluded and only `qty_sold` is read downstream. (2) `stock_movements` (the POS depletion ledger from S228/IMS stock deduction trigger) turned out to have exactly one reader anywhere in the app — Reorder Report's Book Stock column — with no way to see the ledger itself. New `/stock-movements` report (Starter, `stock_movement_log` flag) shows the full per-period ledger: item, qty depleted, source (POS Sale/Comp), the causing order (click-through via the existing `viewPosBill()` helper), staff, and food-cost value; a "Comp Value" stat card surfaces what complimentary items actually cost — a number that existed nowhere else despite comps correctly being zero-revenue everywhere else.
