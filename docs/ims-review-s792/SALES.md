### SALES-1 [P0] Saving a day (or the Bulk total) silently deletes the recorded sales of any HIDDEN dish
- Where: src/modules/ims/sales/Sales.js:236 (menu read `.eq('is_active', true)`), buildDailyRows :417-435, buildBulkRows :454-470; save_sales_day step (1) supabase/migrations/20260727180000_save_sales_day_manual_only.sql:56-59; depletion replaced from the same payload persistSalesDay.js:186-192 / 245-318.
- What happens: staff enter Daily sales for days 1–14 including "Mango Lassi". On day 15 a supervisor HIDES Mango Lassi (Recipe Costing → Hide, D3 — and Hide is the path Recipes points to for any dish that has sold, since sales_entries refuses a delete). On day 16 someone corrects day 10's momo count and presses Save Day. The payload is built only from `recipes` (active, non-sub-recipe), so Mango Lassi is not in it; save_sales_day deletes EVERY manual row for (period, day 10) and inserts the payload → day 10's Mango Lassi revenue row is gone, and depleteManualSales rewrites day 10's stock_movements from the payload, so its ingredient usage goes too. Same on Bulk: one Bulk Save deletes the hidden dish's whole-month bs_day 0 row. Nothing on screen ever showed the row (the grid, Period Summary and Daily Breakdown all iterate `recipes`), nothing warns (findSupersededRows only looks at payload recipes), and the S457 modal never opens. Also hits legacy recipes with is_active NULL (column is nullable, baseline:1303) and a dish re-categorised to Sub-Recipe.
- Secondary (display): Sales Entry's "Period Revenue" card (tooltip: "Used as the denominator for Food Cost %") and Period Summary leave out a hidden dish's sales, while Monthly Summary's periodRevenue (periodCost.js:22-31) counts every row — two revenue figures for one month.
- Evidence: `scopedFrom('recipes').eq('is_active', true).or('category.is.null,category.neq.Sub-Recipe')` (Sales.js:236); `return recipes.filter(r => (merged[r.id] || 0) > 0).map(...)` (:428-434); RPC `DELETE FROM sales_entries WHERE period_id = p_period_id AND bs_day = p_bs_day AND (source IS NULL OR source = 'manual');`. This is S699's "an ENTRY page that under-counts loses the row", via is_active instead of source.
- Status: missed by S756 (S699/S714 fixed the NULL-source and NULL-category versions of this same read; the is_active filter was never examined).
- Fix: carry every stored manual row whose recipe is not in the on-screen menu through the payload unchanged (qty, stored unit_price/vat_rate, discount) and show those dishes in a "hidden dishes with sales this period" block (see Owner question 2); compute Period Revenue from all rows like Monthly Summary.
- Confidence: Confirmed (read → payload → RPC delete read end to end). Severity P0 by the brief's rubric (silent deletion of stored rows); it needs a hidden dish with manual rows in a month someone can still edit.

### SALES-4 [P2] Two quick saves of the same day can deplete that day's stock twice in the ledger
- Where: Sales.js:647 (`depleteManualSales(...)` not awaited), :654 (repost, not awaited); persistSalesDay.js:245-318 (POS guard read → delete the day → explode recipes → insert: 4+ round trips, no lock).
- What happens: Save Day re-enables once the RPC returns and the day reload lands (~1 s). Saving, spotting a typo and saving again starts a second replaceManualMovements for the same day while the first is still exploding recipes. Interleaving A-delete, B-delete, A-insert, B-insert leaves two sets of manual movements for the day. stock_movements feeds Stock Movements and Reorder's Book Stock (ReorderReport.js:140), which then read low. sales_entries itself is fine (atomic RPC).
- Status: missed by S756 (S683/S756 made each run fail-safe, not mutually exclusive).

- Confidence: Plausible — confirm by throttling the network and pressing Save Day twice within ~2 s, then counting that day's `source='manual'` movements.

## GAPs
- **Nobody can see who changed a day's sales, or what it said before.** sales_entries has no log_audit trigger (baseline + 20260804040000), and the supersede modal itself says deleted entries "are not recoverable". Any IMS staff login can rewrite an open month's daily revenue with no trace — an owner comparing the till roll with the screen has nothing to check against.
- **Hidden dishes vanish from Sales Entry.** A seasonal dish hidden mid-month disappears from every tab, including what it already sold this month (see SALES-1). An owner expects "hide from the menu", not "hide from my sales record".
- **The Excel import forgets name matches.** Only exact product names match; a vendor export's "Chicken Momo (Steam)" vs the menu's "Steam Chicken Momo" lands in the unmatched list every single day and must be typed by hand each time. A remembered mapping (file name → menu item) would save the daily re-typing.
- **The Bulk row cannot say which days it covers.** An owner who types a month-so-far total and later switches to the till has no way to tell the system "this total covers days 1–15" (see Owner question 1), so the two cannot be reconciled.

## Owner questions
1. **You typed a whole-month total for a dish, then started using the till for it later in the same month. What should stock reports do with the typed total?** Today the till's first sale of that dish anywhere in the month makes every stock report ignore the typed total completely (salesDepletion.js:53), while revenue still counts it and Stock Movements still deducts it — so days before the till show as "stock used but not sold". Options: (a) keep today's rule; (b) keep counting the typed total for stock alongside the till (risk of counting the same plates twice if the total included till days); (c) when the till starts selling a dish, show a notice on Sales Entry asking you to re-enter that dish's pre-till days as daily figures, and ignore the typed total only after that. Recommendation: (c) — it keeps one fact per plate and tells you what to fix.
2. **Should a hidden dish that already has sales this month still show on Sales Entry?** (a) Yes, editable, in a separate "Hidden dishes with sales" block; (b) yes, read-only (corrections only after un-hiding); (c) no, but saves must never delete its rows. Recommendation: (a) — a correction should not need un-hiding a dish, and nothing that is saved should be invisible on the page that saves it.
