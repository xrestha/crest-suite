### MASTER-1 [P0] Item Master, Vendors and categories carry no IMS rank guard — any IMS login, a 4-digit count PIN included, rewrites master data over REST
- Where: `items` / `vendors` / `categories` policies (baseline `items_all`, `vendors_all`, `categories_all`); S756 self-check list `supabase/migrations/20260918100000_ims_integrity_s756.sql:810-813` (15 guarded tables, none of these three).
- What happens: Item Master and Vendors are supervisor+ pages, but the database lets every IMS account — staff rank, and the count PIN that `ims_caller_has_rank` refuses everywhere else — PATCH these rows with its own JWT: `items.uom` (every past count, purchase and recipe line re-read ×1000; D5's "refuse a unit change" exists only in Items.js), `items.is_active` (a hidden item drops out of stock valuation and Monthly Summary), `items.rate` (re-values closed months), `items.yield_pct`; `vendors.name` / `pan_vat_no` (every past bill, Vendor Report, 1L report and balance letter read the name/PAN off this row, and `vendors` has no audit trigger, so a rename leaves no trace), `vendors.archived_at` / `is_active` (D25 makes archive/restore Owner-only; Vendors.js:75-78 admits "this widens the page, not the database's protection"). Only DELETE is fenced (the BEFORE DELETE triggers).
- Evidence: `ims_rank_guard` is attached to purchase_entries, vendor_returns, payable_payments, par_levels (+ bespoke guards on requisitions, stock_movements, recipes, assets). Writer inventory: the only staff-rank writer of `items` is PurchaseBillPage's post-save rate sync (`rate` only, PurchaseBillPage.jsx:256); `vendors` has no staff-rank writer (Vendors.js supervisor; Settings.js and OutstandingPayables manager); `categories` is written only by Items.js' default seed (supervisor) and Recipes.js' Sub-Recipes row (supervisor). The count PIN has no legitimate writer of any of the three.
- Status: missed by S756 (its stage-1 writer inventory fenced 15 tables and stopped short of master data). Extends the ⚪ S761 caveat (count PIN writes opening/wastage/staff meals over REST) to master data, where one write re-values or re-reads every closed month.
- Fix: `ims_rank_guard`-style triggers — vendors/categories INSERT/UPDATE supervisor; items INSERT supervisor, UPDATE staff only when nothing but `rate` changes, otherwise supervisor; all refuse `ims_email`. Plus a BEFORE UPDATE OF uom trigger that refuses while `item_reference_counts()` > 0 (D5 in the database), with the DEFINER/service-role seam for restore.
- Confidence: Confirmed (policies and trigger lists read). Exploiting it needs an insider replaying the tablet's session token against /rest/v1.

### MASTER-2 [P1] `push_master_data` rewrites a branch item's unit (and active flag) while keeping its rate — D5 bypassed on every adopted or updated item
- Where: `supabase/migrations/20260909120000_items_client_name_unique.sql:329-335` (latest body; later migrations only mention it in comments).
- What happens: HQ "MILK" is in LTR. A branch set up before it joined the group has its own "MILK" in ML with a year of counts and bills. The first push plans it `adopt` ("matched an existing item of the same name") and applies `UPDATE items d SET … uom = s.uom, conversion_factor = s.conversion_factor, is_active = s.is_active …`, leaving `rate` alone on purpose. Every stored ML quantity at that branch now reads as LTR (×1000), and the branch's per-ML rate is now read as a per-LTR rate, so stock value, COGS and food cost change for every past month there, with nothing to flag it. `is_active = s.is_active` also hides a branch item because HQ hid theirs, which takes its stock out of the branch's valuation.
- Evidence: the plan detail the Owner approves is `'definition only - this branch keeps its own rate'` (update) or `'matched an existing item of the same name'` (adopt). The preview never mentions a unit change.
- Status: missed by S756 (D5 was built into Items.js only; the push is the other app path that writes `items.uom`).
- Fix: in the plan, mark `conflict` (skipped and reported) when `d.uom <> s.uom` and the branch item has references, naming both units; never copy `is_active` onto an existing branch row.
- Confidence: Confirmed by reading the SQL. It only bites a grouped client with a same-name item in a different unit.

### MASTER-3 [P1] "Sign out all counting tablets" does not sign out a tablet that is already signed in, which is the lost-tablet case it exists for
- Where: `rotate_ims_device_secret` (20260918100000:762-789); `revokeClientTablets` (admin-user-ops/index.ts:57-63); StockCountSettings.jsx:168-188 (dialog copy); Layout.js:582-586 (the idle lock is POS-only).
- What happens: rotation changes `client_secrets.ims_device_secret`, which only `get_ims_count_staff` and `ims-staff-login` check, so only the NEXT sign-in is affected. A counter already signed in holds an ordinary Supabase session (a refresh token, kept alive by the session keep-alive). Nothing in ProtectedRoute or Stock.js re-checks the device, and count sessions have no idle lock (`isPinStaff = !!profile?.pos_role`). A tablet lost mid-count stays signed in as that counter and can keep writing counts (and, via the ⚪ S761 item and MASTER-1, more over REST). The dialog says: "Every tablet and phone set up for counting stops working straight away, including ones that are lost or stolen."
- Evidence: the fix shape already exists in the codebase: `finalize_final_settlement` does `DELETE FROM auth.sessions WHERE user_id = l.id` (20260915090000:436). Neither rotation path touches sessions.
- Status: missed by S756 (D4 as built).
- Fix: in `rotate_ims_device_secret` (and `revokeClientTablets`), delete `auth.sessions` for the client's `ims_email` profiles. Until then, correct the dialog copy and point at IMS Staff → Delete for a lost device.
- Confidence: Confirmed by code reading (session survival not tested live).

### MASTER-4 [P2] An IMS manager can create or promote IMS Managers; HR and POS allow that to the Owner only
- Where: admin-user-ops/index.ts `create_ims_staff` 1551-1553 and `update_ims_role` 1703-1705 (no `MANAGER_GRANT_MSG` check); compare POS 964/1292 and HR 1824/1895-1896. ImsStaff.jsx offers Manager in the row role select (updateRole), in custom-role level sync (updateCustomRoleLevel) and in applyMismatches.
- What happens: an IMS manager creates another Manager login, or promotes a supervisor. Under `requireManageableTarget` they then cannot undo it; only the Owner can. Manager rank unlocks supplier payments, Overheads, the finance reports, asset posting, IMS thresholds and staff management.
- Status: NEW. The S752/S754 rule "only the Owner grants Manager" was applied to HR and POS; IMS was not swept.

- Confidence: Confirmed. See Owner question 1.

### MASTER-5 [P2] Adding two items in one visit gives both the same item code, and Recipe Import looks ingredients up by code first
- Where: Items.js:532-535 (`getNextItemCode` reads `book.codes`), 751-753 (`save()` reloads `items` only), 195-226 (`book` is rebuilt only by `checkAllUsage`); RecipeImportButton.jsx:25, 51, 344-349.
- What happens: add ITEM A and it gets ITM-010. `book` is not refreshed, so adding ITEM B in the same visit mints ITM-010 again. This is common during setup (the S790 setup guide). Recipe Import's template lists item codes on its reference sheet, and `itemByCode.get(key) || itemByName.get(key)` resolves a code before a name. With two items on ITM-010 the Map keeps the last one, so a recipe line typed as "ITM-010" silently links the other item (the preview prints what was typed, not what it resolved to). The result is a wrong recipe cost and wrong theoretical usage. item-master-rates.md's "nothing keys off item_code" is no longer true. The same staleness makes the duplicate-name check miss a name added earlier in the visit; the DB index catches it, but the message says the name was "saved while this dialog was open".
- Status: NEW since S707 (S707 moved code minting onto `book` without refreshing it after an add).
- Fix: after a successful insert, add the new code and name to `book` (or call `checkAllUsage()`). In Recipe Import, refuse a code that matches more than one item, and show the resolved item name in the preview.
- Confidence: Confirmed by reading the code path.

### MASTER-7 [P2] A database blip during a counting-tablet sign-in wipes the tablet's setup

## GAPs
1. **Item categories cannot be added, renamed or removed.** The only way to get categories is "⚡ Load Default Categories" (6 fixed names), yet the banner says "Rename them or add your own afterwards" (Items.js:904). Settings' category card edits RECIPE categories, not item ones. A cafe cannot make "Bar store" or "Cold room" sections, and Stock Count assignment (who counts what) is per item category.
2. **No Excel import for Item Master or Vendors.** A new client types 150–300 items and every supplier one at a time. Recipes and Sales have importers; the setup guide asks for the item book first.
3. **Suppliers: no duplicate warning, no PAN check.** Two "Bhat Bhateni" rows split one supplier's payables and balance letter. A mistyped PAN (not 9 digits) splits the 1-lakh report's per-PAN totals (D12). Nothing warns at Add Vendor. (vendor-payables.md lists the missing unique index as still open, S708.)
4. **A shared counting tablet never signs anyone out and signs out to the wrong door.** There is no idle lock for count PINs, so the next person counts under the previous counter's name (`counted_by`, and recount protection keyed on it). "Sign out" lands on the email `/login` page, not `/ims/count`, so the next counter is lost.
5. **"Hide" an item has no confirm and no stock check.** One click removes the item's stock value from valuation and the Monthly Summary (HIDE_INSTEAD says "hide it once its stock is down to zero", but only the delete refusal says so, not the Hide button).

## Owner questions
1. **Who may make someone an IMS Manager?** HR and POS say only the Owner. (a) Same rule for IMS: an IMS manager can add Staff and Supervisors only (recommended); (b) keep letting IMS managers create other managers.
2. **A second supplier with the same name or PAN:** (a) warn at Add/Edit and let them save (recommended, since some suppliers legitimately share a PAN); (b) refuse the save; (c) leave as is.
3. **Counting tablet left signed in:** (a) sign the counter out after 10 idle minutes and return to the PIN screen (recommended, the same as POS tills); (b) only send Sign out back to the PIN screen; (c) leave as is.
4. **HQ push finds a branch item with the same name in a different unit (MASTER-2):** (a) skip it and list it in the preview for the Owner to fix by hand (recommended); (b) push anyway (today's behaviour, which re-reads the branch's history).
