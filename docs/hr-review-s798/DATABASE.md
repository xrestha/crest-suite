### DATABASE-1 [P1] After an Archive and a Restore, every staff login is cut off from its employee record: Crest Staff stops for everyone, a leaver settled afterwards keeps their till PIN, and some HR staff can approve their own leave, overtime and claims
- Where: `supabase/functions/admin-user-ops/index.ts:238` and `:253` (deleteClientDataFor deletes hr_final_settlements and hr_employees as the service role while Archive keeps every login); `:1081-1180` (restore_staff_accounts writes hr_employee_id only on accounts it creates, `:1170-1172`); `src/pages/adminClients/ClientDrawer.js:907` (Archive) and `:776-783` (Restore counts only `pos_email` logins, and otherwise leaves logins untouched); `exportClientData.js:150-153` (the profiles roster carries hr_employee_id but not settlement_blocked_by); live FKs `profiles_hr_employee_id_fkey` and `profiles_settlement_blocked_by_fkey`, both ON DELETE SET NULL.
- What happens: a cafe with 12 staff closes for the monsoon. The operator uses Archive, which the card calls "the recommended way" and promises that "restoring the backup fully reverses it" (ClientDrawer.js:2030-2032). Deleting hr_employees sets `profiles.hr_employee_id` to NULL on every linked login (Crest Staff, HR staff, till PINs, count PINs), and deleting the settlements clears `settlement_blocked_by`. Three months later the backup is restored. The employees come back with their old ids, but the Restore says "Existing staff logins were left untouched." and nothing puts the links back. From then on:
  1. Crest Staff refuses every sign-in, and Employees shows nobody as enabled. Enable creates a second login with a new PIN, and the dead one stays in the Staff-app picker under the same name.
  2. When a waiter leaves after the restore, Final Settlement blocks logins by `p.hr_employee_id = e.id`, finds none, and reports an empty blocked list. Their till PIN, count PIN and HR login keep working, against the settled rule that a leaver's logins are blocked at settlement.
  3. The own-record rules (own leave, overtime, TADA, advances, own settlement) now match only by the second arm of `hr_is_own_employee`: the employee record's email equals the login's email. An HR supervisor or manager whose employee record has a blank or different email can approve their own leave or overtime (20 hours of own OT is about NPR 4,300 at 1.5x on a 30,000 basic), approve their own travel claim, and an HR manager can issue or write off their own advance.
  4. Roster-publish and swap notifications reach nobody, because hr-push finds recipients by hr_employee_id.
  5. A leaver blocked before the Archive stays banned, but if rehired, reopening their settlement cannot lift the ban: it unbans `WHERE settlement_blocked_by = s.id`, and that link is gone. This deepens PEOPLE-ACCESS-4.

  No staff page can repair the link: hr_employee_id is written only when a login is created, and `guard_profiles_privileged_columns` stops the browser writing it (only the operator could, over REST, and no UI does). For an HR-only or IMS-only client with no till logins, the `pos_email`-only count reads zero, so the Restore tries to recreate every Self-Service and count-PIN login. Each fails with "already registered", and the result tells the operator to recreate by hand accounts that still exist, which is the S654 failure the comment above that code warns about. Delete-then-Restore has the leaver half too (judge addition): the backup has no settlement_blocked_by and restore_staff_accounts has no ban step, so a settled leaver's till or count PIN is recreated working from their vaulted PIN, and ims-staff-login's picker filter (`settlement_blocked_by IS NULL`, `:99-101`) puts them back on the counting tablet.
- Evidence: live confdeltype `n` on both profiles FKs. Live triggers on hr_employees and profiles: audit, guard_delete, revoke_self_service_sessions, guard_profiles_privileged_columns, client_move; none re-links. Consumers of the link: live `hr_self_service_assert_active` (raises on `e.id IS NULL`); hr-selfservice-login/index.ts:114-118; live `get_hr_self_service_status` (`hr_employee_id IS NOT NULL`); live `hr_is_own_employee` (profile link OR employee email = JWT email), used by the leave-decision, OT, advance and TADA guards and finalize/reopen settlement; live finalize_final_settlement:185-192; live reopen_final_settlement:44-46; hr-push/index.ts:96, 126, 151, 180. restore_staff_accounts calls `createUser` with no ban (`:1135-1140`), and finalize_final_settlement does not touch staff_pin_vault. The other admin-user-ops writes of hr_employee_id (1047, 1242, 1614, 1686, 1892) are all create actions.
- Status: NEW. Missed by S574, which made Archive "fully reversible including logins and PINs" (data-export.md:24), and by S748/S753, which keyed the own-record rules, the settlement login block and the Staff-app gate on profiles.hr_employee_id.
- Fix: add an admin-only, service-role admin-user-ops action, for example `relink_staff_accounts(client_id, roster)`, and have the Restore call it after restoreClientData whether or not logins exist. For each roster profile that still exists in this client with hr_employee_id NULL, set it to the roster value when that employee exists in the client, skipping any clash with the partial unique indexes on profiles.hr_employee_id. Add settlement_blocked_by to the export's profiles select and relink it only when the restored settlement is still finalized; when restore_staff_accounts recreates a login whose settlement is finalized, re-apply the ban. Change the existing-logins test to count any staff login (pos_email, hr_self_service_email, ims_email, hr_role or ims_role), or have restore_staff_accounts skip roster ids that already exist. Until this ships, the Archive card and data-export.md should say that staff logins need re-linking after a restore.
- Confidence: confirmed by reading and the live catalog (FK delete actions, trigger lists, function bodies). The Archive-then-Restore sequence was not run end to end.
- Verified: verifier confirmed with corrections (the own-record gap reaches only staff whose employee email is blank or different; relink settlement_blocked_by only while the settlement is finalized). Judge confirmed: re-read the live FKs, triggers, hr_is_own_employee and the finalize/reopen bodies, found no re-link path, and added the Delete-then-Restore leaver case.

### DATABASE-2 [P2] Restoring a backup drops the client's whole leave history when one pending or approved leave falls entirely on public holidays, so leave balances return to the full quota
- Where: live `hr_leave_requests_validate` (its all-holidays refusal has no operator seam), body as in `supabase/migrations/20260914180000_hr_leave_public_holidays_swap_guards.sql:1139-1185`; the S749 recount at `:1190-1208` kept such requests on file at 0 days; `src/modules/admin/dataExport/restoreClientData.js:47-51` (hr_holiday_calendar restores before hr_leave_requests) and `:254-270` (the first failing 500-row chunk abandons the rest of the table).
- What happens: a waiter's one-day annual leave on 10 Ashwin is approved in Bhadra. The government later declares 10 Ashwin a public holiday and the HR manager adds it to the Holiday Calendar, which leaves the approved request unchanged. The same trap is set by any full-day request the S749 recount stored at 0 days, and by a half-day on a date later made a holiday. Months later the client is archived, or deleted by mistake, and restored. The holidays restore first; the trigger recounts that request, finds no working day, and raises `leave_all_holidays` even for the operator. The restore skips the rest of the table from that chunk on: for a cafe with fewer than 500 leave requests, every request. The operator sees "Skipped: hr_leave_requests (leave_all_holidays ...)" and nothing in the app brings them back. Unless someone re-enters them, this BS year's balances read the full quota, and a cook who took 8 days of annual leave this year and then leaves is encashed those 8 days again at settlement: about NPR 4,600 on a 15,000 basic.
- Evidence: live body `IF NEW.status IN ('pending','approved') THEN v_holidays := hr_public_holiday_count(...); IF v_holidays >= v_calendar THEN RAISE EXCEPTION 'leave_all_holidays ...'`; the only operator exemption is on the overlap test. Live `hr_public_holiday_count` passes for admin, so it counts the restored holidays. The live `hr_leave_requests_guard_decision` and every other HR guard (payslips, settlements, bonus rows, repayments, salary payments, TADA) exempt the operator on INSERT. The restore inserts under the admin's JWT (`restoreClientData.js:256`) and `break`s on the first error (`:269-270`). Nothing that writes hr_holiday_calendar touches existing requests.
- Status: NEW. Missed by S749, which added the check without the operator seam the other HR guards carry. The S707 restore-hazard lesson (a rule a stored row can fail) in trigger form.
- Fix: in `hr_leave_requests_validate`, when `TG_OP = 'INSERT' AND COALESCE(is_admin(), false)`, skip only the all-holidays RAISE and store 0 days (`GREATEST(0, v_calendar - v_holidays)`, 0 for a half day on a holiday), keeping the recount and the date-shape checks. Do not key the seam on `current_user`: `submit_my_leave_request` is SECURITY DEFINER and inserts `days = 0`, so a `current_user NOT IN ('anon','authenticated')` seam that keeps stored days would store 0 days on every Crest Staff leave request. The one side effect is that the operator entering an all-holiday leave from Leave Management gets a 0-day row instead of a refusal, which charges nothing. Verify with a rolled-back probe that inserts an approved all-holiday request as admin. Migration needed.
- Confidence: confirmed by reading the live trigger body and the restore loop. Whether live data already holds such a request was not checked (business tables are off limits).
- Verified: verifier confirmed with corrections, applied above (the original current_user fix would have zeroed every Crest Staff leave request; the "silently recounts every other request" half is dropped, see below; re-encashment needs the lost leave to fall in the settlement's BS year). Judge confirmed against the live body.

## Dropped in verification
- Restore silently recounts every other leave request's days against the restored calendar (the second half of DATABASE-2 as reported): refuted. Recounting approved requests against the current calendar is what the S749 migration did to every stored approved request, and it follows the settled rule that public holidays inside a leave are not charged. The trigger comment "a decided one keeps the figure it was decided on" means rejected and cancelled rows, not approved ones.
- DATABASE-2's first fix sketch (a `current_user NOT IN ('anon','authenticated')` seam that keeps the stored days): withdrawn, because `submit_my_leave_request` is SECURITY DEFINER and inserts `days = 0`, so it would store 0 days on every Crest Staff leave request. Do not re-propose it.

Seen and not raised, so the next review need not find them again:
- MAINTAIN is still granted to anon and authenticated on 21 of the 22 hr_* tables (hr_salary_payments is clean), staff_pin_vault still has anon=Dxtm, and pg_default_acl for postgres still gives every new table anon/authenticated Dxtm. None of it can be issued through PostgREST; it is the known-open S782 item.
- RI cascade actions run as the referencing table's owner, so every `current_user NOT IN ('anon','authenticated')` seam lets cascaded rows through. Today's delete pre-checks cover every cascade that could erase finalized pay, but the comment in `hr_pay_month_guard` reasons as if the cascade ran as the caller. A new guard must not rely on that seam to stop a cascade.
- `get_hr_role_eligible_users` uses a bare IF on its authorisation test, but a NULL there returns nothing, so it fails closed.
- hr_salary_payments has no unique key, but `record_salary_payments` takes `hr_pay_lock` plus FOR UPDATE and recomputes what is still due, so a double click cannot double-record.
- hr_tada_claim_items and hr_roster are unaudited by decision (items lock once decided and the header total is audited; roster was excluded in S749).
- The anon picker `get_hr_self_service_staff` returns profile id and name for a client uuid: the S464 design.
- Month rename (Periods.js) is Owner-only in the database, and the UI limits it to open periods.
- The export adds `custodian_user_id_name` to assets_register rows, and `prepareRow` strips only `*_by_name` keys, so a set custodian would fail the whole assets_register table on restore. It is latent (nothing in src/ or supabase/functions writes custodian_user_id) and belongs to IMS.
