### ROSTER-1 [P1] Editing a shift type's Hours or Normal hrs changes every earlier day of the month not yet generated, so month-end Generate from Roster pays those days at the new length and overtime

- What happens: "Full Day" is 10:00-22:00, Hours 12, Normal hrs 9, so 3h overtime a day. On Kartik 15 the owner shortens it for winter: End 21:00 and Hours 11 (or clears Hours so it recalculates). Most clients generate attendance from the roster at month end (S693). Generate reads the type as it is now and writes 11h with 2h OT for every Full Day in Kartik, including Kartik 1-14, when staff really worked 12h. A full-day worker on NPR 20,000 basic loses about 1h × 14 days × NPR 83 × 1.5 = NPR 1,750, and the payroll run finalizes it. Lengthening a shift for Dashain overpays in the same way. The sharpest case is filling in Normal hrs for the first time mid-month, which adds overtime to every earlier day not yet generated. Renaming a zero-hour type (LEAVE to "Paid Leave") turns earlier unpaid-leave days into paid leave. The past-day "as rostered" cost and the labour standard's roster hours move backwards too. The panel never says the type is in use. A smaller trap sits beside this: the editor preloads the stored Hours (`:259`), so changing only the times moves nothing, and the panel then shows 10:00-21:00 beside 12h.
- Evidence: saveEdit updates name, start, end, hours and regular_hours by id with no read of hr_roster, while deleteShift refuses an in-use type for this exact reason ("Generate from Roster would then mark them Off", `:99`). The Normal hrs Tip (`:167`) promises "every Full Day carries 3 hours of overtime — Generate from Roster fills it in". Generate's confirm counts the days it will write but says nothing about a type that changed.
- Status: missed by S749 (it guarded deleting an in-use type, not editing one) and S742 ("saved attendance does not recompute", but attendance not yet generated does).
- Fix: when an edit changes Hours, Normal hrs, or the name of a zero-hour type, count the roster days on or before today that use it and have no attendance row yet. A simpler interim is to refuse the edit on that count alone and say "add a new shift type and untick this one". Do not refuse on future days or on days already generated, or harmless edits get blocked. When the times change and Hours equalled the old calculated length, recalculate Hours. Snapshotting hours and regular_hours onto each hr_roster row is the heavier alternative, and that one needs a migration.
- Confidence: confirmed by reading and the live trigger list.
- Verified: verifier confirmed with corrections (a times-only edit moves nothing because the stored Hours is preloaded; the example now changes Hours as well; the interim refusal counts only past days not yet generated); judge re-read the edit path, attendanceFromRoster, shiftHours and Generate and found no guard on edit in the page or the database.
