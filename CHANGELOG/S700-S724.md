### S716 — 2026-09-09 — Overheads re-analysed: a save that could empty the period and say "✓ Saved", and four buckets of zero painted green

**No migration, no Edge Function deploy.** `CACHE_NAME` and `APP_VERSION` both bumped to
`crest-v252`.

A re-analysis of `Overheads.js` — the page an owner types their rent, wages and licence fees into,
and the one that answers "am I making money this month". Six findings, all shipped. The page is the
data-entry surface for a figure five other surfaces read (`ClientDashboard`'s `overheadTotal`, the
Owner Dashboard, the Monthly Owner Report, Recipes' True Cost allocation and `get_group_pnl`), so
its failures propagate rather than staying local.

**`save()` discarded both of its write errors, and could empty the period while saying "✓ Saved".**
It is a replace-the-period save — `scopedDelete` then `scopedInsert` — and neither call destructured
`error`. supabase-js **resolves** with `{ error }` rather than throwing, so a bare `await` throws the
only evidence away and the code below proceeds as if it worked. Both directions were live. Delete
fails and insert lands: the period holds both versions and every consumer that sums it
double-counts. Delete lands and insert fails: the period is **empty** — and `loadOverheads()` then
found nothing, fell into the carry-forward branch, and seeded the *previous month's* figures as an
editable draft. So the owner was shown plausible numbers under a success tick, over data that no
longer existed. Both halves are now checked; the delete goes first so its failure is a clean no-op
that can say so; the insert failure names the state the record is in ("cleared but not saved,
everything you entered is still on screen, press Save again, do not reload") per S619, and
**deliberately skips the reload** — after a failed insert the rows in state are the only surviving
copy of what the user typed, and reloading would replace them with a carry-forward draft.

The irony worth recording: `loadOverheads()` has carried a three-line comment about exactly this
class since S612 — *"on a data-entry page the silent-zero class is a data-loss class"* — while the
write path ninety lines below it had no guard at all. And S658, the session whose own subject line
was *"a failed write stops reading as a no-op"*, edited **line 242 of this function** to reword its
`alert()` and walked past 244 and 257.

**`.neq('source', 'pos_comp')` shortened revenue, which is this page's denominator for
everything.** `sales_entries.source` is nullable (`DEFAULT 'manual'`, no `NOT NULL`) and in SQL
`NULL <> 'pos_comp'` is NULL, so the server-side form silently dropped every legacy manual row.
`salesReads.test.js` deferred the remaining ~13 files on the grounds that each is display-only and
"needs its own answer to what its figure is supposed to mean". Overheads' answer is that it is not
display-only: revenue is the denominator of every percentage on the page while the numerator (food
cost, from purchases) stayed whole, so **every error ran one way** — Food Cost % and every "% of
revenue" read high, break-even read high, Net Profit read low, and Net Profit's sign is what picks
between a green "✓ Profitable this period" and a red "✗ Operating at a loss this period". Filtered
in JS over a selected `source` column, and added to the test's `FILES` so it cannot come back.

**An empty bucket was painted green as if it had beaten its target.** `trafficLight(0, 30)` returns
green — `0 − 30 ≤ 2` — so an untouched Labor tab rendered `NPR 0 · 0.0%` comfortably inside a 30%
target, the most flattering possible rendering of "we do not know what this costs". Same for Tax &
Fees (target 5) and Overhead (25). `seedBucket()` writes blank preset rows into every new period, so
the page manufactured its own examples, exactly as Menu Pricing's *+ Add Item* did at S713. The
absence is now carried as `null` from where it is computed to the cell — `pct()` returns null for a
null amount, an un-entered line renders "not entered" and "—" with a muted empty bar, the KPI cards
say "Not entered yet" instead of NPR 0, and a caveat above the Net Profit callout names every
missing line, because a statement that omits a cost overstates profit by exactly that much.

**Net Profit ignored Crest HR payroll entirely.** The page had no `clientModules`, no `hrEnabled`
and zero references to payroll — so an HR client who runs payroll properly and leaves the Labor tab
blank had a Net Profit overstated by their whole wage bill, in green. This is S526 seen from the
other side: that one double-counted labour, this one omitted it. Labour is now payroll **XOR** the
Overheads bucket, never the sum, using `ConsolidatedPnl`'s definition (gross + employer SSF, which
`get_group_summary` also uses) so the three cannot disagree; a finalized run whose payslips cannot
be read **refuses** rather than falling through to the bucket, which would quietly substitute a
different labour source for the one the page says it used. The ignored bucket is **named on screen
with its amount** rather than silently dropped, and the ranked pivot swaps the typed labour rows for
a single "Payroll" line so its own TOTAL still ties out to the 100% it prints underneath.

**"Covers" meant dishes here and bills everywhere else.** `covers` was `Σ qty_sold` — portions sold.
But `pos_orders.covers` is a real and different column, there is a whole Covers Report, the Demand
Forecast counts `o.covers || 1` per bill, and Help states plainly that *covers are counted from POS
bills and manual Sales Entries carry none*. At three dishes a guest, "Actual Covers" read three
times the real count and every per-cover figure was a third of the truth. Renamed throughout to
Dishes rather than switched to POS covers: this page reads `sales_entries`, so covers genuinely are
not available to it for an IMS-only client, and Recipes' True Cost allocation divides by the same
figure. The number was always honest; the label was not.

**The one disclosure sat on one card of four.** The "Purchase-based FC%" tip lived only in the P&L
Summary header, while the Cost Visualisation stack labelled the same figure "Food Cost" unqualified
and the break-even footnote printed a bare "FC%". A report that states a scope must state it
everywhere the report goes. Both now carry it, and the footer gained a plain-language note on all
three of the page's conventions — purchase-based food cost (and that it ignores opening and closing
stock, so a stock-build month reads worse than it was), dishes-not-guests, and payroll-XOR-bucket.

875 tests pass (10 new via the two `salesReads` cases on Overheads), build clean with no ESLint
warnings, `check-rules-globs` OK across 168 globs.

### S715 — 2026-09-09 — Menu Engineering re-analysed: a Star that meant "we never costed this", and a write-back that never once ran

**No migration, no Edge Function deploy.** `CACHE_NAME` and `APP_VERSION` both bumped to
`crest-v251`. `monthly_owner_reports` schema version 4 → 5.

A re-analysis of the whole Menu Engineering surface — the page, the frozen Monthly Owner Report
section that must agree with it, and the POS suggestion engine that reads what it writes. Some of
what the rules files claim was holding: the S682 `useLatestRequest` guard is on the page, the S714
NULL-safe `is_active`/`category` filters are on the recipes read, and `Q_HEX` is the one private
chart palette the S605 audit explicitly sanctioned. Eight things were not.

**Two of them had never worked at all, in opposite directions.**

**The `me_class` write-back has never sent a single request.** The line was
`scopedUpdate('recipes', { me_class: … }).eq('id', r.id)` inside a `forEach` — no `await`, no
`.then()`. postgrest-js issues the request **inside `then()`** (`PostgrestBuilder.then` is where the
`fetch` lives), so an un-awaited builder is an object that gets constructed and dropped. It has been
that way since the line was written in `e8e3d18` (S210). So `recipes.me_class` has been NULL for
every client, for every dish, always — and POS's Pro-tier Menu-Engineering suggestion ranking, which
`pricingPlans.js` sells and `PosOrders.jsx` reads on every menu load, has never had data to rank on.
Nothing failed and nothing logged. The tell in hindsight is S470's migration, which backfilled
`'plowhouse'` → `'plowhorse'` on that column and can only ever have matched zero rows.

**A failed cost read hung the page forever.** S711 gave `computeRecipeCosts` a `throwFirstError` and
recorded that "the callers that already catch it need no change". Four did not catch it at all —
Menu Engineering, Recipe Margin, Menu Repricing and Best Sellers — so a dead `items` read rejected
the loader's promise *before* `setLoading(false)`, and the page sat on "Loading…" indefinitely with
no error card and nothing to retry. All four wrapped. When you make a shared helper throw, "existing
callers already catch it" is a grep, not an assumption, and the symptom of getting it wrong is a
hang, which no error branch will ever report.

**A dish nobody had costed was the best thing on the menu.** `fcPct` was
`sellingPrice > 0 ? cost / price * 100 : 0` — and `0 / 400` is also a real `0`. So "we have not
priced this" and "we have not costed this" both reached `classify()` as **0% food cost**, cleared
the ≤35% cutoff, and came back **Star** or **Plowhorse**, printed as *"Keep on menu. Feature
prominently."* beside a green `0.0% ✓`. This is the S713 rule one level up: there a zero numerator
mis-coloured a cell, here it manufactures a verdict — and `Recipes.js`'s own **+ New Recipe** writes
a recipe with no ingredients, so the page produced its own Stars. Aashish took the recommended
option: `menuFcPct()` returns `null`, `classify()` returns `null` rather than guessing, and those
dishes appear in a fifth **Not rated** group — a summary card, a filter, a full-width panel under
the 2×2 matrix, a Category Breakdown column that only exists when it has something in it, and a
scatter footnote saying how many dots are not on the chart. The row's advice column carries the
reason, because the reason *is* the next step: "No selling price set" / "No costed ingredients".

**A dish that sold nothing could be a Star.** `highPop` was `qtySold >= median`, and the median
spans every active recipe including the unsold ones — so on a menu where under half the dishes sold
in the period, the median is **0**, `0 >= 0` holds for everything, and Plowhorse and Dog become
mathematically unreachable for that whole month. `qtySold > 0` is now required. The in-app guide had
promised the opposite ("never counts as high popularity **by definition**") since it was written;
that sentence is true now, and the guide says which release made it true rather than quietly
correcting itself.

The median deliberately still spans every recipe, rated or not, sold or not. Narrowing it would
re-classify large parts of a menu at once and pull new snapshots away from the historical ones for a
reason nobody asked for. Only zero-sale dishes moved.

**The classification is one function now, not two copies of one.** `MenuEngineering.js` and
`computeMenuEngineeringSection.js` each held their own `FC_CUTOFF`, `median()` and `classify()`,
with a comment on both saying they were mirrored "verbatim" and must never diverge — and this is the
worst file in the product to make that bet in, because the owner report's section is **frozen**: a
quadrant snapshotted wrong stays wrong, and nothing in the artifact says which of the two definitions
produced it. `src/shared/menuEngineering.js` is the one definition, imported by both, with
`menuEngineering.test.js` pinning each of the decisions above. Same move as `imsFormulas.js`,
`operatingBands.js` and `staffLevelBadge.js`.

**`sales_entries` was read bare, with no paging.** One row per recipe per day per source, so a single
month of POS service is thousands of rows and PostgREST returned the first 1000 with no error and
nothing in the data to say so. Best Sellers and the frozen owner report have both paged this same
read for a while; this page was the one left bare. The damage is not a short revenue column — a
truncated qty map moves the **median**, which is the popularity cutoff, so every dish on the page
can change quadrant.

That is also why this page came off `ims-figures.md`'s "still open, deliberately" list for the S699
`.neq('source', …)` trap. "Display-only" was doing too much work in that sentence: this figure sets
a threshold *and* gets written back to a column another module acts on. `source` is selected and
comps filtered in JS now, and `salesReads.test.js` covers this file alongside `Sales.js`.

**Four confident zeros sat above the error card.** The quadrant summary cards and the filter bar's
"N items · Revenue: NPR X · Qty: Y" line were rendered forty lines *above* the
`loading ? … : loadError ? …` ternary — the exact S616 shape, on a page whose zero state reads as
good news: `Star 0 · Plowhorse 0 · Puzzle 0 · Dog 0` over "Could not load this report", and the same
four zeros on every ordinary load before the data arrived. Both are inside the guard now. The cards
also became real `<button>`s with `aria-pressed` (they were click-only `<div>`s), laid out
`flex-start` so a stretched grid row does not sink their labels.

**Revenue was priced at today's menu price.** `sellingPrice × qty − discount`, for any period —
so a past month silently restated itself the moment anyone edited a price. It now uses the row's own
`unit_price` snapshot with the current price as a fallback for rows written before that column
existed, which is `Sales.js`'s `recipeRevenue()` verbatim and the basis Best Sellers records having
fixed for exactly this reason. Built in one pass over the sales array rather than a `.filter()` per
dish.

**Smaller, from the same pass.** The scatter chart's Y domain was pinned `[0, 100]`, so a dish
costing more than it sells for — a state `Recipes.js` warns about at save time — plotted below the
floor and off the chart; the domain follows the data now. `PeriodScope` was missing (both its
folder-mates have it) and the header printed a median it had not computed yet; the chip carries the
period and its open/closed status, and the thresholds stay in the already-gated legend.
`loadPeriods` now claims through `useLatestRequest` too, per that hook's own contract — it
auto-selects a period, so an admin switching clients could otherwise leave one outlet's month
labelling another outlet's figures. It needed its **own** guard rather than the page's existing
one, and that was very nearly shipped wrong: both effects fire on a client switch, in declaration
order, so on a shared `useLatestRequest` the period LOAD's claim — still carrying the previous
client's period id — supersedes the period LIST's, and the new outlet's dropdown never gets set at
all. That is exactly the failure `frontend-performance.md` records from Roster's two loaders ("a
shared one would have them cancelling each other"); adding a guard to a page that already has one
is not the same change as adding the first.

**What the write-back looks like now.** One request per distinct class rather than one per recipe
(a 300-dish menu was 300 concurrent PATCHes on every period change), chunked because the id list
rides in the URL, unrated dishes written back as `NULL` so a dish that loses its price stops
carrying a stale verdict into the till — and **only from the current period** (the open one, else
the latest). Browsing last Shrawan out of curiosity must not re-label what the till suggests
tonight; `computeMenuEngineeringSection.js` had refused to port this write for precisely that
reason while the live page it mirrors did it on every period change. Its failure is surfaced
non-blockingly below the report, named as the consequence — the quadrants on screen are correct,
what could not be updated is the copy POS reads.

`CURRENT_SCHEMA_VERSION` went 4 → 5: `quadrantCounts` gains an `Unrated` key and `items[].quadrant`
can be null, and a v4 matrix and a v5 matrix are not computed the same way. Both consumers guard on
the new key, because a pre-v5 snapshot does not have it and an absent count must not render as a
real 0. The Excel sheet writes "Not rated" rather than a blank cell that reads as an export fault.

**Docs.** The un-awaited-builder trap went into `CLAUDE.md` rather than a rules file — it is not
IMS-scoped, and it belongs beside the two siblings already there (`try/catch` catches nothing, a
bare `.select()` truncates), all three being supabase-js call shapes that fail by doing nothing.
That leaves the root file **200 chars under its 53,000 ceiling**, so the next session that wants to
add a line there cannot; it is due a `/doctor` pass. `.claude/rules/ims-figures.md` took the page's
own rules and dropped Menu Engineering from the S699 "still open, deliberately" list, with the
reason it was ever on it — "display-only" was doing too much work for a figure that sets a
threshold and gets written back to a column another module acts on. Two rows filed in
`docs/CROSS-REPO.md` for hss-suite (the builder trap; and "making a shared helper throw does not
make its callers catch", whose failure mode is a hang no error branch reports). `POS_DECISIONS.md`
gained an amendment rather than a correction: S713's argument for *not* building manual pairing on
the IMS branch rests on Pro clients already having the ME ranking — which had never once run, so
the decision was right for a reason that was not yet true. Six memory claims were wrong and are
fixed: four still carried the pre-S470 `'plowhouse'` spelling, and two recorded the write-back as
shipped in S210.

Verified: `npm run build:verify` clean (exit status read from the process, not through a pipe), 863
tests across 75 suites green including 11 new ones, `npm run check:docs` OK.

### S714 — 2026-09-09 — Sub-recipes re-analysed: the private read that made a shrinkage report lie, and a refusal nobody could read

**No migration, no Edge Function deploy.** `CACHE_NAME` and `APP_VERSION` both bumped to
`crest-v250`.

A re-analysis of the whole sub-recipe subsystem — the two cost walks, the mirror-item lifecycle,
every consumer of `is_sub_recipe` and `sub_recipe_id`. The invariants the rules file claims were all
holding: no third private cost walk (`grep subCostPerUnit` is clean post-S713), the path-set guard
intact, the S711 paging in place on both shared engines, 39 tests green. Nine things were not, and
one more surfaced while fixing them.

**Theoretical Variance read the client's entire recipe book through a bare `.in()`.** The one whole-
book `recipe_ingredients` read the S711 sweep never reached, because this page reimplements the
recursion locally (`expandIngredients`) — the same sentence S713 had to write about the cost walk,
about the read this time. Past PostgREST's 1000-row cap the dishes below the cut expand to nothing,
theoretical usage comes out LOW, and **low theoretical does not read as missing data — it reads as
over-consumption**, on the one report a client uses to chase shrinkage against their own staff. Now
`fetchAllRowsChunked` with `.order('id')`, and the per-recipe `.filter()` join beside it replaced
with a single grouping pass, since the read is now genuinely unbounded.

**Menu Pricing still costed a sub-recipe at zero, one layer below the walk S713 replaced.** The
shared walk landed; the LIST it resolves against was still seeded `.eq('category','Sub-Recipe')`, so
a recipe reached through `sub_recipe_id` whose own category had been changed away fell through
`subCost[id] || 0` — the same under-statement, on the same page, in the same direction, surviving
the fix that existed to end it. What a `sub_recipe_id` names is decided by what points at it, never
by how it is categorised.

**And the write that manufactures that state refused nothing.** `deleteRecipe` blocks while other
recipes reference the row; changing the *category* away from Sub-Recipe — same recipe, same screen,
a dropdown instead of a button — deactivated the mirror, nulled `linked_item_id` and left every
parent pointing at it. Nothing broke loudly, which is why it survived: the cost engines ignore
category, so Recipe Costing stayed right while the parents' ingredient picker rendered blank and
Menu Pricing costed the row at nothing. It refuses now, naming the recipes that hold it. The cycle
guard was gated on the same condition (`category === 'Sub-Recipe'`) and now runs for any existing
recipe — what makes a cycle possible is being *referenced*, which is independent of categorisation.
Both readers stay tolerant of rows written before the guard.

**`.neq('category','Sub-Recipe')` on a nullable column, ten times.** `recipes.category` is nullable
with no default, and a server-side `.neq` drops NULL rows as well as the named one — so an
uncategorised dish was missing from Sales Entry, **unorderable on the POS till**, and absent from
Best Sellers, Recipe Margin, Menu Engineering, Combo Builder, HSC assignment, the Dashboard's recipe
count, the guest-menu readiness counts, and permanently from the frozen Monthly Owner Report's menu
matrix. `.neq('is_active', false)` on two of those is the same shape. The decisive evidence was on
the server: every guest-menu function has always filtered `category IS DISTINCT FROM 'Sub-Recipe'`,
which is NULL-safe — so `AdminGuestMenu.jsx` was claiming to count "exactly the rows get_guest_menu
serves" while measuring a different population. MenuPricing and MenuRepricing carried the fix and
the comment since S683; it did not travel.

**The bulk importer had none of `save()`'s guards.** Two sheet lines naming one item fail with
`21000` after the recipe row is committed, leaving an ingredient-less recipe that costs 0 — which
`fcBand` renders as `0.0% ✓` in green (S713's rule, reached by a different road). Two lines naming
one sub-recipe fail at nothing and silently double the cost. Duplicates are refused in the preview
now, per recipe rather than per line, and a failed ingredient insert deletes the recipe row it just
created — the two writes cannot be reordered, so a compensating delete is the only way to leave the
sheet re-importable.

**Raising one depth cap and not its twin put the S602 silence straight back.** `explodeRecipeTree`
has two limits: the fetch loop's `MAX_DEPTH_ROUNDS`, raised 5 → 12 with a loud `console.error`, and
`explode()`'s own `depth > 10`, which stayed. That is the worst available disagreement — the loop
resolves levels the recursion then refuses to walk, so the frontier comes back empty, the loud error
cannot fire, and the deepest levels vanish silently. Tied to one constant now, reported once per
walk, with an eleven-deep fixture verified to fail against the old number.

**`subRecipeUsage.js`'s `fetchItemMap` was the last raw `.in()` on the walk** — every raw item under
every sold dish plus every sub-recipe's own ingredients, valuing and NAMING at once. A missing rate
is a zero in the reconciliation figure; a missing name drops the ingredient out of the search index,
so find-an-ingredient stops matching and reports nothing rather than reporting a failure.

**Then: every hand-written refusal in `Recipes.js`'s save was reaching the user as "that didn't
work".** Found while wiring the convert-away message, which would have been swallowed the same way.
`errorInfo` recognises Postgres *shapes*; an English sentence matches no rule and returns the
FALLBACK with the real text demoted to fine print — so the duplicate Product Code, both halves of
S707's mirror name clash and S711's "saved, but the previous ingredient list could not be removed"
all arrived as a generic apology. `ActionError` already draws this line (a plain string passes
through untouched); a throw/catch needs it drawn explicitly. A tagged `SaveRefusal` carries copy we
wrote; raw errors are rethrown as objects so their `code` survives into the detail line.

The remaining two were smaller: the sub-recipe picker offered hidden sub-recipes unlabelled while
`itemOptions` beside it labels hidden items, and rendered blank for a row already on the recipe
whose target had been converted away.

**One finding was documented rather than fixed, deliberately.** A mirror item's `items.rate` is
written only by a recipe save, while `PurchaseBillPage` rewrites every raw ingredient's rate on
every bill — so a sub-recipe's WIP valuation in Stock Count (which counts mirrors on purpose), its
closing stock and therefore COGS all ride on a cost frozen at the last save, while every other
sub-recipe figure recomputes live. The snapshot is defensible on the same document-versus-report
reasoning as `requisition_lines.rate`; what is not settled is that it happens by omission, with no
recost action and nothing on Stock Count saying a prep item's rate is older than its ingredients.
That is a product decision about what a WIP valuation means, not a bug fix.

### S713 — 2026-09-09 — Menu Pricing: the last private copy of the sub-recipe walk, and a food cost of zero wearing a green tick

**No migration, no Edge Function deploy.** `CACHE_NAME` and `APP_VERSION` both bumped to
`crest-v249`.

A re-analysis of `/menu-pricing` turned up nine things. Two of them move a number the reader prices
a dish from, three are dropped write errors, and the rest are the residue you get when a page grows
two branches and only one of them keeps being maintained.

**The private copy of the sub-recipe cost walk was the last one in the repo, and it was the only one
still wrong.** `MenuPricing.js` had its own `subCostPerUnit()` with a cycle guard that only ever
added to `seen` and never deleted on the way out. That is the correct shape for "have I been here
before in this whole traversal" and the wrong one for "am I inside myself right now", and the
difference is invisible at one level of nesting and silently under-costs a diamond:
`Sauce → Roux → Stock` costs the Stock, and `Sauce → Stock` then returns 0 because Stock is already
"seen". `recipeCostCalc.js` fixed exactly this in its own copy and left a twenty-line comment
explaining it; every other consumer in `src/` — Recipes.js, the printed cost card, the recipe
importer, Stock Count's sub-recipe usage, the nutrition roll-up — imports that fixed helper. Menu
Pricing did not, so it under-stated food cost against **both** other engines, on the one page where
that number decides a price. The copy is gone; the page now stitches its separately-fetched
ingredients back onto the sub-recipes and calls `calcSubRecipeCostPerUnit` once per sub-recipe.

**A dish with no ingredients printed `0.0% ✓` in green, and this page's own + Add Item created
them.** `fcPct` was `exVat > 0 ? (cost / exVat) * 100 : 0`, and `fcBand(0)` bands as *Healthy* —
so an unrecipe'd item read as the best-performing dish on the menu and sorted to the top of an
ascending FC% sort. Two tells that this was never intended: the **New FC % sort already guarded
`r.cost > 0`** while the cells and the FC% sort did not, and `fcBand(null)` has always returned
`—` with no mark. `fcPct` is now null when there is nothing to divide, both cells render through
`fcFigure()` (the shared "colour + mark + band name together" helper this page had taken apart into
three wrappers of its own), and the dash carries a title saying what to add. The Excel column
exports blank rather than `0.0%`, because that sheet is sent out and priced against.

Worth stating as a general rule: **a rate computed from a zero numerator is not a rate, and a
banding function will happily band it.** The absence has to be carried as null all the way to the
cell, or the first `?:` that defaults it to 0 hands the band the most flattering possible answer.

**Three writes whose errors went nowhere.** `savePairings` was delete-every-row-then-insert with
*both* results discarded — so a refused insert after a successful delete wiped every pairing on the
item, while the modal closed on "Saved" and wrote the intended list into state. It is now a diff
(only what the user actually changed is touched), additions go first (the same insert-before-delete
order `Recipes.js` uses on ingredients, so a half-completed save leaves more than it takes), and
each error is read and surfaced. `togglePos` dropped its error entirely: the 86 toggle snapped back
to its stored value and said nothing, which reads as a missed click rather than "this is still
selling". `saveRow` reported `'Save failed'`, which is the whole S619 rule in two words — the row
keeps a short marker so it stays findable in a table of ~100, and the sentence plus the technical
detail go to a new page-level `ActionError`.

**None of the new messages claims the write did not land**, and one of them is the reason to care:
`recipes` has no unique index on `(client_id, name)` — unlike `items`, which got one in S707 — so a
response lost after the row was committed turns the retry a "the item was not added" sentence
invites into a duplicate menu item. The Add/Edit modal now says the item *may* not have been added
and to check the list first. `errorText.test.js` asserts the library never makes that claim; it
cannot see a call site prepending its own.

**`.neq('category', 'Sub-Recipe')` also dropped every recipe whose category is NULL.** The column is
nullable and a server-side `.neq` excludes NULLs silently, so such a recipe vanished from the one
page that sets its price with no error and nothing missing from any count. Now
`.or('category.is.null,category.neq.Sub-Recipe')`. `MenuRepricing.js` had the identical line and
the identical fix. Neither is reachable from `Recipes.js` (its category control is a bounded
`<select>`), so this is legacy and restored rows only — which is exactly the population nobody
checks.

**The IMS branch rendered 45 lines of Pair With modal that nothing could open.** `openSuggestModal`
is called only from the POS-only table, so the IMS copy was unreachable, and the
`recipe_suggestions` read that fed it ran on every load for every IMS client. `Help.js` already

### S711 — 2026-09-09 — Recipe Costing: the walk that quietly stopped at 1000 ingredients, and a delete that emptied the recipe it could not remove

Vendors, Purchase Orders and Requisitions. Recipe costing has three cost paths — `recipeCostCalc.js`

**The shared walk had no row cap and no chunking, so every figure derived from it could truncate
silently.** `explodeRecipeTree` read `recipe_ingredients` with a bare `.select().in('recipe_id', …)`

```sql
client_id = (SELECT client_id FROM profiles WHERE id = (select auth.uid()))     -- the file
client_id = (SELECT profiles.client_id FROM profiles WHERE profiles.id = ...)   -- pg_policies
```

Postgres parses the expression and re-prints it qualified, so **the source text in the repo and the
stored text in the catalog are two spellings of one thing**, and a grep tuned to either is blind to
the other. `20260909180000` fixes those thirteen. The rule that comes out of it is worth more than

the files are what you edit, the catalog is what is true. The standing check earned its place on its
first run by finding the incompleteness of the fix that introduced it.

(Generating the second migration turned up a third thing worth naming: the substitution regex ended
`\)?\s*\)`, and against the unqualified spelling the greedy optional swallowed the enclosing
clause's own closing paren, producing statements that would not parse. It was caught by asserting
that every emitted clause is paren-balanced and starts and ends with one — the extraction is
balanced-paren scanning now, not a regex. **A generated migration needs a check on its output, not
only on its input.**)

Two things make this worth a standing check rather than a one-off fix. It is **invisible until the
first group exists** — with `active_client_id` NULL the inline expression and the function are byte-identical,
so nothing today can exercise it — and it fails in the **quiet** direction: a switched outlet's
reads come back `{ data: [], error: null }`, an empty POS floor and an empty requisition list being
indistinguishable from a new outlet, while writes raise 42501 on a row the user watched themselves
type. Same shape as the three defects that sat in multi-outlet from S548 to S617: a feature with no
users accumulates faults every review passes over. The migration is a textual, semantics-preserving
substitution generated from each policy's current definition — nothing else moves, not the admin
clause, not the permissive/restrictive split, not the command set — and this must now stay empty:

```sql
SELECT tablename, policyname FROM pg_policies WHERE schemaname = 'public'
 AND (qual LIKE '%profiles.client_id%' OR with_check LIKE '%profiles.client_id%');
```

### S709 — 2026-09-09 — Purchase Orders: the un-swept sibling of the page it writes into

**Service worker `crest-v245` → `crest-v246`, `APP_VERSION` with it.** App code changed.
**One migration to apply**: `20260909150000_purchase_order_receipt_integrity.sql`.

A re-analysis of Purchase Orders, which had never had the sweep `Purchases.js` got in S698 — and
writes the same table. Eighteen findings, all fixed. The framing that made them easy to see:
**receiving goods IS a purchase entry**, so every rule the purchases module had learned applied
here, and none of them had been applied.

**A receipt was four round trips, and the last two could fail in silence.** `confirmReceive`
inserted the bills, fired one `qty_received` update per line, then updated the PO's status — and
that last write was a bare `await` with no error read at all. A dropped status write leaves the PO
on `draft` holding received quantities, and `draft` is exactly the status that still offers **Edit**,
whose save replaces every line row with a fresh one at `qty_received: 0`. The delivery then reads as
never received and can be received, and billed, a second time. Every link of that chain shipped.
`receive_purchase_order()` now does the lot in one transaction: it takes the PO row `FOR UPDATE`,
re-checks each line's remaining quantity, refuses a closed period, writes the bills, **increments**
`qty_received` rather than assigning the number this browser computed, and derives the status from
the table. Either all of it lands or none of it does.

That increment is the second finding. `qty_received` was a read-modify-write off the snapshot the
screen loaded with, so two people receiving one delivery — a storekeeper at the door and a manager
at the desk, which is how a delivery actually arrives — each banked it and the second erased the
first. The over-receive guard was computed off the same stale number, so it could not see it either.
The screen also re-reads the order's lines when it opens now, and **fails closed**: a failed read
does not open the receive screen at all, because "Remaining: 50" drawn from an error is the most
expensive wrong number this page can show.

**There was no closed-period lock, on the one page in the module that writes the locked table.**
`Purchases.js`, `PurchaseBillPage.jsx`, `Sales.js`, `Stock.js` and `Overheads.js` all spell
`const isLocked = !isAdmin && selectedPeriod?.status === 'closed'`; this page never had it, so
receiving was the way around a month-end close for anyone who happened to be here. It is the sixth
copy now, with both banners the others carry — and the first with a **server-side** half, since a
receipt is an RPC and an RPC that can be called directly is a door the page does not control. Why it
went unnoticed is worth keeping: it does not look like an entry page. It is a document workflow.
**Ask which tables a page writes, not which shape it has.**

**Nothing linked a bill back to the order it came from.** `purchase_entries` had no `po_id`; the
only trace was `invoice_ref = po_number`, free text that Purchases lets anyone overwrite. So
deleting the bill left the PO reading Received with no way back, editing its quantity diverged
ordered from billed silently, and no screen could answer "what did we order, and what actually
arrived". The column exists now, the receipt writes it, and the receive screen says what the order
has already produced. `save_purchase_bill` was amended in the same migration to **carry that link
through an edit** — without it the first correction anyone made to a received bill in Purchases cut
it loose. A link that does not survive an ordinary edit is not a link.

**The delete guard lived only in the page**, which is S707's sentence two tables over.
`if (!isAdmin) return` was the whole of it, and `purchase_orders` has no `no_ims_staff` fence — so
`DELETE /rest/v1/purchase_orders?id=eq.<uuid>` succeeded for every IMS account of any rank,
including a `staff` who cannot open the page and never sees the button.
`purchase_orders_guard_delete` refuses that, and refuses any order with bills against it for anyone,
operator included: `po_id` is `ON DELETE SET NULL`, so that delete would have SUCCEEDED and stripped
the link off the bills — the `confdeltype` trap, on a column added the same day. The page pre-checks
and words its own refusal; Cancel is the way through, and on a part-received order it is labelled
**Close Short** now and says what happens to the part that did arrive. Its old tooltip promised "no
purchase entries will be created" on orders whose entries already existed.

**The delivery was dated to today's day number inside the order's month.** Receive a Shrawan PO on
Bhadra 5 and the bill was filed as Shrawan 5, with nothing on screen to say so; the day box was
bounded 1–32, the range the column's CHECK allows rather than the 29–32 days a real BS month has. It
is a `BsCalendarPicker` locked to the order's own period now — it can only offer days that month
has — prefilled with today only when today falls in that period, and the screen states the month the
bill will land in whenever it differs from the one on screen.

**The VAT toggle was sticky.** `openReceive` reset the payment method, the error and the day, and
never `receiveVatInclusive` — so ticking it for one vendor left it ticked for the next order opened
in the same session, and every rate on that delivery was quietly divided by 1.13.

**The edit path could double a PO.** The orphan-line delete was `.not('id','in',(<new ids>))` with
its error discarded: an empty id list renders as `in.()`, which PostgREST rejects outright, and any
failure left the order holding BOTH sets of lines. A doubled PO does not look broken — it looks like
an order for twice as much, and it prices and receives that way. It deletes the ids the form was
opened on now, checks the result, and says what state the order is in if that fails. Editing also
requires draft **and** nothing received, belt-and-braces with the RPC.

**Every read on the page dropped its error** (S594/S612, for the fourth session running). A failed
periods read wore `NoPeriodState` — "no periods yet, create one" — and a failed PO read wore the
empty state: *"No purchase orders raised for Bhadra yet. Use + New PO to raise one"*, which invites
raising a second order for one that already exists. `firstError` + `ReportLoadError` now, and the
last good rows stay on screen under the error card.

**Editing an order whose vendor had since been archived painted "— Select vendor —" over it** —
state kept the id, so it saved correctly right up until someone touched the dropdown, at which point
the vendor was gone with no way back. Same for a deactivated item on a line. This is the repair S698
made in `PurchaseBillPage` for the same reason, on the page it was never carried to; both are
fetched and labelled *(inactive)* now.

**Smaller, and all real.** `getNextPoNumber()` scanned unpaged, so past 1000 orders the max could
sit outside the window and mint a duplicate — paged, and a failed read stops the save now rather
than numbering off a short list (sorting by `po_number` instead is not the shortcut it looks:
`PO-1000` sorts below `PO-999`). Expected Delivery was picked in BS, stored as AD and displayed as
AD — in the list and on the printed order the supplier receives; `formatAdAsBs()` joins
`bsCalendar.js` as the one home for that composition, which two HR files still hand-roll. The
printed order rounded each line to the rupee and took its total off the unrounded figures, so a
document a vendor invoices against need not add up; both are 2dp now and the total is the sum of the
printed lines. Quantities round to 3 decimals — the precision the column stores — so 0.3 ordered and
0.1 received twice stops leaving `0.09999999999999999` still on order, printed at the user in the
refusal. The `items` read pulled a `categories(name)` join nothing on the page renders. Saving an
order into a period other than the one on screen made it vanish, which reads as a save that did not
happen; the list follows it there. `init()` never claimed the page through `useLatestRequest` (its
own contract, the same miss S698 fixed next door). And every save is wrapped in `withTimeout` — a
supabase call can hang forever, and the `saving` flag with it.

**One thing deliberately not built.** Deleting a PO-created bill in Purchases still does not
un-receive the PO; the order keeps its received quantities. Un-receiving is a stock correction, and
stock corrections belong in Stock Count, not in a delete. The receive screen's "already billed" line
is where that divergence is now visible.

Six new `errorText` rules, with tests: these refusals are raised inside the one transaction, so
unlike a dropped fetch they genuinely do prove nothing landed — and saying so is what makes the
delivery safe to re-enter. `formatAdAsBs` has tests of its own, including the local-midnight parse
that keeps a bare `YYYY-MM-DD` off the previous day at +05:45.

Docs: Help → Purchase Orders (rewritten — it described an "approved" status the product does not
have), the IMS module guide's Purchase Orders section, `closed-periods.md` (six copies, and why this
page hid), `supabase-sql.md` (the third atomic RPC, the fourth delete trigger) and
`vendor-payables.md` (the S709 decisions, and that everything on this page is in BASE units).

### S708 — 2026-09-09 — Vendors: archiving a supplier removed it from its own reports

**Service worker `crest-v244` → `crest-v245`, `APP_VERSION` with it.** App code changed.
**One migration to apply**: `20260909140000_vendors_delete_reference_guard.sql`.

A re-analysis of the vendors surface — the page, its four referencing tables, the DB layer, and the
two reports that read vendor history. Ten findings; three were worth acting on today.

**Archiving a vendor deleted it from the two reports built to keep it.** S671 kept the `vendors` row
precisely so history stays readable, and the page says so in those words: "every past record keeps
its supplier", and Confirm Balance stays on an archived row "because reading its history is the
reason the row was kept." Both reports filtered `.eq('is_active', true)`, and archiving *forces*
`is_active = false` — so using the feature was what broke the promise it made.

On **Vendor Report** that filter decided the row set of a historical report. `vendorSummary`, the
Daily Breakdown matrix, the vendor combobox and the Excel export all mapped over active vendors,
while the footer TOTAL, the four KPI cards and `% of Net Total` were computed over *every* purchase
row in the period. A vendor deactivated mid-year therefore had its spend inside the total with no
row above it: the rows visibly failing to sum to their own footer, which discredits the rows that
were right (the S594 lesson). The fix is to drop the filter — `vendorSummary` already ends in
`.filter(r => r.gross > 0 || r.returned > 0)`, so an inactive vendor appears only if it genuinely
traded in the month being read, and the combobox is driven off that same list.

On **Vendor Balance Confirmation** it was a dead end rather than a wrong number. The `?vendor=` link
Vendors.js puts on every row preselects only if the id is in the loaded list (`(v || []).some(...)`)
— correct, and it is what stops a stale id selecting a vendor the client cannot see — but with the
list filtered to active vendors an archived one failed that test silently, so the button landed on
"Select a vendor to generate a balance confirmation" with that vendor absent from the dropdown too.
The picker now loads every vendor and splits the inactive ones under a **No longer active** optgroup:
a supplier still being bought from and one archived two years ago are both legitimate on a letter
about history, but they are not equally likely to be the one being looked for.

**`loadVendors` dropped its read error — the same bug Items.js fixed and wrote up, one directory
over.** `const { data } = await scopedFrom('vendors')` set the list to `[]` on a failed read,
rendered "No vendors yet. Add your suppliers to get started." over a client's entire supplier book,
and **wrote that empty array into the session cache**, so the next visit repainted it instantly with
no read in flight to correct it. It has a knock-on Items does not: `getNextVendorCode()` takes its
max over this array, so on an empty one it mints `VND-001` again on top of the real `VND-001`, and
nothing enforces vendor-code uniqueness in the database. Now it destructures `error`, keeps the last
good list up under a "may be out of date" banner, and shows a failed-read block instead of the empty
state. Paged with `fetchAllRows` in the same change and for the same reason: a read silently
truncated at PostgREST's 1000 rows mints the same duplicate code off the visible slice. A search
matching nothing also gets its own line — the empty state keyed off `viewing`, not `filtered`, so it
used to render a header row over an empty tbody.

**The delete guard moved into the database** (`vendors_guard_referenced_delete`, a BEFORE DELETE
trigger over `vendor_reference_counts()`). S671's browser guard is thorough — all four tables, a
click-time re-read, failing closed when that re-read errors — and none of that is a guard, for the
reason S707 had written down one table over. `vendors` carries no `no_ims_staff` fence, so every IMS
account of any rank can issue `DELETE /rest/v1/vendors?id=eq.<uuid>` with its own JWT, including an
`ims_role = 'staff'` account that cannot open the Vendors page at all and never sees the admin-only
Delete control. Two of the four referencing tables refuse that delete; `vendor_returns` and
`ims_gate_passes` are `ON DELETE SET NULL`, so it **succeeds** and strips the supplier off them. The
loss on `vendor_returns` is unrecoverable in a specific way worth recording: it keeps no name of its
own, its `log_audit` trigger records the SET NULL as an UPDATE carrying the old `vendor_id`, and
that id now resolves to a row that no longer exists — `vendors` itself has no audit trigger, so the
deleted row leaves no snapshot anywhere and the name is simply gone.

The trigger also closes a race the page cannot: its re-check and its DELETE are two round trips, so
a bill entered on another till in between is checked before it exists and deleted around afterwards.

**There is deliberately no `force_delete_vendor()`**, which is where this departs from its S707
sibling. `force_delete_item` exists because an item can be a genuine mis-entry someone needs gone.
A vendor with history is not that — it is a supplier the client really did buy from, and the only
thing a force-delete could do is destroy the record proving it. Archive already loses nothing, so it
is the way through, with no bypass for a client account of any rank, operator included; the service
role stays the escape hatch that keeps Danger Zone working.

**Left open, and named so they are decisions rather than omissions**: `vendors` still has no
`UNIQUE (client_id, lower(name))` and no client-side duplicate check either, so it sits where
`items` was before S706 — a duplicate splits one supplier's payables across two rows in Outstanding
Payables, two lines in Vendor Report and two balance letters each carrying half the balance, and a
lost response on Add Vendor retried makes the second row silently. `VENDOR_REF_TABLES` is inline in
the page with no migration-reading test of the kind `itemRefTables.test.js` is. There is no
`loadedClientRef` guard, so switching client leaves the previous one's vendor rows on screen until
the new read lands. The vendor-code prefix goes into `new RegExp` unescaped (as it does in Items.js).
Settings' vendor renumber loop checks no error yet reports "✓ Renumbered N vendors". And `loadUsage`
transfers every purchase line the client has ever entered just to count them, where
`vendor_reference_counts()` — added by this migration — is one round trip.

### S707 — 2026-09-09 — Item Master: the two guards S706 left as advice

**Service worker `crest-v243` → `crest-v244`, `APP_VERSION` with it.** App code changed.
**Two migrations to apply**, in order: `20260909120000_items_client_name_unique.sql`, then
`20260909130000_items_delete_reference_guard.sql`.

S706 fixed Item Master's duplicate-name check and its delete guard. Both fixes were real and both
lived entirely in the browser, which is a different thing from being enforced. This session closed
the gap on each.

**`items` now has `UNIQUE (client_id, lower(name))`.** The S706 check tests an array held in React
state, so two tabs both pass it — and worse, `loadItems` filters `.eq('is_sub_recipe', false)`, so
the array does not contain sub-recipe mirror rows at all. Stock Count deliberately does not filter
them either, so a real item and a mirror sharing one name are two rows in the same count: the exact
split-the-ingredient harm the check exists to prevent, reached by the one route it could not see.
Three of the four write paths into `items` never ran the check in any form — the Recipes.js mirror,
`push_master_data`, and the Export/Import restore.

The index is case-insensitive (the push's own adoption already matches on `lower(name)`), covers
mirrors, and covers hidden items — hiding is what every delete refusal offers as the alternative,
so hidden rows accumulate by design and still carry the history their name refers to. A looped
dedupe pass renames pre-existing duplicates `-DUP2`, `-DUP3` before the index is created, ordering
real items ahead of mirrors so a real item always keeps the plain name, and asserts it converged
rather than letting `CREATE UNIQUE INDEX` fail on data nobody could see beforehand. **Review
anything it renames**: a `-DUP2` is a genuine pre-existing split that someone has to merge or
retire.

Three call sites had to learn the constraint before it could be added safely. `push_master_data`
gained a fourth plan action, **`conflict`** — without it one colliding item name would raise 23505
and abort an entire multi-outlet push with a constraint name for a message; it is now reported in
the preview, per branch, naming the record in the way, and skipped by the apply pass while the rest
lands. `Recipes.js` checks the mirror's name in both directions and says what a clash means (a
sub-recipe is stock-counted, so the two would split that stock) instead of surfacing a raw 23505.
`restoreClientData` deduped the artifact on the way in — the restore loop breaks a table on its
first failing chunk, so a single duplicate pair in a pre-index backup would have abandoned the
client's entire item book and then every table referencing it.

**The delete guard moved into the database.** `items` carries one permissive policy and restrictive
fences for POS PIN staff, HR self-service and HR-role staff — and is correctly absent from the
`no_ims_staff` list, because IMS needs the item book. So every IMS account of any rank could
`DELETE /rest/v1/items?id=eq.<uuid>` with its own JWT: including `ims_role = 'staff'`, which cannot
open Item Master at all. Five of the eleven referencing tables hold that delete. The three
`ON DELETE CASCADE` tables go with it, and two of those three carry no `log_audit` trigger, so
`requisition_lines` and `staff_meals` leave no trace anywhere — staff meals being inside
`computeUsed()` and therefore inside COGS. There is no server-side closed-period write guard, so a
closed period was not protection either.

It is a **BEFORE DELETE trigger**, not an RPC, per privilege invariant #3: an RPC protects only the
callers that choose to call it and leaves the open policy exactly as wide. Same shape as S698's
`purchase_entries_guard_paid_delete` — SECURITY INVOKER, keyed on `current_user`, so the service
role and SECURITY DEFINER bodies pass through. `force_delete_item()` is that one way through:
admin-only under `COALESCE(is_admin(), false)`, and **atomic**, which the twelve separate HTTP
requests it replaces could never be. That loop is precisely what left eight tables emptied and the
item standing in S706; a function body is one transaction, so the failure message can now say
nothing was removed and mean it.

Smaller things in the same pass: `getNextItemCode()` minted from the filtered, cache-seeded array,
so a mirror's code never counted toward the max and the next item could be minted onto it — it
reads the unfiltered book now (`item_code` is deliberately left without a unique index; nothing
keys off it, and pushing HQ's codes into a branch that minted its own would make every such push an
abort). `errorText.js` gained four rules ahead of the generic 23505 one, since "that already
exists" says nothing about what splits if you proceed. `itemRefTables.test.js` now also reads the
new migration and asserts the SQL table list matches `ITEM_REF_TABLES` in membership *and* order,
and that the INVOKER/DEFINER pair has not been swapped — the list exists twice now, because the
server cannot import a `.js` module.

Deliberately not done: a completion report after a force-delete. The function returns what it
cleared per table, and the only page-level channel on Item Master is `ActionError`, which is red
and carries `role="alert"` — a success report rendered through it reads as a failure, and a neutral
notice is its own piece of design work.

**The IMS module guide had drifted twice and been half-corrected twice.** Its `workflow` array still
taught the Add/Edit modal as "Purchase Qty, Rate … Purchase Unit / Base Unit / Conversion Factor" —
`Purchase Qty` was removed in S597 and `Base Unit` in S706, and both of those sessions updated the
`fields` and `gotchas` arrays directly below it while leaving the workflow line describing a form
that had not existed for two sessions. The same line's neighbour still said delete is blocked
"across 8 tables" while the gotcha S706 added four lines later said eleven. Both corrected, plus a
Help tip for the name rule. This is the drift the module-guide rule exists for: a guide is prose
about a screen, so nothing fails when it stops being true, and fixing the paragraph you came for
is not the same as fixing the section.

Rules updated, and the list is longer than the change because a constraint on a shared table is a
fact several rules had written down: `item-master-rates.md` (two new sections), `error-messages.md`,
`multi-outlet.md` (which asserted in so many words that `items` had no `UNIQUE(client_id, name)`,
and now carries the `conflict` action and the latent double-adopt fault the index closes),
`recipes-and-subrecipes.md` (the mirror shares one name space with the item book, and why the

was taken is a restore hazard, and this loop makes it a whole-table one), `supabase-sql.md` (the
`BEFORE DELETE` guard now has a second instance, so what generalises from it is written down), and
the two places in `CLAUDE.md` that asserted the same missing index.

### S706 — 2026-09-09 — Item Master: a delete guard the database only half backs up

**Service worker `crest-v242` → `crest-v243`, `APP_VERSION` with it.** App code changed.

A re-analysis of the Item Master surface — `Items.js`, its route/nav pair, the eleven tables that
reference `items`, and the IMS guide entry — found twelve things. The first three are one defect
wearing three faces, and the face nobody could see is that **the database is a backstop for five
of the eleven referencing tables and not for the other three.**

**Force-delete destroyed history and then failed, telling the operator to try again.** The clearing
loop knew eight tables. `par_levels`, `purchase_order_items` and `stock_movements` reference
`items` too, all with plain FKs — so Postgres refused the final delete *after* the other eight had
been emptied, and the item survived with its purchases, stock counts, wastage, requisitions,
vendor returns and recipe lines already gone. The message said "Try the delete again", which could
never work: retrying repeats the same refusal and clears nothing further. Any item with a par
level, a purchase-order line or POS depletion hit this. The list is now one exported constant,
`itemRefTables.js`, read by both the usage scan and the delete loop, so the two sets cannot
diverge again — and `itemRefTables.test.js` reads the migrations and fails when a new `item_id` FK
does not reach it (verified to fail against the pre-fix list, on both the omission and a wrong
cascade flag).

**Three of those FKs are `ON DELETE CASCADE`, so a wrong guard does not fail safely.**
`requisition_lines`, `staff_meals` and `vendor_returns` are deleted *with* the item rather than
blocking it — the `confdeltype` rule this repo already learned on `vendors`, in the one place where
the consequence is destroyed history. The guard was reading `usageMap`, which only counts a row
when `qty > 0`, and **`staff_meals.qty` defaults to 0** — so a zero-quantity staff meal earned no
badge, passed the guard, and cascaded away under a confirm dialog reading *"Nothing references this
item, so no purchase, count or recipe changes."* One set of reads now builds two maps: `usageMap`
(live usage, the chip) and `refMap` (any row at all, the only thing the guard may consult).

**And the scan itself could fail open.** Every item id went into one `.in()` — the reference
client's 254 items are ~9 KB of uuids per request, past what proxies accept — and each table's
failure was *skipped quietly*, which blanked the whole Used In column and left every item looking
unreferenced. Chunked through `fetchAllRowsChunked` now, and a table that could not be read is
recorded rather than treated as clear: the column says "not checked" instead of showing a dash,
a banner names what failed, and the delete refuses outright. An absent chip means "no records" or
it means nothing at all.

**Two reads stopped at 1000.** `loadItems` was a bare select, so past 1000 SKUs the page showed a
partial item book as the whole one — and `getNextItemCode()` takes its max over what it can see,
while `item_code` carries no unique index, so it would have minted duplicates. The id read feeding
the usage scan was capped the same way, meaning items past the cap were never checked for usage at
all. Both paged, with `.order('id')` as the tiebreaker.

**A failed read rendered as an empty item book, and then cached it.** Both loaders dropped `error`,
so `data || []` printed "No items yet. Add your first ingredient to get started" over a client's
entire master list — and `writePageCache` stored that empty array for ten minutes, so the next
visit repainted it instantly with no read in flight to correct it. Neither loader now caches a
result it did not get; a failed read renders as a failed read, and a failed *refresh* over a list
already on screen says the rows may be out of date rather than looking freshly loaded.

**`yield_pct` was unvalidated at save.** `min="1" max="100"` on the input is decorative — the
dialog is not a `<form>` and Save is a plain `onClick` — while the column is `numeric(5,2)` and
every recipe cost divides by it, so a typed `500` makes every dish using that item cost a fifth of
what it does, silently and everywhere at once. A `0` became `100` with no message, which is a
different number from the one the user typed.

**`base_unit` was a field nothing reads.** The Purchase Bill scales `qty × conversion_factor` into
the item's `uom` and never looks at `base_unit`, so a base unit disagreeing with the UOM was always
a mistake — and the only screen showing it, this form's own preview, labelled the rate
"per {base_unit}" when the rate is per UOM. The box is gone; the tab states the UOM instead, the
value is derived on save, and a legacy row repairs itself the next time it is edited. Same move as
S597's `Purchase Qty`: a field with one correct answer must not look like a choice.

**Hide's stated consequence was incomplete.** Six report reads filter `.eq('is_active', true)` per
the S436 rule that stock is never valued off an inactive item, so hiding an item that still holds
stock takes its value out of the stock and monthly figures. Every refusal offers hiding as the
gentle alternative and none of them said so. And `toggleActive` — the action all of them point at —
was a bare `await` with nothing destructured, so a refused Hide reloaded the row unchanged, which
reads as the item already being in that state.

Smaller, from the same read: the FK check matched on `error.message` text rather than code `23503`;
an admin switching clients kept the previous client's items on screen, filterable and editable,
because `loading` was only raised when the list happened to be empty; Print emitted the *filtered*
subset under a bare "Item Master" while every filter control is `no-print`, and now carries a scope
line; `clearAllConversions` counted non-sub-recipe items and updated sub-recipe mirrors too; a
duplicate item name saved happily (`items` has no `UNIQUE(client_id, name)`) and split an
ingredient's purchases across two master rows; and the actions cell was `display: flex` on the
`<td>` itself. The IMS guide's Conversion entry, its preview formula and two new gotchas were
updated in the same change — it had been teaching the `base_unit` shape.

A re-analysis of the period surface — `Periods.js`, `closePeriod.js`, the two notes files and the

### S704 — 2026-09-08 — The Quick Calculator stops being a modal, and can be dragged

**Service worker `crest-v240` → `crest-v241`, with `APP_VERSION` moved to match.** Worth noting how
that second half got remembered: not from the bump itself, but from re-reading `README.md`'s
Conventions section while updating the docs — which is the argument for the pairing being a test
(`appVersion.test.js`) rather than a habit.

Reported from a screenshot: the calculator was open over a Purchases bill list and the page behind
it was unreachable. It was not a stacking bug or a missed `pointer-events` — it was the shape the
component had been built on. `Calculator.js` opened with `Modal.js`'s overlay verbatim: a
`position: fixed; inset: 0` scrim at `rgba(0,0,0,0.6)` covering the whole viewport, with
`onClick={onClose}` on it. Every pixel outside the 380px panel belonged to that div, so the page
underneath could not be scrolled, clicked or typed into, and the dimming was the scrim doing
exactly what a scrim is for.

**Which made the tool prevent the one thing it exists for.** You open Alt+C *to check a figure that
is on the page* — a rate, a bill total, a count — and the scrim both dimmed that figure and, being
the close affordance, dismissed the calculator the moment you clicked it. A scrim is the correct
control for a dialog that owns a decision: it says *finish this before doing anything else*. This
owns nothing. So the backdrop, the click-outside-to-close and the focus trap are gone, and the
panel is a floating one the user positions.

**Drag is `setPointerCapture` on the header, not `mousedown` plus document listeners.** Capture
routes every subsequent move and up back to the handle even when the pointer outruns it or leaves
the window, and one code path covers mouse, touch and pen. `touchAction: 'none'` on the row, or a
touch drag scrolls the page underneath instead of moving the panel. Position survives close and
reopen for the session — you put it where it does not cover what you are reading, and reopening
should not undo that — but is deliberately **not** persisted: a position saved on one monitor is
how a panel gets stranded off-screen on another. `clampPos()` measures the live element rather than
the constants (the panel's height changes with the tape, its width shrinks on a phone) and runs on
open and on resize as well as on every drag frame, so the header is always reachable.

**Two rules already in this repo decided the markup.** The drag row holds the `×` button, and
interactive content inside a `role="button"` container is invalid and unfocusable (S653) — so the
row carries the pointer handlers and the grab cursor, and the keyboard affordance is a separate
focusable grip holding only an icon. That grip takes the arrow keys, because the reason to move
this panel is to uncover the figure underneath it and a drag-only affordance puts that out of a
keyboard user's reach entirely (WCAG 2.5.7). `:focus-visible` has no inline form, so the grip is
`.calc-drag-grip` in `Layout.css` with the product's `--theme-focus-ring` + `--theme-focus-outline`
pair, rather than the UA outline an inline-styled element would have fallen back to.

`zIndex` went 400 → **2500**: above every `Modal` (2100 is the highest any caller passes) and below
`Tip`'s 9999. The purchase-bill form is exactly where someone reaches for Alt+C, and a floating
tool a dialog can bury is a tool you cannot use where you most need it. The panel also picked up
`no-print` — without a scrim it is far easier to leave one open over a report someone then prints —
and `role="dialog"` **without** `aria-modal`, since nothing behind it is inert and claiming
otherwise would tell a screen reader the rest of the page is unavailable when it is exactly as
available as before.

The capture-phase Escape handler stays and its long comment stays with it. It was written so the
calculator could sit inside a `Modal` without Escape closing the modal first; now that the two can
genuinely be open together it matters more, not less.

**Docs.** The general rule went to `.claude/rules/design-system.md` as **"A scrim is a control, and
it says finish this before anything else"** — ask what an overlay OWNS before giving it one, plus
the four things a non-modal floating panel needs that `Modal` supplies for free and the three rules
a drag needs. `component-library.md`'s `Calculator` row no longer calls it a modal.
`input-arithmetic.md` — the file that auto-loads when you open `Calculator.js` — got a pointer at
both, since it covers the evaluator and says nothing about the shell. Help → *Quick Calculator &
Inline Math* and the IMS module guide's Purchases entry now say the page underneath stays live and
that the panel can be dragged; the old Help copy already claimed it "floats over any page", which
was true of its position and false of everything else.
