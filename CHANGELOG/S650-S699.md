### S675 — 2026-09-04 — every tenant Owner was locked out of the product by a filter that matched nothing

**Service worker `crest-v187` → `crest-v188`. No migration, no Edge Function deploy.**
**This was a live, total lockout of every client Owner, and accepting could not clear it.**

`AuthContext.js` read the acceptance ledger with
`.in('doc_type', docsRequiringReacceptance())` — but that helper returns document **objects**.
PostgREST stringifies whatever it is handed, so the filter was on the literal text
`[object Object]`, matched no rows, and returned `{ data: [], error: null }`. That is a *successful*
read stating the client has accepted nothing. The memo therefore held every Owner at the blocking
gate, and the acceptance they submitted was written correctly and then never seen by the re-read.

**Both of the safeguards built for exactly this screen were bypassed, and for the same reason.** The
read fails OPEN on error — but `legalErr` was null, so that branch was never reached. And S672 had
already been bitten by the objects-versus-strings distinction in the *other* direction, documented
at length in `legal-documents.md` with the same predicted symptom ("held at the blocking screen
permanently, with no way out except Sign Out"). `reacceptGuard.test.js` was written to catch it and
tests the helper, which was correct both times. **The fault was at the call site, which passed the
wrong one of two correct functions — so a test of the helper passes happily while the product is
shut.**

The fix is structural rather than a corrected argument: `reacceptDocTypes()` now exists beside
`docsRequiringReacceptance()`, and the rule is that anything comparing against the `doc_type`
COLUMN calls the former while anything reading a version or hash calls the latter — neither caller
does the `.map` itself. Two new tests read the **source** and fail if any `.in('doc_type', …)` in
`src/` is given anything but a types-shaped value; both were verified against the exact string that
shipped rather than assumed to work.

Found by shipping S674's recovery message first, which is the only reason the state was
diagnosable: the gate said "your acceptance was recorded but this screen did not refresh", which
distinguished a failed write from a failed read. 52 suites / 614 tests.

### S674 — 2026-09-04 — the re-acceptance gate stops being able to hang on "Recording…"

**Service worker `crest-v186` → `crest-v187`. No migration.** If `record_legal_acceptance` has not
been deployed since S672, **`supabase functions deploy admin-user-ops` is the actual fix** — this
change is what makes that legible rather than silent.

**Reported as a screenshot of the gate stuck on "Recording…" with no error and nothing to press.**
Two defects were behind it, both in code S672 shipped, and each one alone produces that screen.

**`await refreshProfile()` was unguarded, and there was no `finally`.** `busy` was cleared only in
the `catch`, on the reasoning that a successful accept unmounts the gate. That holds right up until
the re-read does not clear it — and `refreshProfile` runs `fetchProfile`, which makes several
sequential Supabase reads, any one of which can hang forever per the standing `withTimeout` rule.
The file's own header comment explains that exact failure mode for the `invoke` call directly above
and then leaves the next `await` bare. It is the worse of the two positions to hang in: the
acceptance row is already in a seven-year ledger, the gate is still up, and the only control on the
screen reads "Recording…" permanently. Both awaits are now bounded, `busy` clears in a `finally`,
and reaching the line after the refresh — which can only happen if the gate did *not* clear — now
says so and offers a Reload, rather than silently re-arming a button whose second press would write
a duplicate row.

**It called `supabase.functions.invoke` directly instead of `adminOp`.** invoke reports every
non-2xx as the same `Edge Function returned a non-2xx status code`, so `Unknown action:
record_legal_acceptance` — what the function returns when it has not been redeployed since S672
added the action — was indistinguishable from `Forbidden` and from a failed insert. This is the S619
rule (`an error surfaced as error.message is not a message`) in the one place where the reader is
held at a blocking screen and has no other diagnostic.

**`adminOp.js` moved from `src/pages/adminClients/` to `src/shared/`**, two importers repointed. A
route guard reaching into a page directory is the wrong direction, and it is what made skipping the
wrapper the path of least resistance in the first place.

App code changed. 52 suites / 609 tests pass; `build:verify` clean.

any lazy route propagated past both `Suspense` boundaries (Suspense catches promises, not errors)

instances: app scope (`App.js`, wrapping `ThemeProvider`, so a crash in the providers themselves is

*only* `<Suspense><Outlet /></Suspense>`, not the whole `<main>`, so the sidebar survives and

credential-shaped before it can reach a clipboard destined for WhatsApp.

copy of a contact row.

**`Legal.jsx` still hard-coded `mailto:support@crestsuite.com`** — the unowned domain S672

to load, i.e. the exact moment nothing else works. Fixed to the one `SUPPORT_EMAIL` constant;
`supportAddress.test.js` scans `src/` so it can't come back under a different file.

**The phone number ships unfilled, behind the same `[[NEEDS VALUE: X]]` marker convention
`isDraft()` already uses for the legal documents** — `supportPhone()` returns `null` while it
stands, so every surface hides the phone entirely rather than ever rendering the placeholder to a
client. Filling in the real digits in `supportContact.js` is the only step left before every one of
these surfaces shows a working number: the login footer, the Help page's new Support tab, the two

Deliberately deferred, with reasoning and precedent pointers left in

### S672 — 2026-09-03 — the sentence that claimed a contract existed gets documents, links and a ledger behind it

**Service worker `crest-v181` → `crest-v182`. Three migrations — `20260903130000_legal_acceptances.sql`,
`20260903140000_client_legal_entity.sql` and `20260903150000_trial_auto_purge.sql` — apply before
deploying, plus `supabase functions deploy admin-user-ops`. The third schedules a job that DELETES
live tenant data: run `SELECT * FROM public.trials_due_for_purge();` and read every row with a NULL
`blocked_reason` before letting it fire.**

**The starting point was one line of copy that had been writing cheques the product could not cash.**
`Login.js` told every trial signup *"By starting a trial you agree to our Terms of Service and
Privacy Policy."* Neither document existed — no route, no file, no text — the two phrases were plain
unlinked prose, and nothing anywhere recorded that anyone had agreed to anything: no version, no
timestamp, no address, no user agent. Under ETA 2063 an e-contract needs clearly expressed offer and
acceptance; this had neither, plus a reference to documents nobody could read.

**The spec this was built from was written against a schema that does not exist.** It assumed
`shared_tenants` and a `shared_` prefix (there is one schema, `public`, and the table is `clients`), a
role called `owner` (there is none — Owner is the ABSENCE of the four staff markers), a pgcrypto
`digest()` trigger for the content hash (pgcrypto lives in the `extensions` schema here and every
`SECURITY DEFINER` body sets `search_path TO 'public'`, so it fails at runtime — a call this repo
already documented avoiding in `pin_vault.sql`), a Storage bucket (the one prior attempt at an
authenticated-INSERT bucket failed and was reverted two days later), and transactional email (there
is none, at all). Its own SQL had a bug too: the unique index references `is_current` on the line
before the `ALTER TABLE` that adds it. The legal TEXTS were good and are used close to verbatim.

**Version, hash and prose ship in one bundle, and the database holds no document text.** The spec
wanted a `legal_documents` table the app reads "current version" from. That combination is unsafe
here specifically: the service worker is cache-first, so a database saying "1.1 is current" against a
browser still serving the cached 1.0 chunk would show someone the old text above a checkbox recording
that they accepted the new one. `src/legal/*.md` is canonical in git, `scripts/hash-legal.mjs`
computes the SHA-256 over LF bytes and emits a tiny metadata module (safe to import anywhere, and
`Login.js` does) plus a 27 kB text module reached only by dynamic import — verified in the built
output: the prose is its own chunk and the main bundle carries only the hashes.

**Acceptance is written by the server, never the browser.** The spec proposed an INSERT policy for
`authenticated` with the row carrying its own `user_id`, `ip_address` and `user_agent` — self-attested
twice over, since a browser cannot know its own public IP and attribution the subject chooses is not
attribution (S531 invariant #3). `legal_acceptances` has a SELECT policy and **nothing else**;
`authenticated` holds only a SELECT grant. `register_trial` now **refuses the signup outright**
without an `accepted_legal` payload — so the checkbox is not decoration — and rolls the auth user and
client back if the ledger insert fails, because an account with no consent record is the state the
whole change exists to end.

**Three registrations are deliberately skipped, and the migration header says so at length**, because
each reads as an oversight: the Danger Zone wipe (a data clear must not erase consent, retained 7
years per the Privacy Policy — which is also why `client_id` is `ON DELETE SET NULL` beside a
denormalised `client_name`, the `audit_logs` shape), `CLIENT_SCOPED_TABLES`, and `RESTORE_ORDER`
(restore inserts from the browser, which has no grant — and an acceptance re-insertable from a
spreadsheet would not be evidence).

**Where things live is mostly a story about gates.** The client's own acceptance record went to
**Help, not Settings** — `/settings` is behind `ModuleGate module="ims"`, so a POS-only or HR-only
client can never reach it. Staff get an explicit "owner only" line rather than an empty table,
because the four RESTRICTIVE families return `{data: [], error: null}` and on this page an empty
table is a claim that the business has agreed to nothing. The re-acceptance gate is a **full page,
not a `Modal`** — `Modal` closes on Escape and backdrop click unconditionally, so a gate built on it
is dismissible by one keypress — mounted at `ProtectedRoute`'s single choke point right after
`accessLocked`. And the agreement print route is a sub-route with no nav item, so its role check
lives in the component after every hook, with the client id pinned to the caller's own whatever the
query string says.

**Four things the documents claimed that the code does not do, found by writing them out.** §7.5's
self-serve export does not exist — `Login.js`'s own marketing copy already says "Ask", deliberately,
because every export path is admin-side — so it is now an assisted export on request. The
sub-processor table lists only providers that are actually live (no email vendor, no analytics, bank
transfer only; the payment webhook is an unonboarded placeholder). Trial terms say **7 days and 15
days** because that is what `register_trial` writes, not the spec's 14 and 30. **Still outstanding

**Then the retention gap got closed rather than reworded, which is the largest and most dangerous
piece of this.** `trial_purge_at` had been written at every signup since the form was built and
nothing read it — `data-export.md` said so outright ("build the parachute before the jump").
`20260903150000` is the jump: pg_cron posts to a new `purge_due_trials` action nightly at 01:05
Nepal. Everything about it is arranged around one question, *what would have to be true for this to
delete a paying customer?*, and the realistic answer is not a bug — `is_trial` is cleared by exactly

So **six independent guards, all in SQL** where they can be audited without reading Deno: still a

ended**. That last guard is not new policy — `data-export.md` had already named `last_backup_at` as

`trials_due_for_purge()` returns overdue trials **with a `blocked_reason` rather than a filtered

### S671 — 2026-09-03 — a vendor can leave the Vendors page without leaving its own history, and the page stops scrolling sideways

**Service worker `crest-v180` → `crest-v181`. Migration `20260903120000_vendors_archive.sql` — apply
before deploying.**

**The ask: an admin-only delete on Vendors for inactive vendors, or ones with no purchases.** Half of
it already existed and had since the modularization commit — the button was `isAdmin`-gated and
refused when purchase entries were recorded. Three things were wrong with it, and the third could
have destroyed data.

**It checked one of four referencing tables.** Only `purchase_entries`. `purchase_orders` holds a
plain FK, so a vendor with an open PO and no bills hit a raw Postgres foreign-key violation instead
of a sentence. Worse, **`vendor_returns` and `ims_gate_passes` are `ON DELETE SET NULL`** — there the
delete *succeeds* and the rows quietly lose their supplier, and `vendor_returns` stores no name of
its own, so a credit note's supplier would have been unrecoverable with nothing on any screen saying
it had happened. The database was never going to catch that half; a check across all four in the app
is the only thing that does. (`payable_payments` hangs off `purchase_entries` and rides along.)

**Its guard passed vacuously on a failed read.** `const { count } = await …` dropped the error,
`count` is `null` when the read fails, and `null > 0` is `false` — so a dropped connection waved the
delete straight through. The shape `CLAUDE.md` names as *a guard that drops its read error passes
vacuously*, on the one action in the module that cannot be undone. The four counts now run together
and any error refuses.

**And the button appeared where it could only refuse.** A vendor with 400 bills carried the same red
Delete as a mis-typed row added yesterday.

**Then the ask's real half: "keep the vendor name in the history, but delete it from the Vendors
page."** Those two cannot both be true of a `DELETE`, and the reason is worth writing down because it
is not visible from the Vendors page at all: **`purchase_entries`, `purchase_orders` and
`vendor_returns` store only `vendor_id`, and every report resolves the name by joining `vendors`.**
`ims_gate_passes` is the one table with a `vendor_name` of its own. So the vendor row is not a lookup
convenience — it is the single copy of the supplier's name, and deleting it is precisely what erases
the supplier from the client's own history. Denormalising a `vendor_name` snapshot onto the other
three was the alternative and was rejected: it needs `vendor_id` to go nullable on the most important
table in IMS, and `VendorReport`/`OutstandingPayables` group by `vendor_id`, so two deleted vendors
would collapse into one NULL bucket and **merge their outstanding balances**.

**So `vendors.archived_at`.** The row is kept and hidden: every FK, join and report is untouched,
history keeps its name, and the vendor leaves the Vendors page and every picker. Reversible. The
admin slot is now one of three, and never a control whose answer is already known:

| Row | Slot |
| --- | --- |
| Nothing references it | **Delete** — a real hard delete |
| Referenced, already inactive | **Archive** — off the page, name kept |
| Referenced, still active | **In use**, with a `Tip` naming what is attached |

A `CHECK (archived_at IS NULL OR is_active IS NOT TRUE)` carries the one invariant that matters:
`is_active` is the column every purchase, PO and gate-pass picker filters on, so an archived-but-active
vendor would keep appearing in the dropdowns it was archived to leave. Archiving sets both; **Restore
clears `archived_at` and deliberately leaves the vendor inactive**, so the two never have to be
reasoned about in one write. Archived rows offer Confirm Balance and Restore only — Edit and Activate
are withheld, since either is a side door back into the pickers.

**The usage pass behind the gating.** One read per table over every vendor at once, not a count per
vendor per table (four requests a row), through `fetchAllRowsChunked` — `purchase_entries` alone
crosses PostgREST's silent 1000-row cap on any real client, and a truncated read here reports a used
vendor as unused, which is exactly the failure S528 found feeding Items' force-delete guard. Admin-only
and not awaited, so a normal login pays nothing and the list paints first. It is a page-load snapshot,
so the click re-checks: a bill entered on another till since then must still be able to stop the delete.

Three states, not two, and the third is a bug this shipped with and then fixed: `'loading'` renders
nothing in the slot (better than a button that appears and vanishes), `'failed'` renders the button
because not knowing is not the same as knowing the row is clean — **and the first cut only reached
`'failed'` on a returned `{ error }`, never on a throw.** A rejected fetch would have left `usage`
stuck in `'loading'` and the control permanently absent, with no error anywhere: the page silently
losing a feature rather than failing. `loadUsage` now catches.

Help gains a rewritten "Why won't a vendor delete?" and the IMS module guide carries the mechanism,
since the answer is a fact about the schema rather than a policy.

**Then the table stopped fitting, which is what the rebuild was really for.** Reported from a
screenshot: the action buttons pushed the page into horizontal scroll, and the thing that scrolled
out of view was the vendor NAME — the only column that says which row you are acting on. Measured
in a harness against the real `Layout.css` and the longest values in the reported screenshots
(S649's rule: sample from the client's data, not from a plausible row):

| | min-content | Actions column |
| --- | --- | --- |
| Before | **1115px** | **314px** |
| After | **809px** | **148px** |

At a 1280px window the page offers 934px, so the old table overflowed — exactly the reported
symptom. Four changes, in order of what they bought:

- **The four text buttons became icon buttons** (`.btn-icon`, new in `Layout.css` — worn over `.btn`
  plus a variant so it keeps the focus ring, the `:disabled` treatment and the coarse touch floor
  rather than being hand-rolled inline). Icon-only means the icon carries no accessible name, so

### S651 — 2026-08-30 — a closed month gets a way in, so a missed purchase bill can still be filed

Service worker `crest-v168`. No migration.

Reported from Periods: *"allow the admin to reopen closed periods to enter missing purchase bills."*
Admin could already do it — every period-scoped IMS entry page locks on `!isAdmin && closed`, so a
closed month has always been writable for admin. What was missing was a **way in**: Purchases opens
on the OPEN period, and nothing on the closed row pointed anywhere. Reopen was the only visible
affordance and it is the one thing that cannot work here — `monthly_periods_one_open_per_client`
blocks it whenever a later month is open, which is precisely the moment a missing bill turns up.

So the fix is a route, not a second open period. Widening that index would have to be paid for by
every page that reads `.eq('status','open').single()`.

- **Periods → "Add missing bills →"** on every closed row (IMS clients), linking to
  `/purchases?period=<id>`. Reopen stays, unchanged, and its tooltip now says what it is actually
  for — handing entry back to the *client's own* logins — instead of describing itself as the way
  to resume editing.
- **`/purchases?period=<id>`** — the list page now honours a period in the query string on first
  load (and keeps the URL in sync on every change, `replace` so arrowing the dropdown doesn't fill
  the back button). An id not in this client's own period list is ignored, so a stale or foreign
  link degrades to the open period rather than rendering nothing.
- **The bill form returns to the bill's own month.** All four `navigate('/purchases')` sites now
  carry `?period=`. Without it, an admin who filed a bill into Shrawan landed back on Bhadra and
  could not see what they had just entered — the worst possible ending for this exact workflow.
- **An amber banner on both screens** whenever admin has a closed month selected. `isLocked`'s
  `!isAdmin` carve-out is what makes the entry possible, and it also meant admin got *no* signal
  the month was closed — every control looked like the open period's. It names the month, says the
  entry is deliberate, and says the part the entry does not do on its own: the Monthly Report was
  frozen at close and does not include the new bill until **Regenerate Snapshot** is run.

The reopen-blocked alert now names all three working paths rather than only Resync Opening Stock.

Also updated: the Periods entry in Help (tips + the "what happens when I close a period" FAQ) and in
the IMS module guide, where "Add missing bills" is now a documented field and the reachability
problem is written down as a gotcha.

**Written down as rules**, since the shape is more general than this one screen:

- **`.claude/rules/closed-periods.md`** (new) — the `isLocked = !isAdmin && closed` line and its five
  copies, why Reopen can never be the admin path, the `?period=` route contract, and the two
  follow-ups a closed-month write does not perform on its own. Loads on Periods and the IMS entry
  modules. `CLAUDE.md`'s existing one-open-period bullet now points at it rather than growing again.
- **`.claude/rules/owner-report.md`** — a "what happens AFTER the close" section: the snapshot does
  not follow a post-close correction, and must not start doing so automatically.
- **`DESIGN.md`** — the red/amber page-state banner pair. Red says *you cannot write here*, amber
  says *you can, and here is why this is unusual*. They are the same fact drawn for two audiences,
  and for a year only one of them existed: the `!isAdmin` carve-out suppressed the closed-period
  notice along with the lock, so the one person who could rewrite a closed month saw the open
  month's screen.

### S650 — 2026-08-30 — Purchases gains a Bill no. search and a Payment filter

Service worker `crest-v167`. No migration.

Two filters added to the Purchases list, beside the existing day pills, Item and Vendor. Both feed
the same `filtered` set, so the entry count and **both** footer totals (goods value ex-VAT, and
payable incl. VAT) follow them; changing period clears all five.

**Bill no.** searches `purchase_entries.invoice_ref` — the `#TII6339` printed under the vendor name
on each bill row. Case-insensitive substring, because a reference is remembered by its tail digits
rather than its prefix, and **a leading `#` is stripped** so pasting it back exactly as displayed
works rather than matching nothing.

**Payment** is Cash / Credit / FonePay, and two decisions in it are the ones worth keeping:

- **The option list is built from the methods the period actually used**, in the bill form's order,
  with any unrecognised value appended rather than dropped. An option that returns nothing is
  noise; a value in the data with no option is a row nothing can reach. Same reasoning as the day
  pills being built from the data instead of 1..32. The whole control hides when a period has only
  one method.
- **A blank `payment_method` is Cash**, which every display already assumed via `|| 'Cash'` — bills
  written before the column existed, and anything the form defaulted. Filtering the raw column
  would have hidden rows the screen labels Cash. `methodOf(p)` is now the single place that
  fallback lives, shared by the filter, the option list and the row badge, so they cannot disagree.
  (Same family as the standing `.neq drops NULL rows` trap: a NULL is not a value you can compare.)

**`PURCHASE_PAYMENT_METHODS` moved to `purchasesHelpers.js`.** It had been retyped identically in
`PurchaseBillForm.jsx` and `PurchaseOrders.js`; this filter was the third reader, which is where two
copies become a list that can disagree with itself. Deliberately still separate from POS's
`PAYMENT_METHODS` — that is how a guest pays *us*, this is how we pay a *supplier*, and they have no
reason to move together.

**`filtered`, `byDay` and `filteredPayable` are now memoized.** This page had no text input until
now; a controlled one re-runs every render-body derivation per keystroke, and `filteredPayable`
walks each bill group through `calcBillTotals`. The values are unchanged — this is the shape
`.claude/rules/frontend-performance.md` exists for, and adding a search box without it would have
introduced exactly what that rule warns about.

Filter row measured at 1366px: all five controls plus Clear Filters and the entry count sit on one
line.
