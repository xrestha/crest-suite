### S766 — 2026-09-16 — An item Used In called unused, that Del would not delete

**Service worker `crest-v314` → `crest-v315` (`APP_VERSION` with it). No migration.**

Reported from a screenshot of Item Master: PANEER's **Used In** read "—", and pressing **Del**
refused it because it "already appears in Closing Stock". Both came from the same scan. The chip
read `usageMap`, which skipped any row whose quantity was not above 0; the delete guard read
`refMap`, which counts every row. Checked on the live database: PANEER's only record was one Closing
Stock row for Bhadra 2083 with `physical_qty = 0`, counted that morning — and since S695 a count of 0
is saved as a real row on purpose ("we counted, there was none"). The chip's `> 0` filter predated
that decision and never caught up. One item of CASA ACAI CAFE's 264 was in that state, but the shape
recurs on every zero count of an item with no other history — which is usually an item being
retired, i.e. exactly the one someone tries to delete. The **Unused** filter read the same map, so it
listed PANEER as unused and then refused to delete it.

S706 had created the split deliberately, for the opposite defect (a zero-quantity staff meal passing
the guard and cascading away), and fixed it by giving the guard its own map. That fixed the delete
and made the screen disagree with itself. The column's own tooltip already said *an item with any of
these can't be deleted*, so the chip, the Used In filters and the guard now read the one `refMap`,
`qtyCol` is gone from `ITEM_REF_TABLES`, and the scan selects `item_id` alone. **Unused now lists
exactly the items that can be deleted.** Vendors' chip had always counted any row.

**The refusal claimed an erasure that would not happen.** It said deleting "would take those records
with it" for every table, but only Staff Meals, Requisitions and Vendor Returns cascade — a count or a
purchase line refuses the delete instead. The message now derives the erased set from
`ITEM_REF_TABLES` and names it only when one applies.

The IMS module guide said "eleven tables" in two places while the list has held twelve since S758
added Customization Options; both now describe the tables without a count, and the guide says how to
retire an item held only by a zero count (blank its cell on Stock Count — a blank removes the row, a
0 keeps it). The Help page's Item Master tips had never explained Used In or the Unused filter at
all, and now do, including that same zero-count step. `.claude/rules/item-master-rates.md` recorded
two maps as the design and now records why there is one, and `component-library.md`'s `UsageChip`
rule — *an absent chip must mean "no records"* — gained this as its second way of being broken.

### S764 — 2026-09-16 — An Android till installed to the home screen would have locked itself upright, and the setup guide still told a new client a bill needs no shift

**Service worker `crest-v312` → `crest-v313` (`APP_VERSION` with it). No migration.**

Both found while answering a question about whether the product runs on a touchscreen POS machine.
The answer is yes — POS is built for one, and S603's `@media (pointer: coarse)` tier reaches IMS, HR,
Customization and Suite at the element level — but two things would have met the first client who
tried it.

**`manifest.json` declared `"orientation": "portrait-primary"`.** A POS machine is landscape. The
value is inert on a Windows till launched from the `--kiosk-printing` shortcut the Help page
documents, because desktop Chrome ignores manifest orientation — which is exactly why this had
never shown up. But an Android POS terminal (Sunmi, iMin, Elo) installed to the home screen runs in
`display: standalone`, where Chrome **does** honour it, and would have locked a bolted-down
landscape screen to portrait with nothing in the app able to override it. Now `"any"`: the device
decides, which is what the owner asked for and what every surface here actually wants — an owner's
phone held upright, a count tablet either way, a till sideways.

**`staff.webmanifest` is deliberately left at `portrait-primary`.** Crest Staff is an employee's own
phone and nothing else; the two manifests having the same value was a coincidence, not a convention.

**`Help.js`'s POS setup step 5 still said "Orders can be billed without an open shift, but they
won't show up in any shift's reconciliation total."** That stopped being true at S754, which made a
fresh open-shift read refuse any Charge or Complimentary close (`PosOrders.jsx`, the `billShiftId`
block). The step now says no shift means no charging, and names Void as the one close that is not
gated.

Worth noting where the drift was and was not: `posGuideData.js` — the Admin → Settings → Guides copy
— was updated in the same session as the behaviour and says it correctly in two places. The Help
page was not. **These are two separate surfaces teaching the same rule, and S754 moved one of
them**, which is the failure mode the module-guide rule exists for, running in the opposite
direction to the usual one.

**Then a sweep of Help.js against all five `*GuideData.js` files, which found five more.** The method
that worked: the guides carry `(S754)` / `(S756)` markers recording *when* each rule changed, and
Help.js carries none — so every marker is a claim to check against the other surface. 47 S754
markers in `posGuideData.js`, 27 S756 markers in `imsGuideData.js`.

**All five misses were in the small arrays at the bottom of the file** — `POS_SETUP_STEPS`,
`POS_MISTAKES`, `FAQS` — never in the big `tips` arrays, which S754 and S761 had both swept
correctly (Shifts, Order Taking, Sales Exceptions and the count-PIN block all read right). **The
tips are where you look when you update a page; the steps, mistakes and FAQ are prose about the
product that nothing points at from the code you are editing.** That is the shape to grep next time,
not the module.

- **`POS_MISTAKES`: the same stale shift claim**, "orders billed with no shift open never show up in
  any reconciliation" — describing a state S754 made unreachable. Rewritten as the mistake that
  actually happens now: service starts, nobody opened the shift, the first guest cannot be charged.
- **`POS_MISTAKES` and a FAQ both described a failure mode that cannot occur.** "An item in a

- **A count PIN was described as "a 4-digit PIN"** in the Stock Count delegation block, the only

### S763 — 2026-09-16 — A guest ordered from their phone and the app told nobody, because the alert lived on a page instead of in the app

**Service worker `crest-v306` → `crest-v312` (`APP_VERSION` with it). No migration.**

Reported from the IMS module: a test order came in from the guest QR menu and there was no
notification anywhere — no sound, nothing on screen. The code was working exactly as written.
`loadPendingGuestOrders` lives inside `PosOrders.jsx` and polls only while `view` is `'floor'` or
`'order'`, so on any other page it is not merely quiet, it is **not mounted**. The banner, the
per-table 🔔 chip and the chime were all correct and all on a screen nobody was looking at.

S686 had already learned this once — a booking request that showed only on the Reservations page
"was reported as no notification by an owner sitting on the IMS dashboard" — and the answer then
was a dot on the POS rail icon. A dot is the right weight for a booking next Tuesday. It is not the
right weight for food a guest is waiting for.

**The alert is now in the shell, and it is loud.** `useGuestOrderAlerts` polls
`pos_guest_order_requests` every 15 s from `Layout.js` for anyone with POS visible, on every page;
`ArrivalAlert` is a fixed banner above everything with the table name, how long it has waited and an
**Open Orders** button; `playGuestAlert` sounds three rising notes twice at roughly double the old
gain, **and keeps sounding every 20 s until someone deals with it**. Past three minutes it escalates
— red, a harder timbre, a third round.

**The Kitchen Display got the same treatment**, for its own event: **any** ticket sitting in New
raises the banner and the repeating alert, and it clears the moment someone presses Start. It
hardens past the 8-minute warn mark and again past the 15-minute late mark — **the two thresholds
the card strip and the ▲/△ marks already use**, so the banner cannot disagree with the board
underneath it, and the elapsed figure rounds the way the card's own label rounds for the same
reason.

**That trigger was revised inside the session, and the revision is the more interesting half.** The
first build fired only past the 8-minute mark, on the reasoning that a kitchen working through a
queue always has tickets in New and a banner up all service gets muted on the first night and never
unmuted. That reasoning is still true. But Aashish sent a real ticket through, went to look for the
alert, and found a board with a ticket on it and nothing saying so — which is the same experience
that opened this session, one screen along. **A threshold chosen to avoid annoying the reader is
still a period in which the product says nothing**, and the owner's call was that a kitchen which
has not yet touched a ticket is exactly the state worth shouting about. The cost — a banner a busy
kitchen sees a lot of — was taken knowingly, with Mute as the release valve.

Decisions worth keeping:

- **Mute silences the sound and leaves the banner up.** A control that makes the evidence disappear
  is how this gets missed a second time. Five minutes, and it says `Muted` rather than going blank.
- **Two routes suppress the shell banner.** `/pos/orders` already answers it better (floor banner,
  per-table chip, its own chime). `/pos/kds` because the kitchen cannot Accept a guest order at all
  — and a kitchen-team login cannot even reach Orders (`KITCHEN_TEAM_ALLOWED_PATHS`), so the button
  would be a dead end. That board raises its own alert for the thing the kitchen CAN act on.
- **Not a `Modal`.** A cashier mid-bill and a chef mid-service both have something in their hands;
  an alert that steals focus or blocks the screen is worse than the miss it prevents. It is
  `role="alert"`, the page behind it stays fully usable.
- **The banner reserves its own height rather than covering the nav.** `ArrivalAlert` publishes its
  MEASURED height as `--arrival-alert-h` (a `ResizeObserver`, because the height changes when the
  TEXT changes and no window event reports that); `.layout-root` pads by it. `.app-topnav` stays at
  `top: 0` — a sticky offset is measured from the scrollport's content box, i.e. already inside that
  padding, so repeating the variable there double-counts it. That was measured, not reasoned: it
  left a 62px gap.
- **The pulse is a class, not an inline `animation`.** An inline animation is unreachable from
  `prefers-reduced-motion`, the rule this product has already broken twice. Under reduced motion the
  urgent fill stays at the loud end rather than reverting to the quiet one.

**One real bug found on the way, and it was silencing every screen in POS that makes a sound.**
Every chime in this product built a **new `AudioContext` per call and never closed one**. Chrome caps
a document at about six, so on any screen opened once and left running the seventh event of a service
made **no sound at all**, silently. Four call sites, and the comment at the top of `posChime.js` had
already looked straight at three of them and waved them through — *"each is on a live service screen
and none of them is wrong"*:

| where | what went quiet |
| --- | --- |
| Kitchen Display | the 7th ticket of the night, on the screen furthest from anyone who would notice |
| POS floor | the 7th guest order of the night, on the screen this whole session is about |
| Reservations | the 7th booking request, on a page a host stand leaves open all day |
| Guest menu | a guest's own phone — Placed → Confirmed → Sent → Preparing → Ready is five of the six |

`getCtx()` keeps one module-level context and `resume()`s it, since a context created before a user
gesture starts suspended and a tab left alone can have one suspended under it. **All four callers are
now in `posChime.js`** — the two inline copies became one-line delegates with identical tones and
timings, so nothing about how any of them SOUNDS changed. Measured live: 9 oscillators in a
24-second window and **0 contexts created**.

Verified live on BHATTI CHOILA, both halves, against real data. **Guest order:** the banner appears
on Item Master in IMS, red and escalated at 46 minutes waiting, with the top bar sitting exactly at
its lower edge (banner 0→66px, nav top 66px); absent on `/pos/orders`, where the floor's own banner

  and amount could all be edited or deleted over the REST API from a till login, a Staff-rank waiter's PIN included.
- **Only a Supervisor or above can close a bill**, and the database now records who closed it and
  when from the server, not from the tablet's clock.
- **A bill line's price comes from the menu.** A tablet cannot send its own price. A dish already
  on an order keeps the price it was ordered at if the menu changes mid-meal.
- **Menu prices, VAT and "On POS" are a manager's.** Only a POS manager, an IMS manager or the
  Owner can change them. A dish a Supervisor creates in Recipe Costing arrives OFF the till until a
  manager puts it on from Menu Pricing, where its price is on screen.
- **Credit Notes are manager-only**, and issuing one now asks how the money went back. Cash is
  recorded as a refund out of the open shift's drawer. The note also takes back the loyalty points
  the bill earned and returns any points spent on it.
- **Every tablet gets its own key.** POS Setup lists the activated tablets, when each was last
  used, and a Revoke button for a lost or sold one. Tablets activated before this keep working on
  the old shared key until a manager switches it off in POS Setup.
- **A POS manager has limits on POS Staff.** They cannot change their own login or another
  manager's, cannot make anyone a manager (only the Owner can), and cannot give a discount limit or
  Void permission bigger than their own.

**Owner decisions (Aashish, 2026-09-14), each with its reason:**
- **Update Order asks whether to send the new items to the kitchen now.** Pressing Update and
  forgetting KOT/BOT was how food got added to a bill and never cooked.
- **Taking payment needs an open shift** (Charge and Complimentary; a Void does not), so every bill
  lands on a drawer count. **This changes BHATTI CHOILA's routine:** all 18 of their recent bills
  were charged with no shift open.
- **Closing a shift over open tables warns and lets it close.** Those bills land on whichever shift
  is open when they are charged. This replaces the old "closing is blocked" rule.
- **Tapping Served clears Ready** on the floor and takes the ticket off the Kitchen Display. There
  is a new `served` ticket stage.
- **Sales Exceptions values everything before VAT.** VAT on a sale that never happened was never
  revenue, and counting it made a void look about 13% bigger than a discount on the same food.
- **Sales Report spreads a split bill across the methods it was paid with**, so Payment Summary's
  Cash ties to the shift Z-report.
- **A return is a minus row on the day the Credit Note was issued**, on every tab. The original
  bill stays at full value on its own day. This replaces the S580 rule that left a credit-noted bill
  out of Daily and counted it only as returned quantity.
- **Covers Report counts dine-in only.** Takeaway and delivery get their own line. Credit-noted
  bills are kept, because a credit note corrects the bill, not the fact that guests sat down.
- **The 1L+ tab merges a name-only bill into the same-name PAN party.** The walk-in row is no
  longer flagged "Missing PAN".
- **Parking slips roll over at 6 AM Nepal time**, so a car parked during a late service is still
  on the Open tab after midnight.
- **The Kitchen Display strikes through a pulled or reduced line** on the ticket that sent it,
  with the word "cancelled", so the kitchen stops cooking it.
- **Recent Bills (reprints and the Credit Note entry) is Supervisor+.**
- **Menu Pricing opens for a POS manager, an IMS manager or the Owner**, by URL as well as by nav,
  on any client.
- **An offline order that conflicts offers "Start new order with these"**, so the items come back
  as unsent lines on a new order instead of being lost.
- **Two bookings may not hold the same table at overlapping times.** This is checked on screen
  only: two saves in the same second can still both land (see Still open).
- **The public booking page counts accepted bookings only** towards "Full". An unanswered request
  no longer blocks a slot.
- **A guest QR order with a dish that went off the menu is refused whole**, naming the dish.
- **Priorities for the next builds, in the owner's order:** table move / merge / split, add-ons
  and sizes, then kitchen and bar printers. Service charge was not chosen.

**The database changes (for engineers).**
- **`20260916100000` — bill integrity.**
  - `guard_pos_order_close()` became the closed-bill lock: an allow-list of eight columns
    (`ims_posted_at`, the two print counters, `credit_note_id`, the four credit-settlement
    columns). A credit-note link needs manager rank and is set once. A settlement needs supervisor
    rank, is set once, and gets `credit_settled_by := auth.uid()`. The close itself needs
    supervisor and stamps `closed_by`/`closed_at`.
  - `guard_pos_order_insert` refuses an order created already closed.
  - `guard_pos_order_delete` refuses deleting a closed bill.
  - `pos_orders_one_open_per_table` is a unique index: one open order per table.
  - Statement-level guards lock the lines and payments of a closed bill.
  - `guard_pos_item_price` lets price, quantity and identity be written only inside
    `save_pos_order_items`.
  - The one payment insert admitted on a closed bill: a Split leg, by the closer, within 10 minutes
    of `closed_at`, never past `paid_amount`.
  - `save_pos_order_items(p_order_id, p_rows, p_removal_reason, p_expected_version)`: open orders
    only, NEW lines priced from `recipes`, and `items_version` for optimistic locking (`stale_order`
    → "changed on another device — here's the latest"). It also stores `sent_qty`. The 3-argument
    signature was dropped.
  - `guard_recipe_menu_price` and `caller_can_set_menu_price()` cover the menu-price rule.
  - `guard_pos_credit_note`: manager-only, `issued_by` stamped, never edited or deleted.
  - `apply_pos_item_comps` and `redeem_loyalty_points` require an open order.
  - `award_loyalty_points` is limited to the closer within the window (Owner/admin later).
  - New `reverse_loyalty_for_credit_note()`.
  - `log_audit` skips a write that only bumps `items_version`.
  - Every guard exempts the operator's restore writes by name.
- **`20260916110000` — rank guards.**
  - `pos_caller_has_rank()` is the one POS rank test, with every operand COALESCE'd.
  - Shifts: supervisor to open or close, and a closed shift is immutable.
  - Cash movements: supervisor to record, never edited or deleted. A new `refund` kind is
    manager-only and linked to a credit note, one per note.
  - `settings`: the till-setup columns need a POS manager. Invoice prefix, VAT number and flag,
    property address and phone, and the payment QR need the Owner.
  - `pos_tables`: anything but `status` needs a manager, and a table under an open bill cannot be
    deleted.
  - Loyalty schemes and enrolment need a manager.
  - **`get_pos_device_secret` fell open for IMS, HR and Self-Service logins** and is COALESCE'd now.
  - Settlement-blocked logins leave the PIN picker.
  - `submit_guest_order` returns machine codes on every refusal.
  - `pos_kot_log.served_at` added.
  - `reservation_hour_load` counts accepted bookings only.
- **`20260916120000` — device keys.**
  - `pos_devices` holds one row per tablet, storing a SHA-256 hash only, with no client grants.
  - `register_pos_device` returns the secret once. `list_pos_devices`, `revoke_pos_device` and
    `get_pos_device_staff` go with it.
  - `verify_pos_device` / `verify_pos_legacy_device` are service-role only.
  - `retire_pos_legacy_device_key` rotates the shared key so nothing still matches it.
  - Not exported and not restored: a backup must not bring a device credential back to life.
- **`admin-user-ops`.**
  - `requireManageableTarget` now runs on POS role changes, deletes and PIN resets.
  - Manager grants are Owner/admin only.
  - `refusePosPowerEscalation` caps the discount limit and Void permission at the caller's own.
  - A login a capped manager creates starts at the creator's cap, not at unlimited.
- **`pos-staff-login`** verifies a per-device key or the legacy key. It fails closed with 503 on
  a read error, so a transient blip is not reported as "re-activate this till".
