### S760 — 2026-09-15 — Build-your-own dishes: a size scales the toppings, the guest menu walks the dish step by step, and Recipe Costing shows what a bowl really costs

**Service worker `crest-v303` → `crest-v304` (`APP_VERSION` with it). Migration
`20260920100000_customization_build_your_own_s760.sql` applied live 2026-09-15.** Before applying,
the four functions it re-creates (`save_pos_order_items`, `pos_price_selection`,
`get_guest_menu_options`, `guard_pos_option_edit`) were read back with `pg_get_functiondef` and
matched their S758 source line for line, so rebuilding from the files reverted nothing. A dry run
(`BEGIN` + the file + a final RAISE) reached the end with every verification step passing and left no
column behind; the real apply then ran clean.

**Where it came from.** Aashish's handwritten sketch: menu options Acai Bowl, Pizza, Salads; serving
size Small / Medium / Large → base (as per dish) → sauces → toppings → checkout; and "a new category in
Recipe Costing" for these dishes. Most of it already existed in S758/S759 (a dish offers its own groups,
so "base as per dish" is a group attached to one dish). What did not: a way to mark the dish, a size that
changes what the toppings cost and use, a step-by-step flow, and an honest food cost. Four owner
decisions settled those — a mark not a category, a portion factor per size, steps on the guest menu
only, a cost range. A packaged "Customization product" of POS + IMS was discussed and dropped.

**The mark.** `recipes.is_build_your_own`. A category would have moved an acai bowl out of Food on
KOT/BOT routing, the product code prefix and every category split. Set from the Recipe Costing form (a
"Build-your-own" tick under Category, which also lets the dish save with no fixed ingredients), from
Option Groups → Dishes (⋯ → Mark as build-your-own), or by the template. Recipe Costing gains a
Build-your-own tab and badge; a newly marked dish says "Set up choices →".

**Size scaling.** `pos_options.portion_factor` (size options only, guarded) and
`pos_option_groups.size_scaling` (`none` / `stock` / `stock_and_price`, never on a size group). One
rule in the till RPC, the guest pricer and `optionPricing.js`: a Large at 1.5× makes a 30 g topping 45 g
and a +50 topping +75, a free pick stays free, a size's own lines never scale. The scaled quantity is
frozen into `ingredient_deltas`, so no IMS reader changed. The option dialog has a Portion field; the
group dialog "When a bigger size is picked".

**The template.** Option Groups → Build-your-own template: pick a dish, and
`create_build_your_own_template` creates "<dish> · Size / Base / Sauces / Toppings" (S/M/L at
0.75/1/1.5, base pick 1 scaling stock, sauces up to 2 scaling stock, toppings any scaling stock and
price), attaches them in order and marks the dish — one SECURITY INVOKER transaction, refused by name
if the groups exist.

**The till and the guest menu.** A marked dish always opens the choice window (the S759 one-tap default
is for ordinary dishes), and every chip price reads at the size picked so far. On the QR menu a marked
dish is a stepper: size first, one group per step with a progress bar, Next that says what is short,
Skip on an empty optional step, and a Review step listing each group with Change before Add to order.
Editing a line opens on Review.

**The cost range.** `src/shared/buildCost.js` (pure, tested on the worked example: a Large bowl with
peanut butter and chicken popcorn bills NPR 820; the range runs NPR 128 – 296) and
`useBuildCostRanges`. Per size, the cheapest build (required picks at their lowest price) and the
typical build (the most-picked selection over 30 days once 10 plates exist, else the pre-selected
choices, labelled), valued through `deltaItems` at today's rates. Recipe Costing and Menu Pricing (IMS
branch) show "NPR low – high" and the FC % range with the worst band's mark; a disclosure opens the
per-size table. A failed read shows "not checked", never the fixed-ingredient figure.

**Deploy order.** No page's own query names a new column: the mark comes through the catalog loader,
whose group/option reads fall back to the S758 lists on a missing column and whose mark read returns
none. The admin dialogs write the new columns only when changed. So the bundle can go first; setting a
portion, a scaling or a mark needs the migration.

**Guides.** Admin → Settings → Guides: the Customization tab gained build-your-own and size
scaling across its Overview, Setup, Service and Report sections; the IMS tab gained them on Recipe
Costing (the tick, the tab, the range formula, the “not checked” state) and Menu Pricing (the IMS
branch only, and why New FC % stays blank); the POS tab points at the new behaviour from Orders and
the Guest Menu. Help → Crest Customization carries the same three additions.

**Verified here.** `npm run build:verify` clean; 65 suites / 821 tests passed, including 6 new
`optionPricing` tests pinned to the migration's own numbers and 6 `buildCost` tests. Live, after the
apply: the three columns and three constraints exist; `create_build_your_own_template` and
`pos_selection_portion_factor` are callable by `authenticated` and not `anon`;
`pos_price_selection` by neither; `get_guest_menu_options` still by `anon`; the migration's own
rolled-back checks (a Large bowl at NPR 495 on both pricers, cheese 45 g, honey 15 g at an unchanged
price, the three refusals, the template and its duplicate refusal) passed inside the apply; no
