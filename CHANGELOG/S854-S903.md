### S860 — 2026-10-23 — Supabase stops auto-granting new public tables on 2026-10-30: the live grants written down so a rebuild works

No service-worker bump (no JS or CSS change). Migration `20261023120000_mirror_live_grants_s860`, applied live. No Edge
Function deploy.

Supabase's notice: from 2026-10-30, a table created in `public` gets no Data API grants unless its migration grants
them, and that includes a schema rebuilt from migration files (a new project, a preview branch, `supabase db reset`).
Existing tables keep their grants, so the live project is unaffected, and new tables were already covered: every
recent migration revokes and then grants explicitly (`apply-migration`). The gap was the files. The 52 tables in
`20260705074838_baseline_schema.sql` and `monthly_owner_reports` (`20260721010000`) were created with no GRANT at
all, so a rebuild after 2026-10-30 would start them locked and every page would read "permission denied".

- **`20261023120000_mirror_live_grants_s860.sql`** lists every grant `anon`, `authenticated` and `service_role` hold on
  a public table, view or sequence, read from the live catalog on 2026-10-23 (`aclexplode` over `pg_class.relacl`:
  233 grants on 122 objects; `PUBLIC` holds none), and grants each one again. It never revokes, skips with a NOTICE
  an object a rebuild lacks (S753: a rebuild comes out usable, not identical), and reads each privilege back with
  `has_table_privilege` / `has_sequence_privilege`, raising if any did not take. `anon` holds exactly one grant,
  SELECT on `settings` (the pre-login `app_name` read). `app_secrets` grants `authenticated` full DML; checked live
  that RLS is on and its only policy is `is_admin()`, so it was copied as it stands.
- **`apply-migration` SKILL.md** step 3 now names `service_role` (Edge Functions; not a superuser here) beside
  `authenticated`, says never to grant `anon` unless a table is public by design, and records the 2026-10-30 change,
  rebuilds included.

Verified: the live grant set read again after applying is identical to the pre-apply snapshot (233 = 233, nothing
added or removed), and the file's own read-back did not raise. Not dry-run first, because the apply-migration rule
forbids a linked query in the turn that writes the file and no local database was running; the DO block is atomic, so
a failed check keeps nothing.
