### S680 — 2026-09-05 — the Reservations audit: a size class that did nothing, and a tooltip that cost every action two Tab presses

**Service worker `crest-v192` → `crest-v193`. No migration, no Edge Function deploy.**

`/impeccable audit` on the Reservations page (`PosReservations.jsx`, `ReservationModal.jsx`,
`SeatTableModal.jsx`) scored **17/20** — zero detector findings on all three files, every colour a
token, every read guarded, the shell classes worn correctly — and every finding that survived was
shared infrastructure the page had inherited rather than anything it did itself. Each was fixed at
the layer it lives on, so the page-local edits are the smallest part of this entry. Code-level only:
no dev server was running, so nothing here was measured in a live browser.

**`.btn-sm` had no base rule.** The only selector in the product mentioning it was the
coarse-pointer `min-height: 32px`, so on every mouse device `btn btn-sm` rendered identically to
`btn` — 13px on 8/16 padding — across 24 sites in 8 files that all believed they were rendering
something smaller. DESIGN.md had described the class as "real" since S678's `.btn`-without-a-variant
rule, which is the same failure one step over: CSS raises no error for a class that does not exist,
and the pair `btn btn-sm` reads complete. It now has one (12px, `5px 10px`, `gap: 4px`, the
`.tab-btn` footprint), and the coarse floor is unchanged. Every Reservations row action, the
day-nav arrows, Legal's nav links, Loyalty's Delete and Table Management's booking controls all
shrink with it, which is what they were written to do.

**`Tip` wrapped around a button was two tab stops, and the wrong one carried the description.** The
component renders a `tabIndex=0` span with `aria-describedby` on the span; around a `<button>` that
is the span, then the button — so a Reservations row with four tipped actions took eight Tab presses
to cross, and a screen reader focused on the actual button never heard the tip. About 60 sites
product-wide. `Tip` now detects a single native interactive child (`button`/`a`/`input`/`select`/
`textarea`/`summary`), adds no tab stop of its own, clones `aria-describedby` and composed
`onFocus`/`onBlur` onto the child, and drops the dashed underline and `help` cursor for that case —
which `Roster.jsx` had already been doing by hand with `style={{ borderBottom: 'none' }}`, the tell
that the default was wrong for buttons. Hover still works on a disabled child, which cannot take
focus at all. A custom component child (react-router's `Link`) is not detectable and keeps the old
behaviour.

**A pressed button that disables itself drops keyboard focus to `<body>`.** Every row action set
`disabled={busyId != null}`, so the button a keyboard user had just pressed vanished from the tab
order and, when the write landed, they restarted from the top of the page. The busy row's buttons
now stay enabled and wear `aria-busy` (`.btn[aria-busy="true"]`: disabled's opacity plus
`cursor: progress`), `transition()` ignores a second press while one is in flight, and other rows'
buttons are disabled as before so only one write can be in flight.

**Page-local, all small.** `Loading…` carries `role="status"` (the shape `LoyaltyTab` already had);
the three filter tabs carry `aria-pressed` and `type="button"`; both tables' empty action header
gets a visually-hidden "Actions"; the table chips in the booking form show their seat count on the
chip instead of only in a hover-only `title` (the host picking tables for a party of eight on a
tablet has no hover — `SeatTableModal` already did this); gaps of 6/10/14/18 move onto the 4/8/16
scale; the seat modal's section eyebrow takes the `data-table th` eyebrow's values instead of its
own weight and a unitless `letterSpacing: 0.4` (= 0.4px); and the capacity strip's 9px denominator
comes up to the 10px floor.

**Left as found, deliberately.** The 7-column table scrolls horizontally on a phone inside
`.table-wrap` — the Guest column absorbs the squeeze and that is the product's table convention.
The `.impeccable/design.json` sidecar was not regenerated: no token value moved, and `.btn-sm` is a
class, not a token. Re-run `/impeccable audit` on the page to see the score move.
58 suites / 647 tests — one of them the `appVersion` parity test, which failed exactly as designed until `APP_VERSION` was bumped with the cache name.

### S676 — 2026-09-04 — the acceptance ledger stops writing its dates in an order Nepal reads backwards

**Service worker `crest-v188` → `crest-v189`. No migration.**

Both Legal tabs (Admin → Clients → Manage → Legal, and the client's Help → Legal) rendered the
acceptance date through `nepalDateAd`, which is `en-US` — so yesterday's acceptances showed as
`09/04/2026`. S670 kept that order deliberately for the printed bill, and its comment says so:
Nepal writes DD/MM/YYYY, and flipping a Tax Invoice's date format is "not one to make silently".
That reasoning does not carry to a surface built two days later, where the cell is not a print
habit but the fact on record — a reader who writes DD/MM takes `09/04/2026` as 9 April, and on an
acceptance ledger a misread date is a misread contract.

`nepalDateLong()` is the new formatter — `4 September 2026`, day first, month **named** — and it
is the form the legal registry's own `effectiveAdLabel` already used on the same panel, so the two
dates there finally agree. `month: 'long'` rather than short on purpose: current ICU gives en-GB's
short September as "Sept", which reads as a typo in a legal record. `nepalDateAd` is untouched and
the bills print exactly as before; the test asserts both forms against the same instant so the
distinction is on record. 52 suites / 618 tests.

### S675 — 2026-09-04 — every tenant Owner was locked out of the product by a filter that matched nothing

**Service worker `crest-v187` → `crest-v188`. No migration, no Edge Function deploy.**
**This was a live, total lockout of every client Owner, and accepting could not clear it.**

`AuthContext.js` read the acceptance ledger with
`.in('doc_type', docsRequiringReacceptance())` — but that helper returns document **objects**.
PostgREST stringifies whatever it is handed, so the filter was on the literal text
`[object Object]`, matched no rows, and returned `{ data: [], error: null }`. That is a *successful*
read stating the client has accepted nothing. The memo therefore held every Owner at the blocking
gate, and the acceptance they submitted was written correctly and then never seen by the re-read.

**Both of the safeguards built for exactly this screen were bypassed, and for the same reason.** The
read fails OPEN on error — but `legalErr` was null, so that branch was never reached. And S672 had
already been bitten by the objects-versus-strings distinction in the *other* direction, documented
at length in `legal-documents.md` with the same predicted symptom ("held at the blocking screen
permanently, with no way out except Sign Out"). `reacceptGuard.test.js` was written to catch it and
tests the helper, which was correct both times. **The fault was at the call site, which passed the
wrong one of two correct functions — so a test of the helper passes happily while the product is
shut.**

The fix is structural rather than a corrected argument: `reacceptDocTypes()` now exists beside
`docsRequiringReacceptance()`, and the rule is that anything comparing against the `doc_type`
COLUMN calls the former while anything reading a version or hash calls the latter — neither caller
does the `.map` itself. Two new tests read the **source** and fail if any `.in('doc_type', …)` in
`src/` is given anything but a types-shaped value; both were verified against the exact string that
shipped rather than assumed to work.

Found by shipping S674's recovery message first, which is the only reason the state was
diagnosable: the gate said "your acceptance was recorded but this screen did not refresh", which
distinguished a failed write from a failed read. 52 suites / 614 tests.
