### S729 — 2026-09-10 — IMS Staff re-analysed: any waiter could read every IMS login's email, and a manager could lock a peer out in two requests

**Migration `20260910120000_staff_list_rpcs_manager_only.sql` must be applied by hand in the SQL
Editor, and `admin-user-ops` must be redeployed** (`supabase functions deploy admin-user-ops`).
App code changed. `CACHE_NAME` and `APP_VERSION` both bumped to `crest-v265`.

A re-analysis of `ImsStaff.jsx`, its two RPCs and its four `admin-user-ops` actions, read against
`HrStaff.jsx` — the file that was mirrored FROM this one at S430 and then swept in S628 while the
original was not. About twenty findings; the four on the server are the ones that matter.

**`get_ims_staff_list` handed every IMS login's real sign-in email to any authenticated account
of the client.** It gated on `caller_role = 'admin' OR caller_client_id = p_client_id` and nothing
else — the exact shape the 2026-08-10 security review closed on `get_ims_eligible_users`, one file
over. That fix removed the pair that disclosed the **Owner's** email and left the pair that
discloses every **staff** email: a POS PIN waiter or an HR Self-Service employee, whose own
profile row tells them their `client_id`, could call it and read the id, full name, `/login`
email, rank and last-seen of every IMS login. The page redirects an under-ranked visitor, but its
`useEffect` had already fired the RPC before the redirect rendered — **a page guard is a guard on
the page, never on the data.** `get_hr_role_staff_list` was byte-identical. Both now require
admin, the Owner, or a manager of that module: exactly the set `admin-user-ops` lets act on the
result, so nobody lost a capability they had a page for.

**"Managers can only be deleted by admin" was two requests long.** `delete_ims_staff` refused a
manager target; `update_ims_role` had no rank check on its target at all, so an IMS manager could
set a peer manager to "— No Access —" — locking them out of every IMS page — and then delete the
now-staff account. `reset_ims_password` had the same gap, which is worse than a lockout: a manager
could set a peer's password and sign in as them. And nothing anywhere stopped a manager setting
their **own** row to No Access, after which only the Owner could restore them. One helper,
`requireManageableTarget()`, now sits behind role change, delete and password reset for IMS and
HR both: a manager never acts on a peer manager or on their own row (own password excepted).
**The Owner is exempt alongside admin, which is a change** — the old "admin only" delete rule had
never actually kept a manager from an Owner who could clear the role first, so the rule people
believed was in force is the one that now is. The page disables the select and hides Delete on
the caller's own row, marked "(you)"; the server is where it is enforced.

**"Existing User" mode could convert a client's only Owner login into staff.** The Owner is the
absence of staff markers, the eligible list is the set of marker-less logins, and an admin sees
the Owner in it — so one assignment demoted the only account that could reach the Suite features,
manage a manager, or use that mode again. `isLastOwnerLogin()` refuses to convert the last plain
login, on both the IMS and HR actions, and a failed count counts as "last".

**The Help page told the Owner to demote themselves.** Its first tip read *"Start by assigning
your own account the Manager role first if you plan to hand day-to-day IMS Staff management to
someone else"* — the precise trap `accounts-and-logins.md` warns about in bold — and the module
guide called Manager "full Owner-equivalent access", which it never was (no HR, no POS, no Suite,
no Existing User mode, and now no peer managers). Both rewritten; the guide's tier lists gained
the pages added since S419 (Stock Ageing, Fixed Assets, Vendor Balance Confirmation, Supplier
Contribution).

**Adding the first custom role blanked every existing login's role.** The scheme is "custom roles
if any, else the three defaults", so a first custom role of *Store Keeper* replaced Staff /
Supervisor / Manager in every dropdown while every existing login still carried one of those
titles: each row's `<select>` had no option matching its value and rendered **blank beside an
Access Level badge that still said Supervisor**. Remove and Reset to defaults did the same. The
first custom role now seeds from the defaults; a role that logins still hold cannot be removed
(the holders are named); Reset refuses while anyone holds a custom title; and a title that has
somehow fallen out of the scheme renders as its own option with an amber orphan mark. The old
fallback — show the *first* role that shares the login's level — is gone too: with two custom
roles at Staff level it named a role the login had never been given.

**The role auto-fix wrote privilege changes off a dropped read, and dropped its own failures.**
`init()` read `settings` with `.single()` (the S613 trap this file's own `saveRoles` comment
describes), discarded the error, fell back to the DEFAULT scheme, and then invoked
`update_ims_role` for every login whose level did not match — sequentially, after the page had
painted, with each result's error ignored. `.maybeSingle()`; a failed staff or settings read now
stops the page below an `ActionError` rather than rendering "No staff yet. Click + Add Staff"
(S594); the auto-fix runs in parallel and names every row it could not correct. That last part
matters now for a new reason: a peer manager's row is *refused* for a manager caller, and the
refusal should be visible rather than one badge quietly staying wrong.

**Passwords accepted "password".** `passwordValid` was a hardcoded `length >= 8` — the same
literal `ClientDrawer.js` was caught hardcoding at 6 — with no `weakPasswordReason()`, on the one
page that mints real `/login` credentials. Creation and reset now take the product's one policy
(`MIN_PASSWORD_LENGTH`, the common-password list, and nothing built from the business name or the
email), the same check Signup and Reset Password apply; the placeholders read the constant.

Also on the page: no `loadedClientRef`, so an admin switching client let the slower load paint the
previous client's names and emails under the new header and run the auto-fix off that list —
the sixth instance of S721; `load()` after a delete did `setStaff(data || [])`, so a failed re-read
emptied the table, which reads as "you just deleted everyone" (last good list kept, refresh
failure named); `updateCustomRoleLevel` dropped per-row failures (HrStaff had reported them since
S628); the search filter was written out twice; `addCustomRole` silently no-op'd on a duplicate
name and cleared the box before the save resolved; five inputs carried an inline style object
instead of `.form-input` (S603 — no `:disabled`, no `[aria-invalid]`, no touch floor); the row
selects shared one `aria-label`; the Add tabs had no `aria-pressed`; and a completed add, delete
or reset left no evidence but a closed dialog — each now says what happened. `HrStaff.jsx` and
`PosStaff.jsx` still carry the orphan-role, `loadedClientRef` and (HR) password-policy shapes.

**Recorded, not fixed.** Every write on this page goes through the service role, so the
`audit_logs` row on `profiles` has **no actor** — `log_audit()` reads `auth.uid()`, null under the
service role; a role grant is recorded as having happened but not by whom, on all three staff
pages. `create_ims_staff` does not check `ims_enabled`. An IMS manager can still *create* a login
at manager rank and *promote* a supervisor to it — only demote, delete and reset are Owner-only —
which is a product decision rather than a defect. Last Seen is an AD date on a BS product,

### S728 — 2026-09-10 — The rest of the vendor-report re-analysis: a "Stable" band that hid a 20% rise on rice

**No migration, no Edge Function deploy.** App code changed. `CACHE_NAME` and `APP_VERSION` both
bumped to `crest-v264`. This closes the 24 findings S727 recorded rather than fixed.

**Price Tracker called a 20% price rise "Stable" on the cheapest things a kitchen buys.** The band
was `Math.abs(last - prev) < 0.01` on a PER-BASE-UNIT rate, so its real threshold was `0.01 / prev`
— a continuum, not a constant. At NPR 250/BTL that is 0.004% and harmless; at NPR 0.05/GM for rice
by the sack it is **20%**, and "↑ Rising Only" hid every one of them. Now a percentage with a tiny
absolute floor, whichever is more forgiving (S644).

**A free line is not a price.** `lineState()` has accepted rate 0 as free goods since S698, and
this page read every one as a price observation: a gift crate rendered **"↓ Down −100%" in green**,
printed Last Rate 0.0000, and switched OFF the >5% master-rate ⚠ on the very item whose rate had
just diverged most — then the next real purchase read as a rise from zero. `priced()` is the one
filter, applied at the five sites that pick a "last" or a "previous". The rows stay in the expanded
history: a free receipt is a real event, it is simply not a price point.

**The `items` read was unpaged while the `purchase_entries` read it GATES was carefully paged**,
under a comment about the very cap it was missing. `itemMap` decides which purchase rows survive,
so this does not shorten a column — past 1000 SKUs it deletes the entire price history of every
item after the cut, from the table, both sheets and the vendor dropdown's count. The
producer/consumer shape from S706/S708 with the halves reversed. Same read on Supplier Contribution.

**The expanded history row emitted 13 cells against a 12-column header**, so every figure in it sat
one column right of its own heading — the rate under "Last Period", the quantity under "Trend", the
change under "Purchases". `colSpan={2}` had already covered Master Rate and Update Rate before the
`no-print` cell added a third.

Also on that page: no `loadedClientRef`, so an admin client switch let the slower, older client's
whole purchase history paint over the new one's; the inline editor was keyed by item id while rows
are keyed `vendor__item`, so one Edit click opened **two** boxes with `autoFocus` landing in the
wrong one; the workbook quoted a per-PACK rate beside a BASE-unit quantity with the pack size
printed nowhere, so `Rate × Qty` was wrong by the conversion factor; the Master Rate tooltip named
a "Gold ⚠" that renders in the accent (oxblood on Modernist Light); and Help promised an
auto-sync that has never existed. The page now also says what a price rise **costs** — rupees on
the latest delivery, beside the count of rising items.

**Vendor Report's KPI strip, split chart and Export button were gated on `loadError` but never on
`loading`.** First paint printed a gold "Gross Purchases NPR 0 / Net Spend NPR 0" above a card
reading "Loading…", every period change held the previous month's money under the new month's chip,
and — the serious half — Export stayed live throughout, building the workbook from the stale index
while `scopeLine` and the filename already read the NEW period. One month's figures inside another
month's workbook, which is the S601 rule verbatim.

**The Daily Breakdown matrix rendered one population in its columns and a different one in its
totals.** Columns were vendors with at least one PURCHASE; "Day Net Total" and the TOTAL row summed
every row in the period, returns-only vendors and unassigned bills included — so the cells could not
be added across to the total beside them. Columns now cover purchases OR returns, Unassigned has its
own column on screen and in the sheet, and the totals follow what is rendered, with the period's own
figure stated underneath when a search narrows it.

**"Transactions" counted line items** while the drilldown one click away counts bills and says so —
a 12-bill vendor with 8 lines a bill read as 96. It is "Bills" now, off the same grouping key the
drilldown uses, with Line Items kept as its own column in the export.

The drilldown — the page's main interaction — was **mouse-only at five sites**: bare `onClick` on
spans, `td`s and a `tr`, no tab stop, no Enter, nothing for a screen reader. All five are real
controls now, on `.btn-linklike`, with the row-level one moved onto the day cell rather than putting
a button role on a `<tr>` (S595/S653). Two coloured sub-marks moved to `.cell-sub`, which carries
the print override that stops a span inside a cell printing pale on white. And `categories(name)`
— fetched on every purchase line since the page was written and referenced nowhere outside the
SELECT — now appears under the item name in the drilldown.

**Supplier Contribution's `init()` never claimed the page** (S721, the fifth instance, fixed on
Vendor Report in S725 and left on its sibling): an admin client switch re-runs it with the previous
client's period id in the ref, every setter is skipped, and the new tenant reads the old one's
supplier figures — on screen and in the export. A superseded load also still cleared `loading`, so
one period's rows could render and Export under another period's name.

**Top Supplier Share read SAFER the less of a period it could trace.** `attributedPct` divides by
every consumed rupee including the Not-attributed bucket, so a month half-fed from earlier stock
diluted the concentration headline on a card that turns amber at 50%. It is measured against named
suppliers only now, and "No vendor recorded" — a data-entry gap, not a supplier you depend on — can
no longer be named as your largest. **Reliance Gap** had the same mismatch one column over,
subtracting a share-of-everything from a share-of-spend, biasing every supplier low by its own share
of what could not be traced.

**The Ingredient Detail sheet repeated each item's WHOLE-period quantity on every supplier's row**,
beside a fractional per-supplier cost — so a two-supplier item printed its full quantity twice and
the Qty column totalled to a multiple of what was consumed. It carries the supplier's share now,
scaled the same way its value is. And the footer's `% of Sales Cost` was a hardcoded `100.0%` —
S594's own defect, one column to the LEFT of where S594 fixed it.

### S727 — 2026-09-10 — S725 fixed one side of a two-sided invariant, and the re-analysis caught it

**No migration, no Edge Function deploy.** App code changed. `CACHE_NAME` and `APP_VERSION` both
bumped to `crest-v263`.

A 15-lens re-analysis of the three vendor reports ran after S725 shipped, with an adversarial
verifier per finding. 99 verdicts, 71 survived. Two are fixed here; the rest are recorded below.

**S725 broke the S580 tie-out, and the page it broke it on was not the page it edited.** Vendor
Report's returns moved onto the discounted basis (`returnBase`); `supplierAttribution.js`'s
`vendorNetByItem` stayed on the list rate. So the two pages' "Net Spend" and "Net Purchases"
silently stopped agreeing, on a figure three separate places still promise is the same one — the
file's own header comment, the column tooltip, and `.claude/rules/vendor-payables.md`:

```text
bill 10,000 gross · 1,000 discount · fully returned
  Vendor Report       9,000 − 9,000  =      0
  Supplier Contrib.   9,000 − 10,000 = −1,000
```

It is worse than a mismatched column. `vendorShares` takes positive parts only, so a negative net
drops that vendor out of the split entirely and the item's whole consumed value falls into **Not
attributed** — the ranking moves, not just the cell. **Fixing one side of an invariant is how you
break it**, and the rule the fix was following (S722's "a return is credited at its bill's
discounted rate") is stated in a file that does not load for `supplierAttribution.js`.

`netFactors` and `returnBase` moved into `supplierAttribution.js`, beside the
`allocateBillDiscounts` they are derived from — `purchaseTaxSplit.js` imports that, so importing
back the other way was a cycle. It re-exports both, so every existing caller is unchanged.

**The fix would have been a silent no-op without widening two SELECTs.** `netFactors` keys on the
purchase row's `id` and `returnBase` looks up `purchase_entry_id`; Supplier Contribution selected
neither. The fallback is deliberate (a return nobody can price is still a return) and it is exactly
what makes a bad SELECT invisible — no error, just the old numbers. `supplierAttribution.test.js`
pins the tie-out and both no-op shapes, and all five assertions were **verified to fail against the
pre-fix arithmetic** before being kept.

**The bill drilldown was the one part of Vendor Report never touched, so S725 widened a gap rather
than closing it.** `allBills` was still raw `qty × rate` with list-rate returns, so the modal
contradicted the row that opened it. And `remaining = Math.max(0, total − paid)` measured
VAT-inclusive, discount-net payments against an ex-VAT, pre-discount, pre-return total: a 10,000
bill with a 1,000 discount, **paid in full**, read `Partial — NPR 1,000 outstanding`.

It now replicates Outstanding Payables' basis exactly — returns netted per line, then
`calcBillTotals` — because that page is the sole WRITER of `payable_payments`, and a settlement
check that disagrees with the page doing the settling is worse than no check. The `Math.max(0, …)`
is gone (S723: a credit is money), so an over-returned bill reads **Credit** rather than Paid. A
new **Payable** column shows the figure the status is measured against; a `Partial` badge beside a
number that is not on screen cannot be checked. The detail row's `colSpan` was 9 against 10 columns
and is now 11 against 11, and it finally carries the `id` that `RowDisclosure`'s `aria-controls`
had been pointing at all along.

**Still open**, from the same run and not yet fixed — recorded so they are not re-found: Price
Tracker's `items` read is unpaged while the `purchase_entries` read it gates is paged (the
producer/consumer shape, S706/S708); a free line (rate 0, legitimate since S698) is read as a price
point, giving "↓ Down −100%" and switching OFF the >5% warning at maximum divergence; the Stable
band is an absolute NPR 0.01 on a per-base-unit rate, so it swallows a 20% rise on rice-by-the-sack
while catching everything on expensive items; the expanded row emits one `<td>` too many; the
inline editor is keyed by item id while rows are keyed vendor+item. Vendor Report's KPI strip,
split chart and **Export button** are gated on `loadError` but not `loading` (S616 + S601);
"Transactions" counts lines while the drilldown counts bills. Supplier Contribution's `init()`
never claims the page (S721), its `items` read is unpaged, Top Supplier Share is diluted by the
Not-attributed row, and its footer `% of Sales Cost` is a hardcoded `100.0%` — S594's own defect,
one column left of where S594 fixed it.

### S726 — 2026-09-10 — The wastage reason list went from 7 to 19, and stopped being re-typed in the guide

**No migration, no Edge Function deploy.** App code changed. `CACHE_NAME` and `APP_VERSION` both
bumped to `crest-v262`.

The Daily Wastage tab offered seven reasons — Spoilage, Expiry, Over-prep, Breakage, Spillage,
Customer return, Other. Correct, but coarse enough that losses with completely different fixes
collapsed into one bucket: knife trim, a burnt pan, a fridge failure and a mis-keyed order all
landed on `Other` or got misfiled as `Over-prep`. The Wastage Report's By-Reason breakdown is only
as good as the vocabulary feeding it, so a coarse list made that report *look* like it answered
"why" while answering very little.

Twelve reasons added, cut by **what they imply the operator should DO** rather than by what the food
looked like when it was binned — a fridge failure, a burnt pan and a mis-keyed order all end as
discarded food, but the fix is a repair, a training session and a POS habit. The 19 now sit in six
`<optgroup>` headings (Storage & shelf life, Kitchen & prep, Damage & handling, Supplier &
receiving, Service & floor, Loss & other), which is **visual only** — `WastageReport` still totals
by the individual reason exactly as before. New: Power / equipment failure, Contamination, Trim /
prep loss, Remnants / crumbs, Cooking error, Recipe testing, Staff training, Damaged on delivery,
Quality reject, Wrong order, Sampling / giveaway, Theft / pilferage.

**Nothing downstream needed touching, and that was worth proving rather than assuming.**
`wastages.reason` is `text` with no CHECK; `WastageReport.js` builds `byReason` from whatever
strings return and its Excel sheet pivots the same array; every badge is a fixed `badge-yellow`, so
there is no palette to exhaust; there is no reason filter; and the other ~25 wastage reads —
dashboards through `computeUsed()` — select `item_id, qty` and never see the column. Export/restore
move whole rows. So no migration, and every row written under the old seven still displays and
still groups.

**Three reasons were deliberately NOT added, because two of them would deduct the same stock twice.**
Staff meal / Complimentary (own table, own tab, already subtracted separately by `computeUsed()`)
and Supplier return (already netted inside Net Purchases). A generic "stock adjustment" was excluded
for a different reason: it turns wastage into a fudge factor for forcing a physical count to tie,
which is the exact signal Variance and Shrinkage exist to catch. The rationale lives in the
constant's header so the next person to extend the list reads it before adding one back.

**The list moved out of the page and into `src/shared/constants/wastageReasons.js`** — a standalone
module rather than an export from `Stock.js`, so the settings guide can import it without dragging
a lazy-loaded page component into its bundle (S440). `DEFAULT_WASTAGE_REASON` replaces the three
hardcoded `'Other'` literals in `Stock.js` (initial form value, insert fallback, badge fallback),
so the fallback can no longer drift away from the list it falls back to.

**The IMS module guide re-typed all seven reasons in prose, and is now derived from the constant.**
That sentence was the module-guide drift trap in its purest form — a list spelled out in a second
place, with nothing to notice when the first one changes. It now interpolates the count and the
group names, so it cannot rot again. `Help.js` was reworded to describe the *shape* of the list
rather than name members, for the same reason.

**Adding Theft / pilferage changes what the Shrinkage Report means**, so its copy says so.
That report defines shrinkage as *unexplained* loss and listed "theft" as a possible cause; now that
theft is loggable, anything you log is explained and leaves that figure. The word is now "unlogged
theft", with a sentence naming the consequence.

A sibling test guards the three invariants that would otherwise fail silently, since nothing
validates this column anywhere: no duplicate spelling (a duplicate renders twice and totals once),
`'Other'` still present (two call sites fall back to it), and `'Monthly (untagged)'` still absent —
`WastageReport.js` reserves that synthetic label for undated catch-all rows, and offering it as a
real option would merge two different facts into one row of a breakdown that still added up.

**And, found incidentally on the way: no rule file globbed `src/modules/ims/variance/**`.** Four IMS
pages live there — `Variance`, `TheoreticalVariance`, `ShrinkageReport`, `WastageReport` — and both
`ims-figures.md` and `report-pages.md` are written *about* them: `ims-figures.md` carries a section
headed "The variance family" and another headed "`WastageReport` was the one page that did not page
`wastages`". Rules describing, at length, files they had never once loaded for. This is the S713
limitation exactly, one directory further on, and `check-rules-globs` stayed green throughout — every
glob it had matched real files, and it can only report a glob matching NOTHING. Both now glob
`variance/**`, and `ims-figures.md` also globs the new constant, since whoever opens that file is the
person about to add a reason to it.

The tell is recorded in `DOCS-REMEDIATION.md` under T3, and unlike the S713 one it is **mechanical**:
compare the file basenames a rule's prose mentions against the files its own globs resolve to. A rule
that names `WastageReport` fourteen times and cannot load for `WastageReport.js` is a contradiction
visible without understanding a word of the rule. Not built — recorded as the next cheap win.

Root `README.md` and `CLAUDE.md` are deliberately unchanged: the README is a map that states it holds
no feature detail, and a module-scoped rule belongs in `.claude/rules/` by CLAUDE.md's own routing —
which is just as well, with 159 characters left under its ceiling.

### S725 — 2026-09-10 — The vendor reports re-analysed: two tabs of one page disagreed about the same vendor by exactly the bill discount

**No migration, no Edge Function deploy.** App code changed. `CACHE_NAME` and `APP_VERSION` both
bumped to `crest-v261`.

Price Tracker, Vendor Report and Supplier Contribution — the three Pro reports a client uses to
decide who to buy from. Supplier Contribution came through almost clean: it already carried
`firstError`, `useLatestRequest`, a paged read on every period-scoped query, an Excel letterhead,
a computed `% of Purchases` total and the `periods[0]` fallback. Vendor Report carried none of the
last three, and the two pages sat one nav item apart.

**Vendor Report's Vendor Summary tab and its Daily Breakdown tab quoted two different numbers for
the same vendor, and both were labelled Net.** `vendorSummary` computed `gross − discount −
returns`; the `netByDay`/`netByVendor`/`netByVendorDay` maps behind the matrix summed a raw
`qty × rate` with returns off and **no bill discount at all**. One bill of 10,000 with a 1,000 trade
discount read **9,000** on one tab and **10,000** on the other — and the Daily tab's table sat
directly beneath a KPI card still saying 9,000, since the stat strip renders above the tab switch.
The Excel workbook shipped the wrong one on its Daily Breakdown sheet. This is the S551 class the
rules file has been describing since Supplier Contribution was built, one tab apart on a single page.

Both now read one arithmetic: `allocateBillDiscounts()` per line, exposed off the `ix` index as
`lineNetOf`, so the summary column, the matrix, the per-method columns, the drilldown and both
sheets are slices of the same allocation rather than four independent sums.

**Returning a whole discounted bill drove Net Spend negative by the discount.** `vendor_returns.rate`
stores the original line's LIST rate, and it was being subtracted from a base that had already lost
the discount — the exact defect S722 fixed on the VAT reports, still live here. `returnBase()` scales
each return by its own line's net factor; a full return now nets to exactly zero.

**Cash + Credit + FonePay could not add up to the Net Spend two cells away**, twice over: the three
filtered the raw `payment_method` column, so every bill written before that column existed fell into
none of them (S650's `methodOf` rule, un-applied), and all three were gross-minus-returns while
captioned "(Net)". `methodOf` moved out of its private copy in `Purchases.js` into
`purchasesHelpers.js`, which is where the rule said it lived.

**The footer asserted `100%`.** S594's Supplier Contribution finding, verbatim, on a page it never
travelled to — and here it diverged for two independent reasons at once. The rows divide by
`grandNet`, which carries the **Unassigned** (`vendor_id IS NULL`) bills that have no row above the
footer; and the footer printed the whole period's totals under a search-filtered list, so narrowing
to one vendor showed one row above a TOTAL for every vendor. The footer totals exactly the rows
rendered above it now, the percentage is computed, and a line underneath states the period's own
totals whenever a search is active. Unassigned gets a real row — discount, returns, net, share and
all three method columns — instead of a `colSpan={8}` that swallowed four of its own figures.

**`payable_payments` was a bare `.in()`.** One row per LINE per settlement, so it grows faster than
the bills it hangs off — S723 fixed exactly this read on Outstanding Payables and Vendor Balance
Confirmation and left the third page bare. Truncated, every credit bill past row 1000 renders unpaid;
the id list is a URL besides. `fetchAllRowsChunked`.

**Defaulting to the open period is not a default.** `find(status === 'open')` with no `|| p[0]`, the
shape S722 named on Payment Summary. Close the month and the page selected nothing, loaded nothing,
and still drew the full stat grid at NPR 0 with the footer at 100% and the period chip reading `—`,
over a dropdown listing every period. It falls back to the latest period, and `init()` claims the
page through `periodReq.begin()` — the fifth instance of that after S698/S709/S718/S721.

**And the discount table was a fourth copy of `calcBillTotals`.** Both `.claude/rules/vendor-payables.md`
and `purchaseTaxSplit.js`'s own header named this page as one of the four that reach the shared

a hand-copied mirror does, with a duplicate `S675-S699.md` sitting loose at the destination root.
`npm run mirror:docs` (`scripts/mirror-docs.mjs`) copies every `git ls-files "*.md"` at the same
relative path. Three properties are deliberate: the list is `git ls-files`, so `node_modules`,
`build/` and gitignored files are excluded for free **and a new rules file joins the mirror when it
is committed rather than when someone remembers**; it **never deletes**, because the destination
also holds legacy material this repo knows nothing about and a prune with a slightly wrong boundary
would destroy a backup — stale files are reported instead, which is how the duplicate was found;
and a missing drive is a skip rather than a failure, since a docs mirror must never be the reason a
commit fails.
