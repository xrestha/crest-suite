### S731 — 2026-09-10 — The PWA re-analysed: the installed app opened on a page half the clients cannot reach, and every HR notification replaced the last one

No migration. `supabase/functions/hr-push` **needs a redeploy** for its half of the notification
fix; the service worker's fallback makes the behaviour correct in the meantime, so the deploy is
not urgent. `CACHE_NAME` and `APP_VERSION` both bumped to `crest-v267`.

A 15-lens re-analysis of the PWA layer — `public/manifest.json`, `public/staff.webmanifest`,
`public/service-worker.js`, `src/index.js`, `src/utils/installPrompt.js` — and of the one page that
actually depends on it, IMS Stock Count, whose offline branch is the only place outside POS that
writes to IndexedDB.

**The installed app opened on `/stock`.** `manifest.json`'s `start_url` had never moved off the
page this product opened on when it was called Crest Inventory. For an HR-only or POS-only client
that is a route `ModuleGate` bounces to `/dashboard` — the install's first impression is a
redirect — and the public guest QR menu is served from the same origin under the same manifest, so
a diner scanning a table code could be offered "Install Crest Suite" and land on a login page.
Moving it is not free: with no `id` the spec makes the app identity default to `start_url`, so
changing that field alone orphans every existing install and quietly creates a second app. `id` is
now pinned to `/stock` — the value the identity already implicitly held — and `start_url` moved to
`/dashboard`, which updates installs in place. `staff.webmanifest` had carried its own `id` all
along, which is why this only ever applied to one of the two apps.

**Every Crest Staff notification replaced the one before it.** The worker's `tag` fallback was the
constant `'crest-hr'` and `hr-push` has never sent a tag, so all four kinds it sends — Roster
Published, Shift Swap Request, the coworker's response, the manager's decision — collapsed into
one another on the lock screen. A swap request arriving on top of an unread roster publish
*deleted* it; the employee never saw the first. A shared tag is right for repeats and wrong for
everything else, so the function now sends `crest-hr-roster` (deliberately shared: republishing a
month should collapse) and `crest-hr-swap-<request id>` (per request, so two swaps both stand), and
the worker falls back to a title-derived tag so an un-redeployed function behaves too.

**The offline shell could be poisoned by an error page.** The navigation branch cached the response
with no status check at all, so a 5xx or a maintenance page served during a deploy became the
cached offline shell and stayed the offline shell until the next `CACHE_NAME` bump. The same line
had the trap the file's own cross-origin comment describes two branches above: a navigation request
carries `redirect: 'manual'`, a redirect resolves to an opaqueredirect whose status is 0, and
`cache.put()` REJECTS on one — with no `.catch()`, an unhandled rejection in the worker. It now
tests `res.ok && res.type === 'basic'` and catches. It also stores under `'/'` rather than under
each visited URL: Vercel answers every client-side route with the same index.html and the fallback
only ever reads `caches.match('/')`, so the per-URL entries were written and never once read —
dead cache growth, unbounded in the query string, while the shell itself only refreshed on a visit
to `/`.

**An unusable IndexedDB bricked Stock Count, online included.** `init()` is async and nothing
awaits it, so a rejection inside it was an unhandled rejection: `setLoading(false)` never ran and
the page sat on "Loading…" with no error anywhere. Firefox private browsing refuses
`indexedDB.open` outright, and an evicted store does the same — and because `flushQueue()` is the
first thing `init()` does, a local cache nobody needed took down the path that reads the server.
There is now a top-level catch that sets the page's real `loadError`, the cache reads degrade to
"no cache", and warming the cache after a successful server read can no longer fail that read.

**A count the server permanently refuses was retried for ever and never mentioned.** `flushQueue()`
had a bare `catch (_) {}`. Queue a closing count offline, have the month closed before you
reconnect, and the write is refused on every page load from then on — while the only place the
"N pending" badge renders is inside the offline banner, so once back online the stuck entries were
invisible from every screen. Failures are now collected and surfaced through the page's
`ActionError`, naming what is stuck and that a closed month has to be re-opened first.

**A queued write could replay under the next person's login.** `sync_queue` is one IndexedDB store
shared by every account that has used the device, and a Stock op carried only a period id.
`switchOutlet()` in `AuthContext` already refuses to switch while either queue is non-empty for
exactly this reason — sign-out has no such guard, so on a shared counting tablet the next session's
`init()` sent the previous one's counts under its own JWT, RLS refused them, and the refusal was
the one being swallowed above. Ops now carry `clientId` and anything belonging elsewhere is left
alone. An op with no `clientId` predates this and still flushes, since it is far likelier to be
this device's own interrupted count. The badge and the sync banner also stopped disagreeing: one
counted the open period's ops, the other counted all of them.

**`sessionStorage` survives a sign-out in the same tab.** `sessionDataCache`'s keys are
`page_section_clientId` — no user id — so signing out and back in as a different account of the
same client served the previous account's cached page data. The staff-isolation policies are
RESTRICTIVE SELECT filters, so the rows an IMS `staff` rank must not see are exactly the ones an
Owner's cache would hand them. `signOut()` now clears it, the way `switchOutlet()` already did. The
file's header had claimed this was impossible; it now explains why it is not.

**Five unchunked `.in('item_id', …)` deletes on the whole item book.** Save All, Clear All and
Carry Forward pass every visible item into a PostgREST URL, which on a 400-item book is ~15 kB and
a 414 from the proxy long before the row cap matters (S629's rule, unapplied here). All five now go
through `runChunkedByIds`. Each delete already ran before the write that replaces those rows, so a
chunk failing part-way throws and the insert never runs — nothing is destroyed without its
replacement.

**Recorded, not fixed.** The service worker gives the *appearance* of offline capability without
it: assets are cached only on demand, `activate` purges every non-current cache, and `CACHE_NAME`
is bumped on every deploy, so a route whose chunk has not been fetched since the last deploy is a
blank page offline. Related: `skipWaiting()` + `clients.claim()` purge the old cache under an open
tab mid-deploy, so a lazily-imported route chunk can vanish from both the cache and the CDN at
once. A `React.lazy` failure lands in `AppErrorBoundary`, whose "Reloading usually fixes it" is
accurate; an `import('xlsx')` inside a click handler is thrown from an event handler, which that
boundary structurally cannot catch, so an Export button silently does nothing until the page is
reloaded. And `navigator.onLine` only reports a network interface — a write that starts online and
loses the connection mid-flight is reported as failed rather than queued.

### S730 — 2026-09-10 — Settings re-analysed: Save Changes wrote the whole row back, and three renumber buttons reported success whatever happened

No migration, no Edge Function. App code changed. `CACHE_NAME` and `APP_VERSION` both bumped to
`crest-v266`.

A re-analysis of the seven client-side tabs of `Settings.js` — Thresholds, Item / Vendor /
Sub-Recipe / Product Codes, Recipe Categories, Theme — read against every reader of each field and
every other writer of the `settings` row. About twenty findings; two are data-loss shapes.

**Save Changes wrote the whole `settings` row as it stood when the page LOADED.** `form` was seeded
from the row and `save()` sent all of it. `settings` is one row per client that nine other pages
write their own columns onto — POS discount reasons, note presets, ticket routing, reservation
settings, delivery partners, opening hours, TADA rates, the three custom-role schemes S729 just
hardened, the combo discount — so an owner who left Settings open while a manager added a discount
reason on the till, then pressed Save on Thresholds, put the row back the way it was. Both saves
reported success. The same shape had already been found once on this page in the *other*
direction (S701: a platform price saved onto the viewed client's row) and fixed for that one tab.
The page-level button now sends **only the columns its own tabs edit** (`PAGE_FIELDS`), and only
those that differ from the loaded row; the Renumber buttons save their prefix and nothing else
(they used to commit every other tab's unsaved edits as a side effect); Save Categories writes one
column; the logo handlers write one column and now report a failure instead of throwing past a
`saving` flag. A test asserts the shape of the write against a row carrying other pages' columns.

**And any save on the page wiped every unsaved edit on every other tab.** The row is re-read after
each save and the form was reseeded from it wholesale — type a warning level, save the categories,
and the warning level was gone with nothing to say so. The seed now keeps whatever differs from
the row it was *last* seeded from; a different client's row still replaces everything, so an
admin's client switch never carries an edit across tenants (and now also clears the four
regenerate results and the category message that used to survive it — S721's shape, seventh
instance).

**Regenerate All Sub-Recipe Codes collided with itself and said ✓.** `recipes.recipe_code` is
unique per client (`recipes_client_recipe_code_key`), and a one-pass renumber gives row A the code
row B still holds. Postgres refused it — and every per-row result in all three renumber loops was
dropped (`await scopedUpdate(...)` with nothing read back), so the page reported "✓ Renumbered N"
over a half-renumbered list. Two passes now: clear every code that is about to move, then write
the new ones; every row's error is checked, the loop stops at the first failure and says how far it
got, and a run that stopped mid-way completes on the next press.

**Regenerate All Item Codes stamped ITM codes over every sub-recipe's mirror row.** A sub-recipe's
mirror in `items` carries the sub-recipe's own SRC code (Recipes.js writes it at insert, and the
ingredient rows print it) and is hidden from Item Master — so the renumber, reading all `items`,
gave each mirror an ITM number and left the hidden gaps it exists to close. It filters
`is_sub_recipe = false` now. The other half: the sub-recipe renumber changed `recipes.recipe_code`
and never touched the mirror's `item_code`, which nothing else ever updates either; it moves both
together.

**Thresholds accepted 0, '' and a critical level below the warning level.** Every reader is
`parseFloat(x) || default` (`fcThresholds`, `varianceFlagPct`, FIFO's `|| 7`), so a stored 0 *is*
the default while the box says 0. A cleared box sent `''`, which Postgres refuses for `numeric`
with a type error in the user's face. Critical ≤ warning saved happily and made the amber band
unreachable — the tip said "set this higher" and nothing checked. The four boxes now refuse 0 and
negatives, refuse critical at or below warning (naming the level), store a cleared box as NULL,
show the reader's default as the placeholder, and render a stored 0 rather than hiding it behind
`|| ''`. Hints said "Dashboard turns amber" for a level that colours eight pages.

**Removing a category said nothing about what it orphans.** The tab now reads the recipe count per
category (paged), confirms with the count before an in-use category leaves the list, and lists
categories that recipes still hold but the list no longer has, each with an Add-back button. In
`Recipes.js` the form's select had no option for an orphaned category, so it DISPLAYED the first
category while the form still held the old one — the screen and the save disagreed; it is offered
as itself now, marked. `addCat` silently no-op'd on a duplicate (S729's shape); the box was a bare
`<input>` outside any `.form-field`, rendering as the browser's native white box (S593).

**The Theme tab could not select "Follow device".** The provider's `SYSTEM_KEY` is the Crest Staff
app's default and the HR guide referred people to "Settings → Appearance" for it; the main app's
tab listed only the two presets, so a device that already had it saved showed no card marked. A
Follow-device card now, with `aria-pressed` on the row, a name on each hidden colour input (the
label's only content was a swatch), and tokens instead of `rgba(255,255,255,…)` hairlines that are
invisible on Light.

Also: the page-level Save no longer renders on Recipe Categories, Product Codes or Theme (nothing
there for it to save, and on Categories it wrote the STALE list over what had just been typed);
Product Codes went from `window.confirm` to the page's `useConfirm`; the Thresholds and Property
checkboxes dropped the inline 16px box S684 said not to re-add; the form-level error renders
through `ActionError`; and the Help entry, which told a client to "configure business name,
location, VAT number, contact phone, email and website" (all admin-only, and the contact fields
have no editor on this page at all) and that "only admins can change settings", was rewritten
alongside the module guide.

**Recorded, not fixed.** The page requires the IMS Manager rank, but `settings` accepts an UPDATE
from any authenticated account of the client at the RLS level (migration `20260707150000` — POS
staff need it for Table Management's tabs), so a rank check on this page is a check on the page.
The provider and the page both call `loadSettings` on mount — two identical reads. Vendor
renumbering includes archived vendors on purpose (no unique index on `vendor_code`; two suppliers
would share a code the day one is restored), and the message says so.

### S729 — 2026-09-10 — IMS Staff re-analysed: any waiter could read every IMS login's email, and a manager could lock a peer out in two requests

**Migration `20260910120000_staff_list_rpcs_manager_only.sql` must be applied by hand in the SQL

App code changed. `CACHE_NAME` and `APP_VERSION` both bumped to `crest-v265`.

A re-analysis of `ImsStaff.jsx`, its two RPCs and its four `admin-user-ops` actions, read against
`HrStaff.jsx` — the file that was mirrored FROM this one at S430 and then swept in S628 while the
original was not. About twenty findings; the four on the server are the ones that matter.

**`get_ims_staff_list` handed every IMS login's real sign-in email to any authenticated account
of the client.** It gated on `caller_role = 'admin' OR caller_client_id = p_client_id` and nothing
else — the exact shape the 2026-08-10 security review closed on `get_ims_eligible_users`, one file
over. That fix removed the pair that disclosed the **Owner's** email and left the pair that
discloses every **staff** email: a POS PIN waiter or an HR Self-Service employee, whose own
profile row tells them their `client_id`, could call it and read the id, full name, `/login`
email, rank and last-seen of every IMS login. The page redirects an under-ranked visitor, but its
`useEffect` had already fired the RPC before the redirect rendered — **a page guard is a guard on
the page, never on the data.** `get_hr_role_staff_list` was byte-identical. Both now require
admin, the Owner, or a manager of that module: exactly the set `admin-user-ops` lets act on the
result, so nobody lost a capability they had a page for.

**"Managers can only be deleted by admin" was two requests long.** `delete_ims_staff` refused a
manager target; `update_ims_role` had no rank check on its target at all, so an IMS manager could
set a peer manager to "— No Access —" — locking them out of every IMS page — and then delete the
now-staff account. `reset_ims_password` had the same gap, which is worse than a lockout: a manager
could set a peer's password and sign in as them. And nothing anywhere stopped a manager setting
their **own** row to No Access, after which only the Owner could restore them. One helper,
`requireManageableTarget()`, now sits behind role change, delete and password reset for IMS and
HR both: a manager never acts on a peer manager or on their own row (own password excepted).
**The Owner is exempt alongside admin, which is a change** — the old "admin only" delete rule had
never actually kept a manager from an Owner who could clear the role first, so the rule people
believed was in force is the one that now is. The page disables the select and hides Delete on
the caller's own row, marked "(you)"; the server is where it is enforced.

**"Existing User" mode could convert a client's only Owner login into staff.** The Owner is the
absence of staff markers, the eligible list is the set of marker-less logins, and an admin sees
the Owner in it — so one assignment demoted the only account that could reach the Suite features,
manage a manager, or use that mode again. `isLastOwnerLogin()` refuses to convert the last plain
login, on both the IMS and HR actions, and a failed count counts as "last".

**The Help page told the Owner to demote themselves.** Its first tip read *"Start by assigning
your own account the Manager role first if you plan to hand day-to-day IMS Staff management to
someone else"* — the precise trap `accounts-and-logins.md` warns about in bold — and the module
guide called Manager "full Owner-equivalent access", which it never was (no HR, no POS, no Suite,
no Existing User mode, and now no peer managers). Both rewritten; the guide's tier lists gained
the pages added since S419 (Stock Ageing, Fixed Assets, Vendor Balance Confirmation, Supplier
Contribution).

**Adding the first custom role blanked every existing login's role.** The scheme is "custom roles
if any, else the three defaults", so a first custom role of *Store Keeper* replaced Staff /
Supervisor / Manager in every dropdown while every existing login still carried one of those
titles: each row's `<select>` had no option matching its value and rendered **blank beside an
Access Level badge that still said Supervisor**. Remove and Reset to defaults did the same. The
first custom role now seeds from the defaults; a role that logins still hold cannot be removed
(the holders are named); Reset refuses while anyone holds a custom title; and a title that has
somehow fallen out of the scheme renders as its own option with an amber orphan mark. The old
fallback — show the *first* role that shares the login's level — is gone too: with two custom
roles at Staff level it named a role the login had never been given.

**The role auto-fix wrote privilege changes off a dropped read, and dropped its own failures.**
`init()` read `settings` with `.single()` (the S613 trap this file's own `saveRoles` comment
describes), discarded the error, fell back to the DEFAULT scheme, and then invoked
`update_ims_role` for every login whose level did not match — sequentially, after the page had
painted, with each result's error ignored. `.maybeSingle()`; a failed staff or settings read now
stops the page below an `ActionError` rather than rendering "No staff yet. Click + Add Staff"
(S594); the auto-fix runs in parallel and names every row it could not correct. That last part
matters now for a new reason: a peer manager's row is *refused* for a manager caller, and the
refusal should be visible rather than one badge quietly staying wrong.

**Passwords accepted "password".** `passwordValid` was a hardcoded `length >= 8` — the same
literal `ClientDrawer.js` was caught hardcoding at 6 — with no `weakPasswordReason()`, on the one
page that mints real `/login` credentials. Creation and reset now take the product's one policy
(`MIN_PASSWORD_LENGTH`, the common-password list, and nothing built from the business name or the
email), the same check Signup and Reset Password apply; the placeholders read the constant.

Also on the page: no `loadedClientRef`, so an admin switching client let the slower load paint the
previous client's names and emails under the new header and run the auto-fix off that list —
the sixth instance of S721; `load()` after a delete did `setStaff(data || [])`, so a failed re-read

name and cleared the box before the save resolved; five inputs carried an inline style object
instead of `.form-input` (S603 — no `:disabled`, no `[aria-invalid]`, no touch floor); the row
selects shared one `aria-label`; the Add tabs had no `aria-pressed`; and a completed add, delete
or reset left no evidence but a closed dialog — each now says what happened. `HrStaff.jsx` and

**Recorded, not fixed.** Every write on this page goes through the service role, so the

consistent across the three staff pages, left alone.

### S728 — 2026-09-10 — The rest of the vendor-report re-analysis: a "Stable" band that hid a 20% rise on rice

**No migration, no Edge Function deploy.** App code changed. `CACHE_NAME` and `APP_VERSION` both
bumped to `crest-v264`. This closes the 24 findings S727 recorded rather than fixed.

**Price Tracker called a 20% price rise "Stable" on the cheapest things a kitchen buys.** The band
was `Math.abs(last - prev) < 0.01` on a PER-BASE-UNIT rate, so its real threshold was `0.01 / prev`
— a continuum, not a constant. At NPR 250/BTL that is 0.004% and harmless; at NPR 0.05/GM for rice
by the sack it is **20%**, and "↑ Rising Only" hid every one of them. Now a percentage with a tiny
absolute floor, whichever is more forgiving (S644).

**A free line is not a price.** `lineState()` has accepted rate 0 as free goods since S698, and
this page read every one as a price observation: a gift crate rendered **"↓ Down −100%" in green**,
printed Last Rate 0.0000, and switched OFF the >5% master-rate ⚠ on the very item whose rate had
just diverged most — then the next real purchase read as a rise from zero. `priced()` is the one
filter, applied at the five sites that pick a "last" or a "previous". The rows stay in the expanded
history: a free receipt is a real event, it is simply not a price point.

**The `items` read was unpaged while the `purchase_entries` read it GATES was carefully paged**,
under a comment about the very cap it was missing. `itemMap` decides which purchase rows survive,
so this does not shorten a column — past 1000 SKUs it deletes the entire price history of every
item after the cut, from the table, both sheets and the vendor dropdown's count. The
producer/consumer shape from S706/S708 with the halves reversed. Same read on Supplier Contribution.

**The expanded history row emitted 13 cells against a 12-column header**, so every figure in it sat
one column right of its own heading — the rate under "Last Period", the quantity under "Trend", the
change under "Purchases". `colSpan={2}` had already covered Master Rate and Update Rate before the
`no-print` cell added a third.

Also on that page: no `loadedClientRef`, so an admin client switch let the slower, older client's
whole purchase history paint over the new one's; the inline editor was keyed by item id while rows
are keyed `vendor__item`, so one Edit click opened **two** boxes with `autoFocus` landing in the
wrong one; the workbook quoted a per-PACK rate beside a BASE-unit quantity with the pack size
printed nowhere, so `Rate × Qty` was wrong by the conversion factor; the Master Rate tooltip named
a "Gold ⚠" that renders in the accent (oxblood on Modernist Light); and Help promised an
auto-sync that has never existed. The page now also says what a price rise **costs** — rupees on
the latest delivery, beside the count of rising items.

**Vendor Report's KPI strip, split chart and Export button were gated on `loadError` but never on
`loading`.** First paint printed a gold "Gross Purchases NPR 0 / Net Spend NPR 0" above a card
reading "Loading…", every period change held the previous month's money under the new month's chip,
and — the serious half — Export stayed live throughout, building the workbook from the stale index
while `scopeLine` and the filename already read the NEW period. One month's figures inside another
month's workbook, which is the S601 rule verbatim.

**The Daily Breakdown matrix rendered one population in its columns and a different one in its
totals.** Columns were vendors with at least one PURCHASE; "Day Net Total" and the TOTAL row summed
every row in the period, returns-only vendors and unassigned bills included — so the cells could not
be added across to the total beside them. Columns now cover purchases OR returns, Unassigned has its
own column on screen and in the sheet, and the totals follow what is rendered, with the period's own
figure stated underneath when a search narrows it.

**"Transactions" counted line items** while the drilldown one click away counts bills and says so —
a 12-bill vendor with 8 lines a bill read as 96. It is "Bills" now, off the same grouping key the
drilldown uses, with Line Items kept as its own column in the export.

The drilldown — the page's main interaction — was **mouse-only at five sites**: bare `onClick` on
spans, `td`s and a `tr`, no tab stop, no Enter, nothing for a screen reader. All five are real
controls now, on `.btn-linklike`, with the row-level one moved onto the day cell rather than putting
a button role on a `<tr>` (S595/S653). Two coloured sub-marks moved to `.cell-sub`, which carries
the print override that stops a span inside a cell printing pale on white. And `categories(name)`
— fetched on every purchase line since the page was written and referenced nowhere outside the
SELECT — now appears under the item name in the drilldown.

**Supplier Contribution's `init()` never claimed the page** (S721, the fifth instance, fixed on
Vendor Report in S725 and left on its sibling): an admin client switch re-runs it with the previous
client's period id in the ref, every setter is skipped, and the new tenant reads the old one's
supplier figures — on screen and in the export. A superseded load also still cleared `loading`, so
one period's rows could render and Export under another period's name.

**Top Supplier Share read SAFER the less of a period it could trace.** `attributedPct` divides by
every consumed rupee including the Not-attributed bucket, so a month half-fed from earlier stock
diluted the concentration headline on a card that turns amber at 50%. It is measured against named
suppliers only now, and "No vendor recorded" — a data-entry gap, not a supplier you depend on — can
no longer be named as your largest. **Reliance Gap** had the same mismatch one column over,
subtracting a share-of-everything from a share-of-spend, biasing every supplier low by its own share
of what could not be traced.

**The Ingredient Detail sheet repeated each item's WHOLE-period quantity on every supplier's row**,
beside a fractional per-supplier cost — so a two-supplier item printed its full quantity twice and
the Qty column totalled to a multiple of what was consumed. It carries the supplier's share now,
scaled the same way its value is. And the footer's `% of Sales Cost` was a hardcoded `100.0%` —
S594's own defect, one column to the LEFT of where S594 fixed it.

### S727 — 2026-09-10 — S725 fixed one side of a two-sided invariant, and the re-analysis caught it

A 15-lens re-analysis of the three vendor reports ran after S725 shipped, with an adversarial

**S725 broke the S580 tie-out, and the page it broke it on was not the page it edited.** Vendor

```text
bill 10,000 gross · 1,000 discount · fully returned

```

It is worse than a mismatched column. `vendorShares` takes positive parts only, so a negative net

purchase row's `id` and `returnBase` looks up `purchase_entry_id`; Supplier Contribution selected

what makes a bad SELECT invisible — no error, just the old numbers. `supplierAttribution.test.js`

That sentence was the module-guide drift trap in its purest form — a list spelled out in a second

and a missing drive is a skip rather than a failure, since a docs mirror must never be the reason a
