### S741 — 2026-09-11 — Leave approved for a month that does not exist yet was never marked, and an approved unpaid leave was paid in full

No migration, no Edge Function. App code changed. `CACHE_NAME` and `APP_VERSION` both bumped to
`crest-v279`.

Reported from a screenshot: a two-day unpaid leave approved for 7–8 Ashwin 2083, with the banner
*"Approved, but no period exists for: 7 Ashwin 2083, 8 Ashwin 2083. Create the period(s), then
re-approve to mark those days."* The question was the right one — staff ask for leave months ahead.

**Approving a leave is TWO writes, and only one of them has a precondition.** It stamps the request,
and it writes an `hr_attendance` row per day — which is the only way payroll ever learns about the
leave: `payrollCompute`'s `unpaidDays` is summed from rows that exist, and a day with no row is a
paid day. Those rows hang off a `monthly_periods` row.

**And a client may have ONE open period at a time**, enforced by
`monthly_periods_one_open_per_client`. So the instruction on screen could not be followed in either
half: Ashwin cannot be opened while Bhadra is open, and an approved row has no Approve button to
press again — before yesterday's Reopen there was no re-approve path in the product at all.

**Nothing back-filled, and nothing anywhere said so.** `AttendanceSheet.jsx` reads `hr_attendance`
and contains no reference to `hr_leave_requests`. So when Ashwin finally opened, those two days
were simply absent: the Leave page said Approved, the attendance sheet was blank, payroll deducted
nothing, and the employee was paid in full for an **unpaid** leave. The only notice the operator
ever got was a transient banner, about a month three ahead, shown once, to whoever happened to be
approving.

`src/modules/hr/leave/backfillApprovedLeave.js` writes those days at the one moment the write
becomes possible — when the month is minted. Both creation paths call it:
`createPeriodWithCarryForward` and `performPeriodClose`'s open-next. Four choices in it are
load-bearing:

- **It fills only days with no attendance row.** At creation that is every day, so the common path
  is unaffected — but the same helper backs the Leave page's catch-up button, where a month may
  already carry marks. A months-old approval silently overwriting a day someone marked `present` by
  hand is a worse failure than the one being fixed. Skipped days are counted and reported.
- **It reports rather than throws.** The month must open whether or not this lands, so the result
  rides back as `leaveFill` and a failure becomes its own `leave_backfill` stage in `failures` with
  its own sentence — the "two writes in one function can diverge" rule: the second write's silence
  proves nothing, so it gets its own answer. A clean run SAYS what it wrote, because those are real
  rows on a sheet someone is about to run payroll from.
- **One day is sent once.** Two approved requests covering the same day would send the same conflict
  key twice in one upsert, which Postgres refuses outright — losing a whole month's back-fill over
  one double-booking.
- **`findApprovedLeaveGaps()` makes an existing gap visible**, which the back-fill alone cannot do
  for anything already in the ground. It splits into `waiting` (the month has no period yet —
  nobody's to act on, and the banner says so rather than implying a mistake) and `unmarked` (the
  month exists and the days are missing — actionable, with a **Mark approved leave** button). Months
  before the client's earliest period are ignored as imported history, and a failed check renders as
  a failed check: "nothing is missing" is the most reassuring answer this function has, and is
  exactly what an error would otherwise produce.

**The approval banner now says what is true.** A warning that asks for an impossible action is worse
than no warning — it teaches people to ignore the banner. It reads as an OK: the days will be marked
automatically when that month is created, nothing to do now.

17 tests over the back-fill and the gap finder, including the boundary case (a leave running 30
Ashwin → 3 Kartik writes only the two days that are in Ashwin). The first draft of that suite is
worth recording: it asserted against Ashwin as BS month **7**, so every date fell outside the period
and seven tests failed at once — Ashwin is month 6. The test was wrong and the code was right, which
is the good direction, but it is the same class of error the day filter exists to catch, so the
month list is now read off `bsCalendar` in a comment rather than recalled.

Help, both module guides (HR Leave and IMS Periods), `.claude/rules/hr-payroll.md` and
`.claude/rules/closed-periods.md` all updated — the last one because a rule that only loads under
`src/modules/hr/**` is invisible to whoever next edits `closePeriod.js`, which is where the call now
lives. `build:verify` clean; 86 suites / 1102 tests pass.

**And both new banners wore a shape nothing else in the product has.** The design hook flagged a
3px amber rule down the left edge of each card — the side-tab accent — and the check that settled
it took one grep: two matches in the whole codebase, both written this session. `PayrollRun.jsx`'s
stale-draft card has been the product's amber banner since S570 (whole border tinted to 35%, an 8%
fill, `role="alert"`, amber-text headline), so both now use it, lifted into one `amberBanner`
constant with a comment recording where it came from. They also gained the `role="alert"` they
should have had from the start, since they announce a payroll consequence.

The rule worth keeping is the grep, not the shape: **before inventing a treatment for a state, grep
for the treatment this product already gives that state.** A visual form that appears exactly once
is not emphasis, it is drift — and it looks most like a deliberate choice to the person who just
made it. Recorded in `.claude/rules/design-system.md`. Nothing was filed for hss-suite: the
side-tab was introduced and removed inside this session, so there is no defect over there to close.

### S740 — 2026-09-11 — A cancelled leave request was a dead end: Reopen, at manager rank

No migration, no Edge Function. App code changed. `CACHE_NAME` and `APP_VERSION` both bumped to
`crest-v277`.

**Cancel sits on the same row as Approve, and its result could not be undone.** `rejected` and
`cancelled` were the two statuses whose Actions cell rendered a literal `—`: no control, and no
path back through any other screen. A mis-click on the wrong row therefore destroyed the request —
the only recovery was re-typing it, which loses the original dates, the reason the employee gave,
`created_at`, and the audit trail that says who decided what and when. The status CHECK constraint
has always allowed `pending`; nothing but the UI stood in the way.

`reopenRequest()` returns a rejected or cancelled request to **Pending**, clearing `decided_at`.
Three choices in it are load-bearing:

**It reopens to Pending, never straight to Approved.** `approveRequest()` is the one place that
writes the `hr_attendance` rows, and the revert on cancel deleted them. A restore that jumped
straight to `approved` would show an approved leave over an attendance sheet with those days blank
— and payroll reads the sheet, so an unpaid leave would stop deducting and a daily-wage staff
member's paid leave would silently go unpaid. Two clicks that end in a consistent state beat one
that ends in a believable wrong one.

**Manager rank, not the supervisor rank the page opens at.** A supervisor decides requests; undoing
a decision that has already cleared attendance days and moved a balance is the rank above. Admin
and Owner resolve to `manager` on the HR axis, so both pass — the owner who made the mistake can
fix it themselves.

**It re-reads the row's status before writing, the mirror of `decideRequestNow`'s guard.** Same
race, opposite direction: if another session has already reopened *and* re-approved the request,
writing `pending` over it would un-approve a leave whose attendance days stay marked and paid. A
status that is no longer rejected/cancelled refuses with the status it actually found, and — the
part that guard shape usually gets wrong — a failed read refuses too rather than falling through.

Nothing else moves: `leaveUsed()` counts only `status === 'approved'`, so a reopened request is out
of the balance until it is approved again, exactly as it was while cancelled. The existing
`audit_hr_leave_requests` trigger records the reopen with no extra work.

**Leave was the outlier in its own module.** Overtime's row already carries an `Undo` that sets
`pending`, and Payroll Run, Festival Allowance, Incentive Run and Final Settlement all have a
`Reopen` — every HR queue had a way back from a decision except this one, which is why this reads as
a missed sibling rather than a new feature. It is not swept into consistency, though: Overtime's
`Undo` stays at the page's own supervisor rank with no confirm and no freshness re-read, because an
OT entry's undo touches no attendance row. Recorded as a deliberate difference in
`.claude/rules/hr-payroll.md` rather than left to look like an oversight, and filed for the sister
repo in `docs/CROSS-REPO.md` — `src/modules/hr/**` is shared, and the shape worth grepping for over
there is any approval queue with a status whose row renders no action.

**And a Help tip had been describing the opposite of what the code does.** It said rejecting or
cancelling an approved request "reverts those days to Present". It deletes them — deliberately,
since the pre-leave state was never recorded and a guessed `present` fabricates an attendance
record. The Help entry, its tips and the HR module guide now all say blank, and carry Reopen.

### S737c — 2026-09-10 — The new tab fell into the entry grid, and its Save All was wired to Wastage

No migration; service worker `crest-v272`.

S737 added a Settings tab to Stock Count. The entry grid below the tabs was gated by an
EXCLUSION list — `activeTab !== 'summary' && !== 'print' && !== 'daily_wastage'` — so the new tab
fell straight into it: the item table rendered underneath the settings panel, with a Search box,
Clear All and Save All. And all four `fieldKey` ternaries on the page ended in `: 'wastage'`, so
for an unrecognised tab they resolved to the wastage field. **Pressing Save All on the Settings
tab would have written the WASTAGE column of every visible item** — from a screen with no
quantities on it, i.e. blanking the month's wastage for anything the filter showed.

Reported from a screenshot, not caught by the build: every branch was valid JavaScript and the
page rendered without an error.

The fix is the direction, not the case. `FIELD_TAB` is an inclusion map and `fieldKeyOf(tab)`
returns null for anything not in it; the grid renders only when that is non-null, and the three
write paths (`saveRow`, `performSaveAll`, `clearAll`) return early rather than falling back to a
field. **A new tab now renders no grid and resolves no field until it is named** — where before,
a new tab was silently opted into writing wastage.

Generalises past this page: **a list that decides which UI a new case gets should be an inclusion
list, and a `? :` chain over a closed set should have no default arm.** The exclusion list and the
trailing `: 'wastage'` were each individually reasonable, and it was adding a member to the set
that made them dangerous together.

**Grepping for the shape found a second instance, and it is the worst case of it.**
`Purchases.js` gated its **Delete All** button on `activeTab !== 'register'` and resolved the
target with `activeTab === 'purchases' ? 'purchases' : 'returns'` — the same two halves, on a
destructive control. It is correct today only because that page has exactly three tabs, so both
arms are covered; a fourth would have inherited a Delete All aimed at returns. Now names the two
tabs that own the action, and passes `activeTab` rather than defaulting. `HrReports.jsx` carries
the same exclusion shape and was left alone deliberately: what falls through there is a read-only
"No payroll run" empty state. **The shape is urgent where what falls through is a WRITE.**

### S737b — 2026-09-10 — The S737 verification block that could not fail, and the page it broke

**Apply `20260910150000_fix_ims_staff_list_result_types.sql`.** Until it is applied, IMS → IMS
Staff and Stock Count → Settings both render their failed-read card.

S737 rebuilt `get_ims_staff_list` to add `has_pin` and to withhold the synthetic
`*.ims.internal` address. It shipped raising `42804 structure of query does not match function
result type` on every call. `RETURN QUERY` compares attribute type OIDs **exactly**, and
`auth.users.email` is `character varying`, which is not `text` even though the two are binary
coercible. Every column is cast to its declared type now — a property of the statement rather than
of the schema underneath it.

**The migration's own verification block passed, and could not have failed.** It called the
function once, deliberately, so a body that does not type-check would abort the migration instead
of surfacing on a live page — the S735 discipline. But it ran in the SQL editor, where
`auth.uid()` is NULL, so the function's caller check was false and `RETURN QUERY` never executed.
The call proved the function could be entered, not that its body works. Where a body sits behind
an authorisation check, a call the guard rejects is not a test: the fix creates a scratch

### S735 — 2026-09-10 — Every purchase-bill edit had failed since S709: `max()` over a uuid, in a function body Postgres never checked

One migration, no app code, no service-worker bump. **Apply
`20260910130000_save_purchase_bill_uuid_max.sql` — until it runs, Save on any existing bill in
Purchases fails.**

Opening an existing bill in Purchases and pressing Save came back with *"This part of the app is
ahead of the database — a migration hasn't been applied yet"* and, in the fine print,
`42883 · function max(uuid) does not exist`. The migration in question had been applied. S709
taught `save_purchase_bill` to carry `po_id` through an edit with `SELECT max(po_id) INTO v_po_id
…` — and `po_id` is a uuid, a type Postgres ships no `max()` aggregate for. It still applied
cleanly, because **plpgsql does not resolve the SQL inside a function body at `CREATE` time**; each
statement is resolved the first time it runs. So the function existed, S709's own assertion that
its source mentions `v_po_id` passed, and the first person to edit a bill found it. The read sits
inside the `p_superseded_ids` branch, which is every edit and no new bill — new bills kept working,
which is why it took a day. Nothing was ever half-saved: the read is the first statement in that
branch, before the DELETE.

**The fix keeps S709's intent exactly.** One bill is one receipt from one order, so there is a
single non-NULL `po_id` to inherit whether the form kept every line or dropped some, and NULL for
a bill typed in by hand; `WHERE po_id IS NOT NULL … LIMIT 1` picks it without an aggregate. The
function is reproduced in full (CREATE OR REPLACE has no other form) with that one statement
changed, and the assertion block now also refuses a source that still contains `max(po_id)`.

**Two things worth writing down, both now in `.claude/rules/supabase-sql.md`.** A `prosrc LIKE`
assertion proves a feature is *mentioned*, not that it *runs* — S709 had exactly that check and it
passed on a function that could not execute; when a migration changes a body, the verification
block should call it once inside `BEGIN … ROLLBACK`, and this one's does. And `42883` does not
always mean an unapplied migration: `errorText.js` words it that way, which is right for a missing
RPC and was misleading here, where the applied function was the thing calling something that
does not exist. The wording is left alone — the consequence it names (nothing saved, retrying
won't help) was true — but the reader of that sentence should know it has a second cause.

A grep of every migration found this the only `min`/`max` over a uuid column.

No migration, no Edge Function. `CACHE_NAME` and `APP_VERSION` both bumped to `crest-v268`.
New: `src/shared/chunkReload.js` + `chunkReload.test.js`.

S731 closed eight PWA and Stock Count findings and left four on the record as understood but
unfixed. This closes all four. Three of them turn out to be the same fact from different angles:
the app fetches its own code by hashed filename, and nothing had ever handled that fetch failing.

**"Offline" was a white screen after every deploy.** The install handler cached `/` and nothing
else, so offline the document loaded, asked for a `main.<hash>.js` that had never been fetched
under the current `CACHE_NAME`, and rendered nothing at all. That was not an edge case: the version
is bumped on every deploy and `activate` purges every other cache, so it was the state after every
deploy until the user next opened the app online. The install now precaches the shell — `/` plus
the one js/css pair named in CRA's `/asset-manifest.json` `entrypoints`, added one at a time
because `addAll()` rejects as a unit and one 404 would throw away the other. **Deliberately not all
283 files in the manifest**: the route chunks are 3.5 MB and this worker is installed by every
diner who scans a table QR code. What it buys is the difference between a white screen and an app
that boots and can say what is missing.

**A deploy under an open tab broke every lazy route, and the Export buttons worst.** Vercel
replaces the deployment's files and `activate` deletes the cached copies on the same event, so an
open tab loses the ability to load its own code the moment a deploy lands. For a `React.lazy` route
that surfaced as a crash card reading "Something went wrong on this screen" — accurate about the
reload, wrong about the cause, and it sent the reader to support for something that is not broken.
For the 43 `await import('xlsx')` calls sitting in `onClick` handlers with no try/catch it
surfaced as **nothing at all**: an event handler's rejection is exactly what a React error boundary
structurally cannot catch, so the button just did not work. `src/shared/chunkReload.js` decides
whether an error is a stale deploy, `AppErrorBoundary` calls it for the routes, and
`initChunkReloadGuard()` in `src/index.js` listens for `unhandledrejection` and `error` to cover
everything React cannot see. Reloading is the fix rather than a workaround, because index.html is
served `no-cache` and the navigation branch is network-first: the reload gets the new document and
the new hashes.

Three constraints on that guard, each preventing a specific failure. **At most one reload a
minute**, or an error that is not a stale deploy — a chunk that genuinely 500s, a proxy mangling
one file — becomes a reload loop, which is a worse failure than the one being fixed and much harder
to diagnose from a phone. **Never reload while offline**, where the reload is answered from the
cached shell and fails identically, having spent the one attempt allowed; that case gets a sentence
instead, and it is a different sentence — the screen has not been opened on this device since the
last update, which is a fact the reader can act on rather than an error. And **never treat an
ordinary error as a chunk failure**: the test asserts the predicate refuses `TypeError: Failed to
fetch` and a plain null-property read, because a real crash misread as a deploy would be hidden by
the very mechanism meant to recover from it.

**`navigator.onLine` was deciding whether a count could be queued.** It reports whether the device
has a network interface, so it is true on a restaurant wifi with no upstream and stays true when
the signal dies between pressing Save and the request landing. Stock Count branches on it, so those
writes took the direct path, failed, and were reported as lost counts while the offline queue —
which exists for precisely this situation — was never consulted. The failure is now what decides:
`isNetworkError()` is exported from `errorText.js` as a predicate over the same regex the network
message already tested on, and only a dropped connection queues. A refusal never does — an RLS
rejection or a closed-period trigger is a decision the server made, and queueing one retries a
refusal for ever, which is the defect S731 had just finished fixing at the other end.

Safe to replay because every write on that page is idempotent: opening and closing are upserts,
wastage and staff meal are delete-then-insert over the same key, so re-running one converges on the
same rows whether or not the original landed. That is the property that matters, since a dead fetch
never proves the write did not land — only that we did not hear back.

**A queued write is not a saved write, and two places were about to say it was.** The persist
helpers return `'queued'` as a third answer beside true and false, so Save All and Clear All no
longer flash "✓ Saved" over a notice saying the connection dropped — the same contradiction that
page fixed one state along. And because the browser still believes it is online, the amber offline
banner never renders and the pending count lived inside it, so the held entries would have been
invisible from every screen with nothing to send them until the next page load. They get their own
banner now, with a **Sync Now** button, which is the action the situation actually has.

**`sessionStorage` survives a sign-out in the same tab.** `sessionDataCache`'s keys are

**Recorded, not fixed.** The service worker gives the *appearance* of offline capability without

### S727 — 2026-09-10 — S725 fixed one side of a two-sided invariant, and the re-analysis caught it

**No migration, no Edge Function deploy.** App code changed. `CACHE_NAME` and `APP_VERSION` both
bumped to `crest-v263`.

A 15-lens re-analysis of the three vendor reports ran after S725 shipped, with an adversarial
verifier per finding. 99 verdicts, 71 survived. Two are fixed here; the rest are recorded below.

**S725 broke the S580 tie-out, and the page it broke it on was not the page it edited.** Vendor
Report's returns moved onto the discounted basis (`returnBase`); `supplierAttribution.js`'s
`vendorNetByItem` stayed on the list rate. So the two pages' "Net Spend" and "Net Purchases"
silently stopped agreeing, on a figure three separate places still promise is the same one — the
file's own header comment, the column tooltip, and `.claude/rules/vendor-payables.md`:

```text
bill 10,000 gross · 1,000 discount · fully returned
  Vendor Report       9,000 − 9,000  =      0
  Supplier Contrib.   9,000 − 10,000 = −1,000
```

It is worse than a mismatched column. `vendorShares` takes positive parts only, so a negative net
drops that vendor out of the split entirely and the item's whole consumed value falls into **Not
attributed** — the ranking moves, not just the cell. **Fixing one side of an invariant is how you
break it**, and the rule the fix was following (S722's "a return is credited at its bill's
discounted rate") is stated in a file that does not load for `supplierAttribution.js`.

`netFactors` and `returnBase` moved into `supplierAttribution.js`, beside the
`allocateBillDiscounts` they are derived from — `purchaseTaxSplit.js` imports that, so importing
back the other way was a cycle. It re-exports both, so every existing caller is unchanged.

**The fix would have been a silent no-op without widening two SELECTs.** `netFactors` keys on the
purchase row's `id` and `returnBase` looks up `purchase_entry_id`; Supplier Contribution selected
neither. The fallback is deliberate (a return nobody can price is still a return) and it is exactly
what makes a bad SELECT invisible — no error, just the old numbers. `supplierAttribution.test.js`
pins the tie-out and both no-op shapes, and all five assertions were **verified to fail against the
pre-fix arithmetic** before being kept.

**The bill drilldown was the one part of Vendor Report never touched, so S725 widened a gap rather
than closing it.** `allBills` was still raw `qty × rate` with list-rate returns, so the modal
contradicted the row that opened it. And `remaining = Math.max(0, total − paid)` measured
VAT-inclusive, discount-net payments against an ex-VAT, pre-discount, pre-return total: a 10,000

is gone (S723: a credit is money), so an over-returned bill reads **Credit** rather than Paid. A
new **Payable** column shows the figure the status is measured against; a `Partial` badge beside a
number that is not on screen cannot be checked. The detail row's `colSpan` was 9 against 10 columns
and is now 11 against 11, and it finally carries the `id` that `RowDisclosure`'s `aria-controls`
had been pointing at all along.

**Still open**, from the same run and not yet fixed — recorded so they are not re-found: Price
Tracker's `items` read is unpaged while the `purchase_entries` read it gates is paged (the
