# Multi-outlet: one login, several clients (S548)

A group of outlets is several `clients` rows joined by `clients.group_id → client_groups`. An Owner switches between them from the top bar (the drawer's client badge below 768px); the Group Console (`/group-dashboard`, Suite Pro) rolls them up.

**The architecture is selected-outlet indirection, NOT policy rewriting.** `my_client_id()` appears in ~151 places across 18 migrations. Rewriting them to a set-returning `my_client_ids()` would touch every policy on ~50 tables and permanently widen RLS from "one client" to "any client in my group", removing RLS as the backstop behind `scopedDb`'s filter. Instead `profiles.active_client_id` was added and **only `my_client_id()` changed**, to `coalesce(active_client_id, client_id)`. Every policy keeps its exact shape and resolves to the selected outlet. The frontend gets it free: `useScopedDb` binds `clientId` from `AuthContext`, so one value re-scopes ~200 call sites and all 65 `CLIENT_SCOPED_TABLES`.

Both columns default NULL, so an ungrouped client is byte-identical to before — which is what makes this safe to have shipped across the whole book at once.

Five things to know before touching it:

- **`client_groups` splits its policies per command, and that is deliberate (S688).** The house rule in `supabase-sql.md` is one `<x>_all` per table; this table is the exception, because members READ their own group row while only admin WRITES. A single `FOR ALL` would have to carry the member's read clause in `USING` — and DELETE is checked against `USING` with no `WITH CHECK` behind it, so the collapse would let any member delete the group row. `20260907120000` therefore keeps `client_groups_select` and splits the old `FOR ALL` into insert/update/delete, which also clears the `multiple_permissive_policies` lint the `FOR ALL` was causing on SELECT. That migration also grants `authenticated` INSERT/UPDATE/DELETE: `20260812170000` granted SELECT only, while `ClientDrawer.js`'s "Create group" inserts from an admin's browser as `authenticated` — so the write policy may never have been reachable by its only caller.
- **`active_client_id` is privilege-bearing and must never be user-writable.** It decides which tenant every RLS policy resolves to. It is deliberately NOT on `guard_profiles_privileged_columns()`'s allow-list (S531 invariant #1); `set_active_outlet()` is the only write path, and under `SECURITY DEFINER` `current_user` is the owner so the guard passes it through — the same mechanism `record_pos_pin_attempt` relies on.
- **Membership is validated at WRITE time, not in `my_client_id()`.** That function runs per row across ~120 policies, so it stays a join-free `coalesce`; a trigger on `clients.group_id` clears stale selections instead.
- **`clients_select` is the one policy that had to widen** — it was `id = my_client_id() OR is_admin()`, so a customer could not read that a sibling outlet existed at all.
- **Group-spanning reads cannot go through scoped queries** — that's intended. `get_group_summary()` is `SECURITY DEFINER` with its own caller check, returns **raw aggregates** (the page derives food-cost %/labour %, so this doesn't become a fourth definition of those formulas), filters to `suite_plan = 'pro'` **server-side**, and returns excluded outlets by name so the page can state its coverage. A client-side filter would ship an unpaid outlet's revenue to the browser and then hide it.
- **Outlets keep independent periods** (`monthly_periods` is `UNIQUE(client_id, bs_year, bs_month)`), so align on `(bs_year, bs_month)`, never `period_id`. And **`pos_orders` has no `period_id` or BS columns** — only AD `closed_at` — while BS→AD conversion lives in JS, so the RPC takes `p_ad_start`/`p_ad_end` from the caller.

Suite Pro is sold **per outlet**, including inside a group, which is why the console shows only paid outlets and names the rest rather than silently under-reporting. Switching is blocked while the offline queue is non-empty (**both** `getQueue()` and `getPosOrderQueue()` — stock ops write against the current tenant just as POS orders do).

**Who may switch is `profile_outlet_access`, and it grants REACH, never RANK (S617).** An Owner reaches every outlet in the group; anyone else reaches their home outlet plus what they have been allowlisted into, at the same rank they already hold. Deliberately not a per-outlet role matrix — that would put a second rank rule into `AuthContext`, all three `hasXAccess` helpers and `is_client_owner()`. The table has **no write policy at all**, so `set_outlet_access()` is the only path, and a revoke clears `active_client_id` so it evicts rather than merely denying the next switch.

**HQ→branch master-data push is built** (`push_master_data`, S617), and three of its refusals are the rules, not the implementation. **`items.rate` is never pushed on update** — that is what the BRANCH pays its own supplier and the input to every costing figure it produces, so HQ's rate would put another city's prices into its food cost; it is seeded on create only, because the column is NOT NULL. **Selling price is a separate opt-in**, never swept along with the recipe definition. **An ingredient with no counterpart at the branch is reported, never dropped** — a recipe costed from a silently-shortened list is the wrong-number-nobody-questions shape. Records are matched on `master_id` — never by name, because renaming either side would otherwise silently merge two different records — with **one** exception: the first push into a branch that already has data has no `master_id` yet, so it matches by name once, calls it `adopt`, and shows every one in the preview before writing. The preview IS the plan — a dry run computes into a temp table with pure SELECTs and the write pass applies from that same table, because two implementations of "what will happen" is how a preview comes to lie.

**`items` gained `UNIQUE (client_id, lower(name))` in S707, and the push had to learn the word `conflict` in the same migration** (`20260909120000`). Three of its item-write paths could produce a second row with a name the branch already used — a `create` whose name a differently-linked branch item holds, an `update` renaming onto a sibling's name, and the sub-recipe mirror INSERT, which was name-checked nowhere. Under the index each of those raises `23505`, and **the whole push is one function call**, so one colliding item name would have aborted an entire multi-outlet push with a constraint name for a message. `conflict` is a fourth plan action: reported in the preview per branch, naming the record standing in the way, and skipped by the apply pass so everything else still lands. **A constraint added to a shared table is a change to every writer of that table** — find them before adding it, or the index turns a silent duplicate into a loud failure of something unrelated. (`recipes` is still name-unconstrained; only its `recipe_code` carries an index.)

That index also closed a latent fault the adopt join had all along: `lower(a.name) = lower(s.name)` produced TWO plan rows where a branch held two same-named items, and both would have been given `master_id = s.id` — a violation of `items_client_master_key`. The dedupe pass makes that unrepresentable and the index stops it recurring.

**Thirty-eight live policies never called `my_client_id()` at all — they inlined its pre-S548 body** (`client_id = (SELECT profiles.client_id FROM profiles WHERE id = auth.uid())`), so the one-function-change architecture above simply did not reach them. Fixed in `20260909160000` and `20260909180000`. Sixteen came from the baseline and were carried through the `20260812130000` initplan-wrap pass verbatim — that migration was rewriting the `auth.uid()` calls *inside* those expressions and had no reason to read the rest of them. The other nine were written **after** multi-outlet shipped: `pos_cash_movements`, `pos_kot_removals`, the loyalty pair and the reservations pair, each copied from the table next to it. The affected surfaces were Requisitions, POS (orders, items, payments, shifts, tables, KOT, credit notes, customers, cash, loyalty, reservations), Purchase Orders, payables, staff meals, stock movements, budgets, demand forecast and recipe suggestions — i.e. most of the transactional book.

**The first of those two migrations found only 25, and the difference is the lesson.** It was generated by scanning the migration files for `profiles.client_id`; the other thirteen (all of Fixed Assets, Gate Passes, guest order requests, parking slips, payment confirmations) are written with **unqualified** columns — `(SELECT client_id FROM profiles WHERE id = ...)` — which Postgres re-prints qualified in `pg_policies`. The repo's spelling and the catalog's spelling are different, so **a policy audit runs against `pg_policies`, never against the files**. The check below found that on its first run, against the migration that introduced it.

Two things make this shape hard to see and worth a standing check. It is **invisible until the first group exists**: with `active_client_id` NULL the inline expression and the function are byte-identical. And it fails in the **quiet** direction — a switched outlet's reads come back `{ data: [], error: null }`, an empty POS floor and an empty requisition list being indistinguishable from a new outlet. So: **a new client-scoped policy calls `my_client_id()`, never its body**, and this must return zero rows —

```sql
SELECT tablename, policyname FROM pg_policies WHERE schemaname = 'public'
 AND (qual LIKE '%profiles.client_id%' OR with_check LIKE '%profiles.client_id%');
```

**Three defects sat in this feature from S548 until S617 and none were reachable, because no client has ever had a `group_id`.** Worth knowing as a shape: a feature with no users accumulates faults that every review passes over. `set_active_outlet()` and `get_group_summary()` each checked group MEMBERSHIP and called it authorisation, so the Owner-only rule lived only in React; `/group-dashboard` had no role guard at all while the command palette advertised it; and `active_client_id` was read in two places in `AuthContext` and never selected, so switching outlets would have left every scoped query filtering on the home id while RLS resolved to the new one — every client-scoped table returning zero rows with `error: null`.
